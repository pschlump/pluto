= sll_ts

A generic *singly linked list* that is *safe for concurrent use* —
the thread-safe twin of link:../sll/[pluto/sll].  Every operation is
guarded by a `sync.RWMutex`: readers run in parallel with each other,
writers are exclusive.  Like `sll`, it works as a stack
(`Push`/`Pop`/`Peek` at the head), supports O(1) tail insertion
(`InsertAfterTail`), value-based search and delete, and in-place
reversal.

* Elements are stored and returned *by value* (`T`, not `*T`).
* Lists of types comparable with `==` need no equality function:
`sll_ts.NewSll[int]()`.
* Any other type — or equality by a single field — takes a plain equality
function, with no interface to implement.

The public API is identical to `sll` (plus the locking behavior below),
so switching between the two is a package-name change.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.  The link:../sll/[sll README] documents the full API usage;
it applies unchanged.

== Locking behavior

* *Reads* (`Search`, `Peek`, `Len`, `Length`, `IsEmpty`) take the read
lock and release it before returning — they can run in parallel with
each other.
* *Writes* (`InsertBeforeHead`, `InsertAfterTail`, `Push`, `Pop`,
`Delete`, `DeleteFound`, `Reverse`, `Truncate`) take the write lock.
*`Delete`/`DeleteFound` hold the write lock across their search*, so
search-and-delete is atomic.
* *`IterateOver` operates on a snapshot* taken when it is called (one
O(n) copy, under the read lock).  It is safe to mutate the list while
iterating — including from inside the loop — and an iterator never
observes modifications made after it was created.
* *The cursor iterator (`Front`/`Current`) walks the live list*: each
iterator method takes the list's read lock for the duration of that
call only (plus the iterator's own mutex, so one iterator may be shared
between goroutines).  This is race-free, but the iterator observes
concurrent modifications as they happen and terminates early if its
current element is deleted.  Prefer `IterateOver` for a stable view.
* *`Dump` holds the read lock for the whole dump*, so the writer must
not call methods on the same list.

[source,go]
----
for _, v := range list.IterateOver() {
    list.Delete(v) // safe: IterateOver walks a snapshot
}
----

== Errors and panics

Identical to `sll`.  Empty-list and not-found conditions are errors
(`ErrEmptySll`, `ErrNotFound`; compare with `errors.Is`).  The error
precedence matches the plain `sll` package exactly: `Delete` on an empty
list returns `ErrNotFound` (an empty list has no matching value), while
`DeleteFound` on an empty list returns `ErrEmptySll`.  The package panics
in exactly three situations, all programmer errors:

[options="header"]
|===
| Call                               | Why

| `NewSllFunc(nil)`                  | nil equality function, caught at construction time
| Insert-family on a nil `*Sll`      | a nil list cannot store an element
| Insert-family on a zero-value list | no equality function; the message names the constructors
|===

The insert family is `InsertBeforeHead`, `InsertAfterTail` and `Push`.
Everything else tolerates a nil list and the zero value as an empty list.

== Usage

[source,go]
----
package main

import (
    "fmt"
    "sync"

    "github.com/pschlump/pluto/sll_ts"
)

func main() {
    stack := sll_ts.NewSll[int]()

    // Writers from many goroutines share one stack.
    var wg sync.WaitGroup
    for w := 0; w < 8; w++ {
        wg.Add(1)
        go func(w int) {
            defer wg.Done()
            for i := 0; i < 100; i++ {
                stack.Push(w*1000 + i)
            }
        }(w)
    }
    wg.Wait()
    fmt.Println(stack.Len()) // 800

    // Deleting from inside an IterateOver loop is safe: it walks a snapshot.
    for _, v := range stack.IterateOver() {
        stack.Delete(v)
    }
    fmt.Println(stack.IsEmpty()) // true
}
----
