= pluto — Go Generics Data Structures

pluto is a library of classic data structures written with pure Go
generics (Go 1.27+; iterators use range-over-func). Element data is
never boxed into an interface and never unboxed with a type assertion —
ordering and equality are either the type's built-in operators or a
caller-supplied function, never a method call through an interface.

Zero external dependencies (stdlib only, including tests); no binaries
or servers — every structure is its own package.

Every structure comes with tests, checked examples, and — where sharing
between goroutines matters — a thread-safe twin in a `_ts` directory
with an identical public API.

== Common Conventions

* *Ordering never goes through an interface.* Every ordered structure
(trees, skip list, heap family) has two constructors: `NewX[T cmp.Ordered]()`
orders by the type's built-in `<` / `>` operators (integers, floats,
strings — no boxing, no dynamic dispatch), and `NewXFunc[T any](cmp func(a, b T) int)`
takes a caller-supplied comparison function (e.g. a struct ordered by
one field; a reversed function reverses the order). The struct stores
that one function. *Equality-based structures* (the lists, the hash
tables) work the same way: `NewX[T comparable]()` compares with `==`,
`NewXFunc[T any](eq func(a, b T) bool)` takes an equality function.
* *Elements are stored and returned by value* (`T`, not `*T`). No
per-element allocation for the sake of an interface, and find-style
operations return `(T, bool)` instead of a nil-able pointer. The
thread-safe twins return value copies taken under the lock — never a
live `*T` aliasing internal state.
* *Walk callbacks take no `interface{}` userData* — callers capture
state in a closure (Go methods cannot add type parameters, so closures
are the fully generic replacement).
* *Constraint-free containers* (`queue`, `stack`, and their `_ts`
siblings — anything with no ordering and no equality) need no
constructors at all: the zero value is fully usable, including Push.
The string-keyed tries (`trie`, `tst`, and their twins) also have no
constructors — their ordering is inherent in the key bytes, so there
is no comparison function to store and the zero value is usable — and
`stream` (with its twin) is constructor-free the same way: the entry
ordering is inherent in the ID type.
* *A nil container and the zero value behave as an empty container*
for every operation that has a sane answer (searches return
not-found, deletes return false, walks visit nothing). Each package
panics only where no sane answer exists — always a programmer error,
with a message naming the method and the fix (the constructors).
The lists and queues instead report empty/not-found/out-of-range via
sentinel errors (`ErrEmptyQueue`, `ErrNotFound`, ... — check with
`errors.Is`); trees, heaps, and hash tables use `bool`/`(T, bool)`
signals. Each package's README documents its exact panic contract.
* *Thread safety.* A package is not safe for concurrent use unless
its directory ends in `_ts`. The `_ts` twins guard every operation
with an internal `sync.RWMutex` and keep the identical public API, so
switching is a package-name change. Their `All`/`Backward`/`Front`
iterators walk a *snapshot taken under the read lock* (safe to
mutate — even from inside the loop; changes made after the call are
not visible). `Walk`-style callbacks and `Dump` hold the read lock
for the whole traversal, so the callback must not call methods on the
same container. The exceptions are the legacy `DllIter`/`SllIter`
cursors in the list packages, which walk the live list under a
per-call read lock.
* *Compound operations.* Most `_ts` packages — `heap_ts`,
`priority_queue_ts`, `heap_sort_ts`, the hash-table twins
(`hash_grow_ts`, `hash_tab_ts`, `hash_tab_bt_ts`, `hash_tab_dll_ts`,
`cuckoo_ts`, `cuckoo_grow15_ts`, `sharded_hash_ts`), `skip_list_ts`,
`index_pq_ts`, `fenwick_tree_ts`, `segment_tree_ts`, `trie_ts`,
`tst_ts`, `stream_ts`, `hyperloglog_ts`, `lfu_ts`, `lru_ts` and
`bloom_ts` — expose the
*real `Lock`/`Unlock`* plus `Nl`-prefixed no-lock methods
(`NlLen`, `NlSearch`, `NlInsert`, ...) so a search-then-update
sequence can run atomically (and `dll_ts` exposes `Lock`/`Unlock`).
Calling a regular method while the lock is held will deadlock — use
the `Nl*` methods inside. The plain counterparts keep no-op
`Lock`/`Unlock` so the same code compiles against both.

== Linear Structures

=== Queue — `queue/`, `queue_ts/`

A FIFO on a slice, `Queue[T any]` — constraint-free, no constructors,
zero value ready. `Push`/`Enqueue` amortized O(1) (backing array
grows), `Pop`/`Dequeue`/`Peek` O(1) returning `(T, error)`
(`ErrEmptyQueue`). Popped slots are zeroed and the backing array
released on full drain so the GC can reclaim elements. `All`/`Backward`
are range-over-func iterators.

* Good: simplest, fastest FIFO; no per-element allocation; no
comparison function to supply.
* Bad: the moving-window slice reallocates over long grow/drain cycles
— point callers needing stable O(1) memory at `queue_dll` (or `dll`'s
`Enqueue`/`Pop`). Not thread-safe (`queue_ts` is the twin).

`queue_ts` snapshots `All`/`Backward` under the read lock, and `Peek`
returns the value copy taken under the lock — never a pointer into
the queue's internals that could race with a concurrent pop.

=== Queue on a list — `queue_dll/`

A FIFO queue on a doubly linked list.
*Self-contained*, not a wrapper over `dll` (pluto's `dll` requires an
equality function; a queue never compares — the same rationale as
`dqueue` and `stack_sll_ts`). Same API as `queue` — `Push`/`Enqueue`
at the tail, `Pop`/`Dequeue`/`Peek` at the head returning
`(T, error)` (`ErrEmptyQueue`), one panic: the pushes on a nil queue —
but every operation is *strict* O(1) with stable memory: one node
allocation per push, no window that reallocates. `All` head→tail,
`Backward` tail→head via the `prev` pointers; both walk the live list.

* Good: the FIFO for long-lived, grow/drain-heavy use where `queue`'s
slice window would churn; `Backward` is O(1) per step.
* Bad: per-push allocation makes it slower than `queue` for short-lived
queues; not thread-safe and no `_ts` twin — a shared FIFO on the same
list structure is `dqueue_ts`'s `PushBack`/`PopFront`.

=== Stack — `stack/`, `stack_ts/`

A LIFO on a slice, `Stack[T any]` — constraint-free, zero value ready,
single panic (`Push` on a nil stack). `Push` amortized O(1); `Pop`/
`Peek` O(1) returning `(T, error)` (`ErrEmptyStack`); `Pop` zeroes the
vacated slot and releases the backing array on full drain. `All`
numbers from 0 at the *top* (most recently pushed) going down;
`Backward` from the bottom going up.

* Good: same virtues as `queue` for LIFO use.
* Bad: same slice-reallocation caveat; not thread-safe.

`stack_ts` copies a value snapshot at call time for `All`/`Backward`
(the plain package's iterators walk the live stack); it is `stack`
plus the lock.

=== Stack on a list — `stack_sll_ts/`

A thread-safe LIFO stack on a singly linked list — *self-contained*,
not a wrapper over `sll_ts` (pluto's `sll_ts` requires an equality
function at insert, which a stack never uses; wrapping would break the
constraint-free contract — the same rationale as `dqueue_ts` and
`hash_tab`'s own chains). `Push`/`Pop`/`Peek` strict O(1), one node
allocation per push, stable O(1) memory per operation. Own
`ErrEmptyStack` (not `sll_ts.ErrEmptySll`), eager value-snapshot
`All`/`Backward`.

* Good: stable O(1) memory — the stack for long-lived, grow/drain
heavy use where the slice window would churn.
* Bad: per-push allocation makes it slower than `stack_ts` for
short-lived stacks; `_ts`-only (no plain twin — use `stack`).

=== Double-Ended Queue — `dqueue/`, `dqueue_ts/`

A deque on a doubly linked list — self-contained, not a wrapper over
`dll`/`dll_ts` (pluto's `dll` requires an equality function; a deque
never compares, and the `prev` pointers make `PopBack`/`Backward` O(1)
per step). The plain package is `dqueue_ts` with the lock left out.
`PushFront`/`PushBack`/
`PopFront`/`PopBack`/`PeekFront`/`PeekBack` all O(1) returning
`(T, error)` (`ErrEmptyDeque`); two panics: the two pushes on a nil
deque. Used one-ended it is a stack; `PushBack`+`PopFront` is a FIFO.
`All` front→back with index 0 at the front; `Backward` back→front with
indexes matching `All`'s assignment — the plain package walks the live
list (O(1) extra space), the ts twin snapshots.

* Good: strict O(1) at both ends, stable memory, value semantics.
* Bad: per-element allocation; the plain package's iterators require
the deque to hold still while looping (the ts twin snapshots instead).

=== Singly Linked List — `sll/`, `sll_ts/`

Generic SLL storing `T` by value with head and tail pointers.
Equality-based: `NewSll[T comparable]()` compares with `==`,
`NewSllFunc` takes an equality function — consulted *only* by
`Search` and the `Delete` calls built on it; stack
and positional ops never compare. `Push`/`InsertBeforeHead`, `Pop`,
`Peek` at the head, `InsertAfterTail` O(1); `Search`, `Delete`,
`Reverse` (in place), `Truncate`; iteration via the `SllIter` cursor
(`Front`/`Current`, forward only) and `IterateOver`
(`iter.Seq2[int, T]`). Error API: `ErrEmptySll`, `ErrNotFound`, with
fixed precedence (`Delete` on empty returns `ErrNotFound`;
`DeleteFound` returns `ErrEmptySll`).

* Good: O(1) push/pop at both ends; constant memory per element;
`sll_ts` adds the `sync.RWMutex` and a snapshot `IterateOver`, so
the loop body may safely call list methods.
* Bad: `Search`/`Delete` are O(n) — a list is not a lookup structure;
`DeleteFound` is a *value-based re-search* (O(n)) — use `dll` for
O(1) delete-by-node. Careful: a one-variable `range` over
`IterateOver` yields the *index*, not the value.

=== Doubly Linked List — `dll/`, `dll_ts/`

Generic DLL storing `T` by value — the broadest list API in the
library. Head ops (`Push`/`InsertBeforeHead`, `Pop`, `Peek`), tail ops
(`Enqueue`/`AppendAtTail`, `PopTail`, `PeekTail`), positional
`Index`/`IndexFromTail` (walks from the nearest end), `Search`/
`ReverseSearch` returning `(*DllElement, pos)` with a `-1` sentinel,
O(1) `DeleteFound` given that element, `DeleteAtHead`/`DeleteAtTail`,
`DeleteSearch`, `Reverse`/`ReverseList`, `Trim`/`TrimTail`, `Concat`,
`Truncate`, `Dump`, plus four iteration styles (the legacy `DllIter`
cursor with `Front`/`Rear`/`Current`/`Pos`, `Walk`/`ReverseWalk`
callbacks, `All`/`Backward` range-over-func). Usable directly as a
stack or a queue. All end operations O(1); `Index`/`Search` O(n)
(n/2 average). Error API: `ErrEmptyDll`, `ErrNotFound`,
`ErrOutOfRange`, `ErrInternalDll`. Equality-based constructors like
`sll`. The stored `eq` is consulted only by the search-style calls.

* Good: O(1) at both ends, *O(1) delete-by-node* (the handle from
`Search` splices through the `prev` pointer — the reason to pick dll
over sll), bidirectional iteration.
* Bad: per-element node allocation (slower than slice `queue` for pure
FIFO); two opposite-of-the-trees conventions to remember —
`Walk`/`ReverseWalk` return *true to stop*, and `Search` returns
the element handle, not `(T, bool)`.
* `dll` is not thread-safe. Its `Lock`/`Unlock` are no-ops kept so
code written against `dll_ts` compiles unchanged; `dll_ts` has the
*real* lock. `dll_ts` `Delete` holds the write lock across its
search (atomic search-and-delete), `Concat` snapshots the source
under the source's lock first, and its `DllIter` walks the live list
under per-call read locks — unlike the snapshot `All`/`Backward`
(which, as in `sll_ts`, yield the *index* in a one-variable
`range`).

== Trees

All trees store `T` by value with the two-constructor pattern
(`NewX[T cmp.Ordered]` / `NewXFunc(cmp)`); duplicates replace on
insert. The shared API is `Insert`, `Search`, `Delete`,
`FindMin`/`FindMax`, `DeleteAtHead`/`DeleteAtTail` (splice the extreme
node in a single descent — no FindMin+Delete round trip),
`IsEmpty`/`Len`/`Length`, `Truncate`, `Depth`, `Dump`, and
`All`/`Backward` range-over-func iterators. Not thread-safe — see the
`_ts` twins.

=== Unbalanced BST — `binary_tree/`, `binary_tree_ts/`

A plain binary search tree: average O(log n) insert/search/delete,
worst case O(n). The fullest tree API: `DeleteMatch` (custom matcher),
`WalkFunc` and `WalkInOrder`/`WalkPreOrder`/`WalkPostOrder` callbacks,
`Index(pos)`, `Reverse`, `Front`, `Depth` (O(n) walk). Panics in
exactly two situations: `NewBinaryTreeFunc(nil)`, and `Insert` on a nil
or zero-value tree — everything else tolerates nil/zero as an empty
tree.

* Good: simple, no balancing overhead or color/height bookkeeping; the
reference implementation the balancing trees are measured against.
* Bad: *worst case O(n)* — sorted input degenerates it into a linked
list. Use `avl_tree` or `rb_tree` when input order is not random.

`binary_tree_ts` adds the `sync.RWMutex`; `Front`/`All`/`Backward`
iterate `snapshotInOrder()` taken under the read lock.

=== AVL Tree — `avl_tree/`, `avl_tree_ts/`

Self-balancing BST keeping child heights within 1, so
insert/search/delete are *guaranteed* O(log n). Every node caches its
subtree height, so `Depth` is O(1) (and `Height(e)` reads a node's
cached height in O(1)). The richest tree: three walk orders with
early-stop callbacks, `All`/`Backward`, `Index`, `Reverse`, `Front`,
`Dump`, and the whole-tree set operations — `Copy`, `Union`, `Minus`,
`Intersect`. The set operations snapshot their operands before
rebuilding the destination (a source may alias the destination), and a
zero-value destination adopts an operand's comparison function.
`Insert` returns bool (added vs duplicate-replaced).

* Good: hard O(log n) bound; O(1) `Depth`; set operations you will not
find elsewhere here; `avl_tree_ts` has the same API behind the
RWMutex with snapshot iterators.
* Bad: rotations make inserts/deletes slightly heavier than red-black;
`Index` is O(n); no `DeleteMatch`/`WalkFunc` (unlike `binary_tree`).

=== Red-Black Tree — `rb_tree/`, `rb_tree_ts/`

Classic CLRS-style red-black tree with parent pointers. All ordered
operations worst-case O(log n) (longest path within 2× the shortest)
and deterministic — unlike `skip_list` (expected-case) and
`binary_tree` (degrades on sorted input). Iterators (`All`/`Backward`)
are successor/predecessor walks over the parent pointers: O(1) extra
space, no stack, no snapshot. Deliberately the leanest tree API — no
`Index`, `Reverse`, `Walk*`, `Front`, or set operations; just
insert/search/delete, min/max, head/tail removal, the color-aware
`Dump` (`data(R)`/`data(B)` lines), and the iterators. `Depth` is an
O(n) walk (the value it returns is O(log n)).

* Good: strongest complexity guarantees; cheapest iteration (O(1)
space, live walk); smallest surface to get wrong.
* Bad: smallest API of the trees — reach for `avl_tree` when you need
set operations, positional `Index`, or O(1) `Depth`.

== Skip Lists — `skip_list/`, `skip_list_ts/`

Probabilistic ordered map: towers up to 32 levels, level probability
0.5, drawn from the *global* `math/rand/v2` source. Expected O(log n)
insert/search/delete; `FindMin` O(1), `FindMax` O(log n);
`DeleteAtHead`/`DeleteAtTail`; `Truncate` O(1); per-level `Dump` for
debugging. Every forward pointer carries a *span* (the number of
level-0 nodes it skips — Redis `zskiplist` style), which makes the
positional/range family O(log n): `Rank`/`AtIndex` (0-based position
and its inverse), `Ceil`/`Floor`, `CountRange`,
`Range`/`RangeBackward` (iterators over lo ≤ x ≤ hi yielding global
ranks, O(log n + m)), `DeleteRange`/`DeleteByRank` (bulk removal,
O(log n + m)). API is lean like `rb_tree` (no `Index`/`Walk*`/`Front`/
set ops — the span family replaces `Index`). Duplicates replace.
Because tower heights come from the global source, outputs that depend
on them (`Dump` line counts, the `level` field) are nondeterministic —
never asserted in tests/examples. `All` walks the level-0 chain in
O(1) space; `Backward` collects it into a slice (O(n) space — no back
pointers).

* Good: unlike `binary_tree`, does *not* degrade on sorted input;
simpler to reason about than balanced-tree rotations; ordered
iteration for free; span-backed rank/range queries without the
balancing machinery a ranked tree needs.
* Bad: expected-case, not worst-case, bounds (use `rb_tree` for hard
guarantees); `FindMax`/`DeleteAtTail` are O(log n), not O(1);
`Backward` costs O(n) space.

`skip_list_ts` is the twin with the RWMutex and snapshot iterators;
its `Range`/`RangeBackward` snapshot only the m elements of the range,
and it exposes the real `Lock`/`Unlock` plus `Nl*` no-lock variants of
the positional/range methods for atomic compounds such as
rank-then-delete.

== Streams — `stream/`, `stream_ts/`

The Redis stream as a plain Go structure: an append-oriented log of
entries keyed by strictly increasing `<ms>-<seq>` IDs, with consumer
groups and pending-entry tracking (the XADD/XRANGE/XREAD/XGROUP/XACK/
XCLAIM/XAUTOCLAIM semantics; built for the Ultima Redis-clone).
Constructor-free like the tries — the ordering is inherent in the ID
type (`CompareID`), so the zero value is ready to use. Storage composes
`pluto/skip_list` keyed by ID: O(log₂ n) add/seek, O(log₂ n + m)
`Range`/`RevRange` (inclusive bounds; RevRange takes (end, start)
mirroring XREVRANGE), and span-backed O(log₂ n + k) trims by rank
(`TrimMaxLen`/`TrimMinID`). `Add` copies the ordered field pairs
(duplicates allowed, as in Redis) and enforces the ID rules as errors:
`ErrIDTooSmall` (equal/smaller than last — so 0-0 is never an entry
ID), `ErrIDExhausted`; `ID{Ms, Seq: AutoSeq}` asks for the next
sequence of that millisecond. `LastID` survives delete/trim;
`SetLastID` is the XSETID support. The package's only panics are `Add`
and `CreateGroup` on a nil stream.

Consumer groups deliver entries to named consumers (`ReadGroup` with
after = MinID is the Redis `>` form; any other floor is a replay that
does not move the group's last-delivered ID), track them in a per-group
PEL ordered by ID, and reclaim them: `Ack`, `Pending`/`PendingRange`,
`Claim` (min-idle gated) and cursor-based `AutoClaim` with the Redis 7
deleted-IDs report. Deleting or trimming entries *never touches the
PELs* — Redis behavior — so abandoned work over evicted data is
discoverable. `GroupNames`/`GroupLastID`/`GroupConsumers` plus
`Pending` are the XINFO surface.

* Good: the whole stream command family's data structure in one
dependency-free package; drop-in `_ts` twin; model-tested against a
reference implementation at fixed seed.
* Bad: expected-case (skip list) bounds, not worst-case; the PEL is
  per-group (no per-consumer sub-index — scans filter by consumer);
  `Range` on the plain package walks live storage (mutate-and-iterate
  is a `stream_ts` snapshot away).

`stream_ts` guards a plain `stream.Stream` value with one RWMutex (the
`hash_tab_bt_ts` composition pattern) and aliases the ID/Entry/
PendingEntry types, so switching twins is an import change: snapshot
`Range`/`RevRange`, real `Lock`/`Unlock` plus the full `Nl*` mirror for
atomic read-then-ack compounds. Concurrent appends use the AutoSeq
form — the next-sequence resolution runs under the lock, which is how
a Redis server assigns XADD IDs.

== HyperLogLog — `hyperloglog/`, `hyperloglog_ts/`

The Redis PF* sketch as a plain Go structure: an `Hll` approximates the
number of *distinct* byte strings added, in a fixed 12 KiB of dense
6-bit registers (m = 2^14), never storing an element. `Add` hashes with
a frozen xxHash64 (seed 0 — pinned bit-for-bit against the xxHash
reference suite's vectors; not Redis's MurmurHash64A, which the request
note made optional) and raises one register, returning whether anything
changed (the PFADD reply). `Count` estimates: LinearCounting below the
2.5m threshold while zero registers remain (near-exact — the noise is
the 0.55%-relative register-collision floor), Ertl's σ/τ corrected
estimator above it (the estimator current Redis ships; standard error
≈ 0.81%) — and caches the result (atomics, so the twin can `Count`
under its read lock). `Merge` is the register-wise maximum, the
lossless HLL union — splitting a set across sketches and merging is
*bit-identical* to adding everything to one, which the tests assert.
`Bytes`/`HllFromBytes` serialize to the frozen 12288-byte dense form
(corrupt input → `ErrBadLength`/`ErrBadRegister`, never a panic).
Non-generic over elements (`[]byte` hashed on the way in — the
union_find/suffix_array precedent) and constructor-free (no comparison
or equality exists to store; zero value ready, `NewHll` is convenience).
Two panics: `Add` on nil, and `Merge` into nil that would fold in a
non-empty operand.

* Good: distinct counts in constant memory with Redis-compatible
accuracy (measured 0.4–0.7% mean error from 1k to 10M); lossless
mergeable unions; ~127M adds/s single-goroutine, zero allocations.
* Bad: an estimate, not an exact count (±0.8%); no element removal or
iteration — a sketch is write-only besides the count; fixed precision
(16384 registers, 12 KiB — no sparse encoding yet).

`hyperloglog_ts` is the twin with the RWMutex: reads under the read
lock, `Merge` snapshots operands under their own read locks before
taking the destination's write lock (no nested locks, so opposite-way
merges cannot deadlock), plus the real `Lock`/`Unlock` and `Nl*`
methods for atomic add-batch-then-count compounds.

== Bloom Filter — `bloom/`, `bloom_ts/`

The classic Bloom filter (Bloom 1970) as the pluto-standard port of
the author's 2016 `bloom-filter` library: a fixed-shape bit array that
approximates set membership with one-sided error — `Add` sets k probe
bits, `MayContain` checks them all, an added element *always* reports
present (false negatives are structurally impossible) and an absent
one reports present at rate ≈ p. `NewBloom(n, p)` sizes the filter
from the workload (m = −n·ln(p)/(ln 2)² bits, k = ln(2)·m/n probes,
the classic optima); `NewBloomBits(m, k)` takes the shape directly;
`TestAndSet` is the 2016 library's atomic insert-if-absent signal.
The hash pair is frozen — MurmurHash2 under a fixed seed plus
SuperFastHash, both now faithful to their C originals (the 2016 port's
`uint32(data[1] << 8)` shifts inside the byte type and silently
dropped every odd byte; the fixed hashes are pinned by vectors
generated from the compiled C) — and generalized to any k via
Kirsch–Mitzenmacher double hashing. `Merge` is the bitwise OR (the
lossless union; merging k shards is bit-identical to adding everything
to one filter — the tests assert it), `Count` estimates distinct
elements from the fill ratio, `Added` counts insertions exactly.
Elements are `[]byte` hashed and forgotten (the hyperloglog precedent);
deletion is not possible. Panics: constructor validation, writes on a
nil/zero-value filter (the shape must exist first — the lru capacity
precedent), and `Merge` shape mismatches; serialized corruption is
errors (`ErrBadLength`/`ErrBadHashes`/`ErrBadBits`).

* Good: ~24 ns/op zero-alloc `Add` for 16-byte elements (hash-bound —
the two hashes cost ~3.4 ns each); measured false-positive rates
0.5×–1.6× of p at the design load; mergeable, serializable, and
`Count`/`Saturation` are O(1) (incrementally maintained counters).
* Bad: an *approximation* — false positives at rate p, no deletion, no
iteration (membership is the only query); the shape is fixed at
construction (past the design load the false-positive rate climbs —
watch `Saturation`); no removal means unbounded workloads need a
rebuild.

`bloom_ts` is the twin with the RWMutex: reads under the read lock,
`Merge` snapshots operands under their own read locks before the
destination's write lock (the hyperloglog_ts pattern — no nested
locks, opposite-way merges deadlock-free), plus the real
`Lock`/`Unlock` and `Nl*` methods — batch insert-if-absent under one
`NlSaturation` view is the canonical compound.

== LFU Frequency Counters — `lfu/`, `lfu_ts/`

The Redis LFU eviction mechanism as a generic structure (built for the
Ultima Redis-clone's `allkeys-lfu`/`volatile-lfu` policies and `OBJECT
FREQ`; the LRU counterpart is `lru`). Two layers: a standalone
`MorrisCounter` — the 8-bit logarithmic counter in Redis's exact form
(`LFULogIncr`: increment with probability `1/((v-5)·logFactor+1)`,
certain at or below `InitVal` = 5, saturating at 255) with `Decay` —
and `Lfu[K comparable]`, the keyed table mapping each key to a counter
plus a 16-bit last-access-minute. `Touch` is Redis's `updateLFU`:
decay by the elapsed full periods, then the probabilistic increment,
then retimestamp; `Counter` reports the decay-adjusted view without
storing it (the `OBJECT FREQ`/eviction value); `IdleMinutes` is the
`OBJECT IDLETIME` signal. Storage is `hash_grow` (intra-pluto
composition, eq/hash reading only the key field), so everything is
O(1) average. `NewLfu(logFactor, decayTimeMinutes)` takes the two
Redis knobs (`DefaultLogFactor` 10 / `DefaultDecayTime` 1 are its own
settings); `NewLfuWithClock` injects the clock so tests are
deterministic. The 16-bit minute clock wraps every ~45.5 days, and
Redis's wrap arithmetic is mirrored exactly, boundary quirk included.
Panics: `NewLfuWithClock(nil clock)` and `Touch`/`Add` on a nil or
zero-value table; every read tolerates nil/zero.

* Good: ~41 ns/op zero-alloc Touch — cheap enough for per-command
  bookkeeping; hot/cold separation of ~10 counter standard deviations
  across a 100× access difference; the distribution matches Redis
  (trial means within a few percent of the fluid-limit expectation,
  and of the table printed in redis.conf).
* Bad: the counter is a probabilistic estimate (sd ≈ 2 at 1k accesses,
  ≈ 7 at 100k); idle time past the 65535-minute wrap is invisible to
  the 16-bit clock — both inherent to the Redis design it mirrors.

`lfu_ts` is the twin with one RWMutex (the note's guidance: Ultima
calls these inside shard owner-goroutines, so the simple single lock
suffices) plus the real `Lock`/`Unlock` and `Nl*` methods — the
eviction scan is the canonical compound: `Lock`, `NlCounter` over the
sampled candidates, `NlDelete` the coldest, `Unlock`.

== Capacity-Bounded LRU — `lru/`, `lru_ts/`

The recency counterpart to `lfu`: `Lru[K, V]` is a map for O(1)
lookups plus a recency list (MRU at the front), capacity-bounded with
an eviction *veto* callback — `NewLruFunc(capacity, evictable)`,
where `evictable(k, v) == false` skips that entry and evicts the
next-older one — and a *soft cap*: when nothing is evictable the cache
temporarily exceeds capacity instead of stalling (`b_tree_disk_ts`'s
block cache depends on this: dirty/pinned blocks must never be
evicted). `Get` re-marks the hit MRU, `Peek` looks without reordering,
`Put` evicts down to capacity before inserting, `All`/`Backward`
iterate MRU→LRU / LRU→MRU over the live list. Panics: `capacity < 1`
at construction and `Put` on a nil/zero-value cache.

`lru_ts` is the twin (built for Ultima's `allkeys-lru`/`volatile-lru`,
one cache per shard): one RWMutex with a lock split worth knowing —
`Get` takes the *write* lock (a hit mutates the recency list; `Peek`
is the read-lock form; measured ~7 ns lock overhead uncontended, and
at 8 goroutines `Get` serializes at ~135 ns while `Peek` readers share
at ~86 ns), snapshot `All`/`Backward` (safe to mutate from inside the
loop), and the real `Lock`/`Unlock` + `Nl*` surface — the atomic
batch put with eviction-to-capacity is the canonical compound. The
veto callback runs with the write lock held: it must not call back
into the cache (deadlock), which the twin's docs state prominently.

== Heaps and Priority Queues

=== Min-Heap — `heap/`, `heap_ts/`

Generic binary min-heap adapted from the stdlib `container/heap` (Go
Authors attribution kept) but with a plain method API and a stored
comparator — no interface boilerplate. `Push`/`Pop`/`Delete`/`Fix`/
`SetValue` O(log n); `Peek`/`GetValue` O(1); `Search` O(n) returning
`(T, pos, bool)` with a `-1` sentinel. *Indexed operations report
`false` on out-of-range instead of panicking.* `AppendHeap` bulk-
appends unordered, then `Heapify` rebuilds bottom-up
(`i = Len()/2-1` down to 0). `All` yields *internal breadth-first
order, not sorted order* — drain with `Pop` for sorted order; `Dump`
prints the indexed internal-order listing. `Pop`/`Delete` zero the
vacated slot and release the backing array on a full drain. A reversed
comparator makes it a max-heap. Three panics:
`NewHeapFunc(nil)`, `Push`/`AppendHeap` on nil or zero-value.

* Good: full heap API including delete/fix-by-index, which the stdlib
wrapper makes awkward; value semantics throughout.
* Bad: `All`'s order surprises people (it is the internal array, not
sorted); not thread-safe.

`heap_ts` is the twin with the RWMutex, eager value-snapshot `All`,
and the *real `Lock`/`Unlock` plus `Nl*` methods* (`NlLen`,
`NlGetValue`, `NlPush`, `NlPop`, `NlDelete`, `NlFix`, `NlAppendHeap`,
`NlHeapify`) for compound operations; reads return value copies taken
under the lock, never pointers aliasing heap elements.

=== Priority Queue — `priority_queue/`, `priority_queue_ts/`

Generic min-first priority queue *composed on `pluto/heap`* (the
heap is exactly the building block — an intra-pluto composition).
`Peek` O(1); `Insert`/`Pop` O(log n); `Search` O(n) returning
`(T, pos, bool)`; `UpdatePriority(pos, v)` replaces in place and
re-heapifies in O(log n); positional `Delete` O(log n). `All` yields
*priority order — genuinely sorted, unlike the heap's `All`* — by
draining a private snapshot copy (non-destructive; safe to mutate the
queue from inside the loop). Value semantics throughout; three panics
mirroring the heap's.

* Good: priority-ordered non-destructive iteration; in-place priority
updates; `UpdatePriority` is cheaper than delete+insert.
* Bad: positions from `Search` are invalidated by any mutation; the
plain variant is not thread-safe.

`priority_queue_ts` composes `heap_ts` the same way: real
`Lock`/`Unlock` delegating to the heap's, `Nl*` methods for atomic
search-then-update sequences, and `All`'s snapshot copied out under
the heap's *write* lock then drained privately.

=== Heap Sort — `heap_sort/`, `heap_sort_ts/`

A convenience sorter layered on `pluto/heap`: insert items (`Insert`
O(log n), or `InsertArray` — bulk append plus one bottom-up rebuild,
O(m+n)) then `Sort()` (ascending) or `SortDown()` (descending), each
O(n log n). Sorting *drains* the sorter; it is reusable afterwards
and returns a `[]T` of copies (not in-place; not stable — equal
elements may come out in any order). Batches are copied in, so the
caller's slice can be mutated afterwards. Three panics mirroring the
heap's.

* Good: the cheapest way to sort with this library; `InsertArray`
beats per-element `Insert`.
* Bad: allocates the result; not stable; not thread-safe (see
`heap_sort_ts`).

`heap_sort_ts` composes `heap_ts` (like `priority_queue_ts`): no lock
of its own, `Lock`/`Unlock` delegate to the heap's, and the three
multi-step operations — `InsertArray` (append+rebuild) and
`Sort`/`SortDown` (drain) — hold the heap's write lock for the whole
operation, so each is *atomic*.

=== Indexed Priority Queue — `index_pq/`, `index_pq_ts/`

Sedgwick's §2.6 `IndexMinPQ`: a min-first priority queue where the
client owns stable indices `0..n-1` and can `Change` (decrease-key) or
`Delete` by index. *Self-contained* — not composed on `pluto/heap`,
because the inverse position map (`qp[]`, index → heap position) must
be maintained inside swim/sink, which the heap does not expose (the
same self-contained rationale as `stack_sll_ts`/`dqueue`). Two-
constructor ordering like `heap` (`NewIndexPQ(n)` /
`NewIndexPQFunc(n, fx)`; max-PQ via a reversed comparator).
`Insert(k, v)` *replaces* the value if k is already present (the
trees' duplicates-replace convention); `Peek`/`Pop` return the minimum
as `(index, value, ok)`; `All` drains a private snapshot in priority
order (non-destructive). Insert/Change/Delete/Pop O(log n);
Peek/Contains/Value O(1). This is the priority queue Dijkstra and
Prim want.

* Good: decrease-key by client index in O(log n); stable client-owned
indices — none of `priority_queue`'s stale-position problem.
* Bad: the index space `0..n-1` is fixed at construction.

`index_pq_ts` is the twin with the RWMutex, snapshot `All`, and the
compound-op surface (real `Lock`/`Unlock` + `NlLen`/`NlContains`/
`NlValue`/`NlInsert`/`NlChange`/`NlDelete`/`NlPop`).

== Hash Tables

All four families are equality+hashing structures with two
constructors: `NewHashTab[T comparable](n)` uses `==` and hashes with a
*per-table random `maphash` seed*, and `NewHashTabFunc` takes the
function pair — which *must agree* (equal-comparing elements must
hash equal, or Search/Delete look in the wrong bucket). With the
default constructors, bucket order and `Dump` hashes are
nondeterministic across processes — never assert them. `Insert`
*replaces* an equal element and returns bool (added vs replaced);
`Search` returns `(T, bool)` (except `hash_tab_dll`, below); deletes
return bool. The bucket count is fixed for the life of the table
(n ≥ 5) — point unknown-size callers at `hash_grow`. Shared panic
contract, four panics: `NewHashTabFunc` with a nil function, `n < 5`,
and `Insert` on a nil or a zero-value table; nil and zero-value tables
tolerate every read.

=== Separate chaining — `hash_tab/`, `hash_tab_ts/`

Fixed-size table; each bucket is a singly linked chain of
self-contained nodes (data by value plus the raw hash for `Dump`) —
deliberately *not* a wrapper over `sll` (the chain never uses sll's
tail pointer or error API, and `Delete` splices the node out in one
walk with a prev pointer). `Insert` pushes at the chain head, so
`Walk`/`All`/`Values` visit bucket order and, within a bucket,
newest-first — documented, not asserted. `Dump` shows the raw hashes.
O(1) insert; O(n/k) average search/delete.

* Good: simple, cache-friendly-enough chaining; the baseline hash
table.
* Bad: fixed size — chains lengthen as the table fills (use
`hash_grow` or a bigger `n`); worst case O(n) all-in-one-bucket.

`hash_tab_ts` is the twin with one table lock, snapshot
`All`/`Values`, whole-traversal `Walk`/`Dump`, and the compound-op
surface (`Lock`/`Unlock` + `Nl*`).

=== Tree buckets — `hash_tab_bt/`, `hash_tab_bt_ts/`

The buckets are each a `*binary_tree.BinaryTree[T]` — an intra-pluto
composition (a bucket that is a search tree is exactly what
`binary_tree` is). Because the bucket is a tree, the element type needs
an *ordering*, not just equality: `NewHashTab[T interface{ cmp.Ordered; comparable }](n)`
(orders with `Compare[T]`, hashes with `maphash.Comparable`; the
`& comparable` intersection exists only because `maphash.Comparable`
demands it) or `NewHashTabFunc(cmp, hash, n)` with equality derived as
`cmp(a, b) == 0`. Lookups stay *O(log(n/k))* even under heavy
collisions instead of degrading linearly. `Walk`/`All`/`Values` visit
bucket order and, within a bucket, the tree's in-order (ascending) —
the opposite of `hash_tab`'s newest-first chains. `Dump` shows no hash
values (tree nodes keep none); `Walk` passes the *bucket index* as
pos.

* Good: graceful degradation under adversarial keys or too few
buckets; sorted-within-bucket iteration.
* Bad: worst case still O(n) — `binary_tree` is unbalanced, so sorted
inserts into one bucket degenerate; fixed bucket count; the
constructor constraint is the clunkiest in the library.

`hash_tab_bt_ts` keeps the *plain* `binary_tree` buckets and the one
table lock guarding everything — no per-bucket locks. Compound-op
surface included; `All`/`Values` copy value snapshots under the read
lock.

=== dll buckets, O(1) delete-by-handle — `hash_tab_dll/`, `hash_tab_dll_ts/`

The buckets are each a `*dll.Dll[T]` — the fourth intra-pluto
composition, and the counterpoint to `hash_tab`'s self-contained
chains: here the bucket _does_ use dll's `prev` pointers. The
differentiator in the family: `Search` returns a live
`(*dll.DllElement[T], bool)` *handle* — the one pointer-handle find
in the pluto hash tables — because the handle is what makes
`DeleteFound(el)` *O(1)* (hash `el.GetData()`, then the bucket
splice — no chain walk). Handles stay valid across an `Insert`
replacement (the replacement is `SetData` on the same node). Within a
bucket, iteration is dll head-to-tail = newest-first, like `hash_tab`.

* Good: O(1) delete of a previously located element — locate once,
delete many times; the handle survives replacement.
* Bad: the handle must be a live element of this table (a stale
handle is undefined, the same contract as `dll.DeleteFound`); under
concurrency a handle can go stale between `Search` and use — the
race-free form is `Lock` + `NlSearch` + `NlDeleteFound` + `Unlock`.

=== Open addressing with growth — `hash_grow/`, `hash_grow_ts/`

Open addressing with linear probing — the linear-probing member of the
self-sizing hash tables. The table doubles and rehashes when the load factor
exceeds the configurable saturation (default 0.5; `≤ 0` or NaN selects
the default), so it stays O(1) average as it grows. Delete uses
backward-shift to keep probe chains intact; an insert into a
completely full table (saturation ≥ 1.0) *forces growth* instead of
being silently dropped; probes stop after one full cycle. Empty
buckets are marked by a zero raw hash in
`originalHash` (a hash of exactly 0 is remapped to 1) — no nil
pointers. `Walk` is `func(pos int, data T) bool` with *false-to-stop*
(the tree convention) and no depth/userData; `All`/`Values`/`Dump`
round out iteration. `Truncate` clears both slices.

* Good: O(1) average that holds up as data grows; no per-element
pointer chasing; the hash table for unknown sizes.
* Bad: O(n) worst case; growth pauses for a full rehash; linear
probing is sensitive to clustering and hash quality; fixed `Dump`
hashes are nondeterministic under the default seed.

`hash_grow_ts` is the twin with value snapshots and the compound-op
surface.

=== Cuckoo hashing — `cuckoo/`, `cuckoo_ts/`

Cuckoo hashing — the second self-sizing hash table, and the one whose
lookups never probe. Each element is hashed once into a full 64-bit
base hash (the stdlib `hash/maphash` under a per-table random seed, or
a caller-supplied function), the full hash is stored beside the
element, and four candidate slots are derived from it by shifting and
masking: `h & mask`, `h>>1 & mask`, `h>>2 & mask`, `h>>3 & mask`.
Table sizes are therefore powers of two (the requested size rounds up,
minimum 256). Search and Delete examine exactly those four slots — O(1)
worst case for the lookup itself — and Delete is a slot clear with no
chain repair. An insert with all four candidates occupied displaces an
element (the cuckoo step) and re-places it in one of its own
candidates; a chain that exceeds the kick limit rolls back and forces
a doubling. The saturation is tracked by `Saturation()` with two
configurable thresholds: grow above 0.85 (default) after an insert,
shrink below 0.10 (default) after a delete, halving down to the
minimum size. An empty slot is an explicit flag, so a base hash of
exactly 0 is legal (no remap, unlike `hash_grow`). The package is
written to the same contract as `hash_grow`.

* Good: O(1) lookups with no probing and no clustering sensitivity;
  the stored 64-bit hash lets resizes re-derive every position without
  re-hashing; deletes are trivially cheap; the table shrinks again
  after deletions.
* Bad: inserts may displace chains (O(n) worst case); consecutive
  candidate hashes share bits, so adversarial hashes can force resizes
  below the threshold (the collision-loop path absorbs this); a hash
  function that maps several distinct elements to coinciding
  candidates at every size panics (documented pathological input).

`cuckoo_ts` is the twin with a difference in the resize machinery: a
collision-loop resize runs synchronously (the insert must place its
element before returning), but a threshold crossing starts a
*background goroutine* that takes the write lock on its own thread and
rebuilds the table — at most one per table, re-checking the thresholds
after each rebuild. Operations between trigger and rebuild run against
the still-valid (merely saturated) table. Plus the usual twin surface:
snapshot `All`/`Values`, real `Lock`/`Unlock`, and the `Nl*` methods
for compound operations.

=== Sharded for concurrency — `sharded_hash_ts/`

The striped hash table — one logical table sharded over a power-of-two
number of independently locked stripes, built for shared keyspaces (the
Ultima keyspace request). Each stripe is a *chained* table with a
power-of-two bucket array that doubles at a configurable load factor
(default 0.75); `Insert`/`Search`/`Delete` touch exactly one stripe, and
`Len` is a lock-free atomic — no global lock anywhere. The stripe
internals are deliberately not `hash_grow`/`cuckoo` open addressing: the
Redis SCAN guarantee (a full iteration returns everything present
throughout, at least once) is only provable when elements never change
buckets except by the deterministic v-or-v+size split of a doubling —
`hash_grow`'s backward-shift deletes and home-slot re-probing can strand
an unscanned element. Chains move nothing: insert pushes a node, delete
unlinks, growth re-links at `hash & newMask` (Redis's own `dict` split).
`Scan` walks all stripes with one cursor (stripe index in the high bits,
Redis reverse-binary bucket cursor in the low bits) holding at most one
stripe read lock, never across calls; `LockKey(key)` plus the `Nl*`
methods give atomic read-modify-write on one key's stripe (multi-key
clients must lock in stripe-index order). Replaces N independent tables
plus caller-side routing glue: ~12.5 ns/op read-heavy at 256 stripes
versus ~67 for single-lock `hash_grow_ts` on 14 cores, matching the
manual N-tables arrangement while giving it the one thing it lacks — a
single cursor space. No plain twin; striping exists only for concurrent
use.

== Union-Find — `union_find/`, `union_find_ts/`

Sedgwick's §1.5 disjoint set over the indices `0..n-1` — the one
non-generic structure in the library, because the elements *are* the
indices. Union-by-rank with path halving in `Find`, so `Union`/
`Find`/`Connected` are amortized O(α(n)) — effectively constant.
`Union` reports whether a merge happened (false when the pair was
already connected); out-of-range indices report `false`, never panic
(the `heap` indexed-operation convention). Panics only on
`NewUnionFind(n < 1)` and `Union` on a nil set. This is the building
block for Kruskal-style connectivity over a fixed universe.

* Good: near-constant amortized operations; tiny API; no comparison
or equality function to supply.
* Bad: the universe `0..n-1` is fixed at construction; sets cannot be
split back apart.

`union_find_ts` is the twin with the RWMutex — but `Find`/`Connected`
take the *write* lock, not the read lock, because path halving mutates
the parent pointers; only `Count`/`Len` are true reads.

== Graphs — `graph/`, `graph_ts/`

Sedgwick's §4.1–4.2 undirected graph on the int vertices `0..n-1`
(adjacency lists; self-loops and parallel edges allowed — a self-loop
counts once in `E`, twice in `Degree`), plus the three fundamental
queries as constructor-style result objects in the same package:
`NewDFSPaths(g, s)` and `NewBFSPaths(g, s)` (`HasPathTo`, `PathTo` —
a source-first slice; BFS adds `DistTo`, the shortest distance in
unweighted edges) and `NewCC(g)` (`Connected`, `ID`, `Count`).
`AddEdge` O(1); the traversals O(V+E) time and O(V) space. Result
objects are immutable snapshots of the graph at call time — later
`AddEdge` calls are not reflected — and there is no `RemoveEdge`
(deliberate, matching Sedgwick's Graph). BFS uses `pluto/queue`
internally (an intra-pluto composition).

* Good: the classic graph traversals with pluto's value semantics and
panic contracts; BFS shortest paths and connected components out of
the box.
* Bad: undirected only — the directed sibling is `digraph`; int
vertices — a symbol layer is a possible later package; no edge
removal.

`graph_ts` is the twin with the RWMutex: `Adj` yields a snapshot slice
copied under the read lock, and the traversal constructors deep-copy
the adjacency under the read lock, then run *lock-free* on the
snapshot — no lock is held for the duration of a traversal.

== Directed Graphs — `digraph/`, `digraph_ts/`

Sedgwick's §4.4–4.6 directed graph on the int vertices `0..n-1` — the
directed sibling of `graph`, with the same adjacency-list shape
(self-loops and parallel edges allowed; no `RemoveEdge`) plus a
maintained in-degree array so `InDegree` is O(1) alongside
`OutDegree`. `Reverse()` flips every edge (Kosaraju's building block).
The §4.4–4.6 queries are constructor-style immutable result objects in
the same package: `NewDirectedDFS(g, sources...)` (multi-source
reachability — `Marked`, `Count`), `NewDFSDirectedPaths` /
`NewBFSDirectedPaths(g, s)` (`HasPathTo`, source-first `PathTo`; BFS
adds `DistTo` — `pluto/queue` internally, like `graph`),
`NewDirectedCycle(g)` (`HasCycle`, `Cycle` — on-stack DFS marking),
`NewDepthFirstOrder(g)` (`Pre`, `Post`, `ReversePost`),
`NewTopological(g)` (`HasOrder`, `Order` — cycle check plus reverse
postorder) and `NewKosarajuSCC(g)` (`StronglyConnected`, `ID`,
`Count`). All traversals O(V+E). Sourced constructors panic on a
nil/empty graph or out-of-range source; the source-less queries
(`DirectedCycle`, `DepthFirstOrder`, `Topological`, `KosarajuSCC`)
tolerate empty graphs — an empty digraph has a sane answer, the
`NewCC` precedent.

* Good: the full §4.4–4.6 toolkit — reachability, paths, cycle
detection, topological sort and strong components — with pluto's panic
contracts and immutable result objects; verified against the algs4
tinyDG/tinyDAG datasets.
* Bad: int vertices (a symbol layer is a possible later package); no
edge removal; edge-weighted directed graphs live in `dijkstra`.

`digraph_ts` is the twin with the RWMutex: `Adj` yields a snapshot
slice copied under the read lock, and every query constructor
deep-copies the adjacency under the read lock, then runs *lock-free*
on the snapshot — no lock is held for the duration of a traversal.

== Dijkstra Shortest Paths — `dijkstra/`, `dijkstra_ts/`

Sedgwick's §4.4 shortest paths on edge-weighted graphs: an
`EdgeWeightedDigraph` (directed) and `EdgeWeightedGraph` (undirected)
on the int vertices `0..n-1`, with the constructor-style query objects
`NewDijkstraSP(g, s)` (`DistTo` — `+Inf` when unreachable, `HasPathTo`,
`PathTo` — a source-first edge slice whose weights sum to the
distance), its undirected twin `NewDijkstraUndirectedSP`, and
`NewDijkstraAllPairsSP` (one search per source; `Dist`/`HasPath`/
`Path`). The priority queue is `pluto/index_pq` (an intra-pluto
composition — Dijkstra's decrease-key is exactly `index_pq.Change`);
single-source is O(E log V), all-pairs O(V·E log V). All weights must
be non-negative — a negative edge panics at construction, as do a nil
or empty graph and an out-of-range source. Result objects are
immutable snapshots of the graph at call time; self-loops and parallel
edges are allowed; no `RemoveEdge` (deliberate, matching Sedgwick).

* Good: the classic algorithm with pluto's panic contracts and value
semantics; single-source, undirected and all-pairs out of the box, all
verified bit-for-bit against the algs4 Java reference.
* Bad: non-negative weights only — negative weights are
`bellman_ford`'s job; int vertices — a symbol layer is a possible
later package; no edge removal.

`dijkstra_ts` is the twin with the RWMutex: `Adj` returns a snapshot
slice copied under the read lock, and the Dijkstra constructors
deep-copy the adjacency under the read lock, then run *lock-free* on
the snapshot — no lock is held for the duration of a search. The query
objects are immutable, so they are safe for concurrent reads.

== Minimum Spanning Trees — `mst/`, `mst_ts/`

Sedgwick's §4.7–4.8 minimum spanning trees over `dijkstra`'s
`EdgeWeightedGraph` — three algorithms, each a constructor-style
immutable result object with the same surface (`Edges` — the tree
edges, `Weight` — their sum, `Len`): `NewLazyPrimMST` (crossing edges
in `pluto/priority_queue`, stale edges discarded on pop),
`NewPrimMST` (eager — `pluto/index_pq`, decrease-key via `Change`),
and `NewKruskalMST` (edges sorted with `slices.SortFunc`, cycle check
via `pluto/union_find`) — three intra-pluto compositions on one graph
type. Eager Prim is O(E log V), lazy Prim O(E log E), Kruskal
O(E log E). Any edge weights are legal (negative edges are no problem
for MSTs — only the Dijkstra constructors reject them); a disconnected
graph yields the minimum spanning *forest* (fewer than V-1 edges).
Constructors panic on a nil or empty graph; verified edge-for-edge
against the algs4 tinyEWG dataset (weight 1.81) and cross-checked
against each other plus an in-test brute-force reference at fixed
seed.

* Good: pick the algorithm that fits — eager Prim for dense graphs,
lazy Prim for code clarity, Kruskal when edges come pre-sorted; all
three agree, tested so.
* Bad: undirected only (an MST is inherently undirected); the graph
type is borrowed from `dijkstra` — no weighted-graph container of its
own.

`mst_ts` is the twin whose constructors take
`*dijkstra_ts.EdgeWeightedGraph`: each per-vertex `Adj` call already
returns a snapshot copied under the graph's read lock, so the
algorithms run lock-free on a consistent-per-vertex view (not an
atomic whole-graph snapshot — `dijkstra_ts` exports none) and the
result objects are immutable.

== Bellman-Ford & DAG Shortest Paths — `bellman_ford/`, `bellman_ford_ts/`

Sedgwick's §4.10–4.11 shortest paths where `dijkstra` cannot go:
negative edge weights. `NewBellmanFordSP(g, s)` over `dijkstra`'s
`EdgeWeightedDigraph` is the queue-based Bellman-Ford (FIFO of
vertices whose `distTo` decreased — `pluto/queue` internally; relax
rounds counted, a full round with no improvement ends it, and every
V-th round scans the `edgeTo` subgraph for a negative cycle).
`DistTo` (`+Inf` when unreachable), `HasPathTo`, source-first `PathTo`
whose weights sum to `DistTo`, `HasNegativeCycle` and `NegativeCycle`
(the cycle in cycle order). Following algs4, when a negative cycle is
reachable from the source, `DistTo`/`PathTo` panic naming the method —
the distances are undefined; `HasNegativeCycle`/`NegativeCycle` are
the way to inspect that case. Also in the package, §4.10:
`NewAcyclicSP` / `NewAcyclicLP` (g, s) — shortest and longest paths in
an edge-weighted DAG by topological-order relaxation, O(E+V), with an
internal topological sort (self-contained; no import of `digraph`);
both panic if the digraph has a cycle. `AcyclicLP` reports `-Inf` for
unreachable. Verified against tinyEWD/tinyEWDn/tinyEWDAG from algs4
and cross-checked against `dijkstra` on non-negative graphs and a
naive relax-everything reference at fixed seeds.

* Good: the general single-source shortest path — negative edges,
negative-cycle detection with a witness cycle, plus the linear-time
DAG special cases (CPM-style critical paths included).
* Bad: O(V·E) worst case — use `dijkstra` when weights are
non-negative and `AcyclicSP` when the digraph is a DAG.

`bellman_ford_ts` is the twin whose constructors take
`*dijkstra_ts.EdgeWeightedDigraph`, snapshot the adjacency per vertex
under the read lock (same atomicity caveat as `mst_ts`), then compute
lock-free; the result objects are immutable.

== R-way Tries — `trie/`, `trie_ts/`

Sedgwick's §5.4 `TrieST`: a string-keyed symbol table generic over the
value (`Trie[T any]`) built on a byte-oriented R-way trie (R = 256, so
arbitrary UTF-8 strings work as keys transparently — including the
empty string, which lives at the root). No comparison function and no
constructors — the ordering is inherent in the key bytes, so the zero
value is fully usable; the single panic is `Insert` on a nil `*Trie`.
`Insert` replaces duplicates (returns added-vs-replaced); `Delete`
prunes childless value-less nodes on the way back up. Beyond the
symbol-table basics (`Search`/`Contains`/`IsEmpty`/`Length`) it
supports the trie specialties: `LongestPrefixOf`, `KeysWithPrefix`,
`KeysThatMatch` (`.` matches any one byte), and `All` — an ascending
`iter.Seq2[string, T]` over the live trie. `Insert`/`Search`/`Delete`
are O(L) for a key of length L.

* Good: search hits in time proportional to the key, not the table;
prefix and wildcard queries no hash table can answer; ascending key
iteration for free.
* Bad: memory — every node carries a `[256]` children array (2 KiB of
pointers), so wide shallow key sets waste space; `tst` is the
memory-efficient alternative.

`trie_ts` is the twin with the RWMutex: identical API, eager
value-snapshot `All`/`KeysWithPrefix`/`KeysThatMatch` taken under the
read lock (safe to mutate from inside the loop), and the real
`Lock`/`Unlock` plus `Nl*` methods for atomic search-then-update.

== Ternary Search Tries — `tst/`, `tst_ts/`

Sedgwick's §5.5 `TST`: the same string-keyed symbol-table surface as
`trie` (`Tst[T any]` — `Insert`/`Search`/`Contains`/`Delete`/
`IsEmpty`/`Length`/`LongestPrefixOf`/`KeysWithPrefix`/
`KeysThatMatch`/`All`), but each node holds one byte and three
pointers (left/mid/right) instead of a 256-way array — one small node
per character, so it is the memory-efficient counterpart to `trie`.
The empty key is rejected (`Insert("")` returns false; algs4 throws).
`Delete` clears the value and prunes childless value-less branches
(algs4's TST has no delete; pluto's trees all do). Search/Insert are
O(L + ln n) on average. Same contract as `trie`: no constructors,
zero value usable, single panic (`Insert` on a nil `*Tst`).

* Good: a fraction of `trie`'s memory; the full prefix/wildcard query
set; ascending `All`.
* Bad: misses cost a compare-and-branch per character instead of one
array index — slower than `trie` on search-heavy workloads with cheap
memory.

`tst_ts` is the twin with the RWMutex, snapshot iterators, and the
real `Lock`/`Unlock` plus `Nl*` methods, mirroring `trie_ts`.

== Patricia Tries — `patricia_trie/`, `patricia_trie_ts/`

Sedgwick's radix-searching chapter in the crit-bit formulation:
`PatriciaTrie[T any]` stores keys only at the leaves and one internal
node per actual branching point (a critical bit index plus two
children) — no unary internal nodes, so n keys cost n leaves + n−1
internal nodes (96 bytes/key measured) and every operation is O(w) in
the key length in bits, independent of n. Keys go through an
order-preserving prefix-free encoding (marker bit + 8 data bits per
byte, a 0 terminator), so `""` and `"\x00"` never collide and `All` is
plain ascending byte order. Constructor-free like `trie`/`tst` (zero
value usable, single nil-`Insert` panic) and binary-safe (any byte
value legal). Beyond the basics: `KeysWithPrefix`,
`LongestPrefixOf(key) (string, T, bool)` (longest stored key that is a
prefix of the query — the routing-table lookup), `KeysThatMatch` (a
Redis-style glob with the exact `stringmatchlen` semantics behind the
KEYS command: `*`, `?`, `[abc]`, `[a-z]`, `[^...]`, `\x` escaping —
not the `.`-wildcard of `trie`/`tst`), and ascending/descending
`All`/`Backward` over the live trie. On 1M random 16-byte keys it
builds in ~479 ns/key (96 B/key) and searches in ~234 ns — faster than
`tst` at a seventh of the memory, and where the R-way `trie` would
need ~30 GiB (see the package README's comparison table).

* Good: the smallest footprint and fastest searches of the string
tables; prefix + Redis-glob queries; O(w) everything.
* Bad: bitwise descent touches every bit of the key (no byte skips);
no wildcard pruning beyond the pattern's literal prefix.

`patricia_trie_ts` is the twin with the RWMutex: identical API, eager
snapshot `All`/`Backward`/`KeysThatMatch` taken under the read lock
(safe to mutate from inside the loop), `KeysWithPrefix` an eager slice
by construction, `Dump` holding the read lock for the whole traversal,
and the real `Lock`/`Unlock` plus `Nl*` methods, mirroring
`trie_ts`/`tst_ts`.

== Suffix Arrays — `suffix_array/`

Sedgwick's §6.3 `SuffixArray`: the sorted order of a string's
suffixes, with the LCP (longest common prefix) table alongside —
non-generic over `string`, like `union_find`. `NewSuffixArray(s)`
builds the array by prefix doubling (sort by rank pairs, doubling the
lookahead — O(n log² n), simple and deterministic) and the LCP table
with Kasai's algorithm (O(n)). Queries are all O(1): `Index` (text
offset of the i-th sorted suffix), `Select` (the suffix itself),
`LCP`, `Rank` (the inverse of `Index`), plus `Len` and
`LongestRepeatedSubstring` (the algs4 LRS client folded in as a
method, O(n)). Out-of-range indices report `false`, never panic — the
package has no panics at all.

* Good: O(1) positional access to the sorted suffixes and their LCPs;
the base for substring/repeat analyses (binary search over `Select`
answers substring membership in O(m log n)).
* Bad: construction cost and three n-word tables; static text only —
a new string is a new `SuffixArray`.

The structure is *immutable after construction*, so concurrent reads
are safe as-is and there is no `suffix_array_ts` twin (the `queue_dll`
precedent — documented in the package doc and README).

== Fenwick & Segment Trees — `fenwick_tree/`, `segment_tree/` (+ `_ts` twins)

The two classic range-query structures from Sedgwick's "Beyond"
section, generic over `g_lib.Numeric` (the `~int|~float64|...` union —
defined numeric types pass). `FenwickTree[T]` (binary indexed tree,
internal 1-based array over the indices `0..n-1`) answers prefix sums:
`Add(i, delta)` point updates and `Sum(i)`/`RangeSum(lo, hi)` queries
in O(log n), plus `Value` (prefix-difference reconstruction) and `Set`
(via computed delta); `NewFenwickTree(n)` or `NewFenwickTreeFrom(data)`
(O(n) build). `SegmentTree[T]` is the general form: array-backed
(2·next-pow-2, identity-padded leaves), `NewSegmentTree(data)` for
range sums and `NewSegmentTreeFunc(data, combine, identity)` for any
associative op — min/max/gcd — with `Query(lo, hi)` and point-assign
`Update(i, v)` in O(log n) and `Value` in O(1). Both follow the `heap`
indexed-operation convention: out-of-range indices report
`false`/zero, never panic; panics only on `n < 1`/empty data, a nil
`combine`, and writes on a nil tree.

* Good: O(log n) range queries with tiny constants; Fenwick is ~1/3
the memory of the segment tree for the sum case, the segment tree
covers any associative combine.
* Bad: both are point-update structures — no range-update/lazy
propagation (yet); the index space is fixed at construction.

The `_ts` twins add the RWMutex: reads under the read lock, writes
under the write lock, nil guards before lock acquisition, and the real
`Lock`/`Unlock` plus `Nl*` methods (`NlSum`/`NlRangeSum`/`NlAdd`... /
`NlQuery`/`NlUpdate`) for atomic read-modify-write compounds.

== Quicksort — `quick_sort/`

Sedgwick's §2.3 3-way quicksort (Dijkstra Dutch-national-flag
partitioning, algs4 `Quick3way`) as stateless in-place slice sorts:
`quick_sort.Sort[T cmp.Ordered](data)` and
`quick_sort.SortFunc[T any](data, cmp)` — not stable. Because a
library cannot pre-shuffle like the textbook client, robustness comes
from a median-of-3 pivot, an insertion-sort cutoff at ≤ 12 elements,
and recurse-smaller-side/loop-larger-side (O(log n) stack); the
three-way partition makes all-equal-key input O(n). The single panic
is `SortFunc` with a nil comparison function. Stateless functions —
safe for concurrent use on disjoint slices; no `_ts` twin.

* Good: O(n log₂ n) average with small constants; excels on
duplicate-heavy keys where two-way quicksort goes quadratic.
* Bad: not stable; O(n²) worst case remains possible in principle.

== Substring Search — `substring/`

Sedgwick's §5.3 substring search as three constructor-style,
compile-once/search-many query objects over byte strings: `NewKMP`
(DFA simulation, guaranteed O(n+m)), `NewBoyerMoore` (bad-character
rule only, like algs4 — sublinear in practice, O(n·m) worst), and
`NewRabinKarp` (rolling hash; the deterministic Las Vegas variant with
a fixed prime and byte-for-byte verification on every hash hit —
algs4's published Monte Carlo version is nondeterministic and never
verifies). `Search(text)` returns the leftmost index or -1 (the
`strings.Index` convention — algs4 returns n on a miss); the empty
pattern returns 0. No panics anywhere; nil receivers report -1.
Immutable after construction — concurrent searches are safe, no `_ts`
twin (the `suffix_array` precedent).

* Good: KMP never re-examines a text character (stream-safe);
Boyer-Moore skips ahead on ordinary text.
* Bad: KMP's DFA costs 256·m ints per pattern; Boyer-Moore without
the good-suffix rule has a quadratic worst case.

== LZW Compression — `lzw/`

LZW compress/expand over byte slices (Sedgwick §5.5, widening-code
variant): `Compress(data []byte) []byte` and
`Expand(compressed []byte) []byte`. The encode table is a
`pluto/tst.Tst[int]` (intra-pluto composition); the bit format packs
codewords MSB-first, starting 9 bits wide and widening to 16 as the
codebook grows toward 65536 entries (256 = EOF sentinel). `Expand`
returns nil on malformed input — the package has no panics. Stateless
functions; safe for concurrent use; no `_ts` twin. Note the format is
NOT wire-compatible with the stock algs4 `LZW.java`, which uses fixed
12-bit codes — the widening variant handles arbitrarily large inputs
without table exhaustion.

* Good: O(n) expected; adapts to the data; no entropy model needed.
* Bad: the table never resets, so compression degrades on very long
inputs once the 65536-entry codebook fills; fixed-width algs4 streams
cannot be exchanged.

== Max Flow — `maxflow/`

Sedgwick's §6.4 max-flow / min-cut: a `FlowNetwork` container
(vertices `0..n-1`, `AddEdge(from, to, capacity)` with float64
capacities — integer capacities stay exact under float64 summation)
plus the constructor-style immutable query object
`NewFordFulkerson(g, s, t)` — Ford-Fulkerson with Edmonds-Karp BFS
shortest augmenting paths on `pluto/queue` (O(V·E²) worst case). The
constructor computes on a private deep copy (the caller's network is
never mutated) and the result is immutable: `Value()`, `InMinCut(v)`,
`S()`/`T()`, `Edges()`. Panics name the constructor/method: `v < 1`,
negative/NaN capacity, nil/empty network, out-of-range or equal s/t.
No `_ts` twin — results are immutable (the `suffix_array` precedent);
the network container itself is not thread-safe.

* Good: min-cut certificate comes for free (`InMinCut`); exact
arithmetic on integer capacities.
* Bad: Edmonds-Karp is the simple heuristic — no scaling or
push-relabel; float capacities make the result
data-dependent-terminating.

== Supporting Packages

* `g_lib/` — the one non-structure package: pure generic utility

`MinArray`/`MaxArray`, `Abs`/`Pow`, `IfTrue` (ternary selector),
`Ptr` (pointer to a copy — the Go 1.26 `new(expr)` form), slice
helpers (`InArray`, `LocationInArray`, `RemoveAt`, `Remove` via
`reflect.DeepEqual`, `RemoveComparable`, `Unique`, `EqualSlice`,
`SortSlice`), map helpers (`ToBoolMap` set conversion,

numeric constraint interfaces (`Numeric`, `SignedInteger`,
`SignedNumeric`, `Unsigned` — all `~T`; `Number` — exact types

live here; they are not library code.
* There are no interface-constraint support packages — pure generics
provide ordering and equality, and no interface indirection is needed
to swap a `_ts` twin (it is a package-name change).
