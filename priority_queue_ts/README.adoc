= priority_queue_ts

A generic *priority queue* that is *safe for concurrent use* — the
thread-safe twin of link:../priority_queue/[charon/priority_queue],
composing the thread-safe heap in link:../heap_ts/[`heap_ts`].  The
lowest-priority (minimum) element is always the next to come out; a
reversed comparison function (`NewPriorityQueueFunc`) makes the highest
priority come out first.

Like `priority_queue` it follows the same conventions (no interface
constraint, elements stored and returned by value, false returns
instead of nil pointers and errors), plus the additions this twin
needs: the real `Lock`/`Unlock` pair and the `Nl*` (no-lock) methods
for compound operations.

* Elements are stored and returned *by value* (`T`, not `*T`) — the
copies are taken under the heap's lock, so nothing aliases the
queue's internals.
* Queues of types comparable with `==`-style ordering (numbers, strings)
need no comparison function: `priority_queue_ts.NewPriorityQueue[int]()`.
* Any other type — or ordering by a priority field — takes a plain
comparison function, with no interface to implement.

The public API is identical to `priority_queue` (plus the locking
behavior below), so switching between the two is a package-name change.

== Locking behavior

* Every operation delegates to the guarded methods of the underlying
`heap_ts.Heap`: *reads* (`Peek`, `Search`, `Len`, `Length`,
`IsEmpty`) run under the read lock and in parallel with each other;
*writes* (`Insert`, `Pop`, `Delete`, `UpdatePriority`, `Truncate`)
are exclusive.
* *`All` operates on a snapshot* taken when it is called — copied out
under the heap's write lock, then drained privately in priority order
(minimum first, non-destructive).  It is safe to mutate the queue while
iterating — including from inside the loop — and an iterator never
observes modifications made after it was created.
* *Positions returned by `Search` may be invalidated by any concurrent
mutation* between obtaining the position and using it with
`UpdatePriority`/`Delete` (both report `false` for a now-stale
position).  For atomic search-then-update sequences use `Lock`/`Unlock`
with the `Nl*` methods: `NlLen`, `NlIsEmpty`, `NlPeek`, `NlInsert`,
`NlPop`, `NlSearch`, `NlUpdatePriority`, `NlDelete` — each returning
values exactly like its locked counterpart (`NlSearch` uses the
queue's own comparison function).  Calling a
regular method while the lock is held will deadlock.

[source,go]
----
pq.Lock()
// Atomic: find the priority-20 element and demote it below the minimum.
if v, pos, found := pq.NlSearch(Task{Priority: 20}); found {
    pq.NlUpdatePriority(pos, Task{Priority: v.Priority - 100, Name: v.Name})
}
pq.Unlock()
----

== Errors and panics

Identical to `priority_queue`: no errors — every empty or out-of-range
outcome is a `false` return — and exactly three panics:

[options="header"]
|===
| Call                               | Why

| `NewPriorityQueueFunc(nil)`        | nil comparison function, caught at construction time
| `Insert` on a nil `*PriorityQueue` | a nil queue cannot store an element
| `Insert` on a zero-value queue     | no underlying heap; the message names the constructors
|===

Everything else tolerates a nil queue and the zero value as an empty
queue.

== Usage

[source,go]
----
package main

import (
    "fmt"
    "sync"

    "github.com/pschlump/charon/priority_queue_ts"
)

func main() {
    pq := priority_queue_ts.NewPriorityQueue[int]()

    // Writers from many goroutines share one queue.
    var wg sync.WaitGroup
    for p := 0; p < 8; p++ {
        wg.Add(1)
        go func(p int) {
            defer wg.Done()
            for i := 0; i < 100; i++ {
                pq.Insert(p*1000 + i)
            }
        }(p)
    }
    wg.Wait()
    fmt.Println(pq.Len()) // 800

    // Concurrent pops drain it in ascending order overall.
    for !pq.IsEmpty() {
        if _, found := pq.Pop(); !found {
            break
        }
    }
    fmt.Println(pq.IsEmpty()) // true
}
----
