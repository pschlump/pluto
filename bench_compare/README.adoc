= bench_compare

Benchmarks `charon/binary_tree` against `pluto/binary_tree` on identical
workloads to measure the cost of the interface boxing/unboxing that charon
removed.

This is a *nested module* (it has its own `go.mod`) so that the root
charon module stays dependency-free.  Both libraries are pulled in from
the local checkouts with `replace` directives — nothing is fetched from
the network.  `../pluto` must exist relative to the charon checkout.

== What is compared

Three trees run the same workloads (same keys, same deterministic shuffled
order):

[options="header"]
|===
| Variant           | Tree                                                               | What it measures

| `pluto-interface` | `pluto/binary_tree`, element implements `comparable.Comparable`    | Every comparison boxes the argument into an interface (a heap allocation per comparison), dispatches through the interface, and unboxes with a type assertion.  Elements stored and passed as `*T`.
| `charon-func`     | `charon/binary_tree`, same struct shape, plain comparison function | Apples-to-apples with pluto: no interface, no boxing, no assertion; elements by value.
| `charon-ordered`  | `charon/binary_tree`, plain `string` keys, built-in `<`/`>`        | No wrapper struct at all — a shape pluto cannot express, since a bare string cannot implement `Comparable`.
|===

Workloads: `Insert` (build tree), `Search` (n successful searches),
`Delete` (delete all), `Iterate` (full in-order `All()` traversal), each
at n=1000 and n=10000.

== Running

From this directory:

----
go test -run '^$' -bench . -benchmem
----

or

----
make bench
----

`Insert`/`Delete` report ns/op for the whole n-element workload; `Search`
reports ns/op for n searches.  Compare the ratio between variants within
the same workload — the absolute numbers are machine dependent.

For statistically robust results:

----
go test -run '^$' -bench . -benchmem -count=10 > bench.txt
benchstat bench.txt
----

== Reading the results

* `ns/op`: the interface dispatch shows up in every workload that orders
elements (`Insert`, `Search`, `Delete`); `charon` variants should be
clearly faster at equal n.
* `B/op` and `allocs/op`: the boxing is visible here most directly.  The
pluto element is a struct containing a string, so converting it to
`comparable.Comparable` cannot use the interface data word and
allocates on the heap on *every comparison* — expect pluto's
ordering workloads to show roughly one allocation per comparison, and
charon's to show none beyond the tree nodes themselves.
* `Iterate` involves no comparisons; it isolates pointer-chasing and
`*T` yields (pluto) versus value yields (charon).
