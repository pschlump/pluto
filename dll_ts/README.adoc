= dll_ts

A generic doubly linked list with head and tail pointers that is *safe
for concurrent use* — the thread-safe twin of
link:../dll/[pluto/dll].  Every operation is guarded by a `sync.RWMutex`:
readers run in parallel with each other, writers are exclusive.  Like
`dll`, it works as a stack (`Push`/`Pop`/`Peak` at the head), a queue
(`Enqueue` at the tail, `Pop` from the head), and a positional list with
O(1) removal of previously found elements.

* Elements are stored and returned *by value* (`T`, not `*T`).
* Lists of types comparable with `==` need no equality function:
`dll_ts.NewDll[int]()`.
* Any other type — or equality by a single field — takes a plain equality
function, with no interface to implement:
`dll_ts.NewDllFunc(func(a, b Item) bool { return a.ID == b.ID })`.

The public API is identical to `dll` (plus the locking behavior below),
so switching between the two is a package-name change.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.  The link:../dll/[dll README] documents the full API usage;
it applies unchanged.

== Locking behavior

* *Reads* (`Search`, `ReverseSearch`, `Index`, `IndexFromTail`, `Peek`,
`PeekTail`, `Len`, `Length`, `IsEmpty`) take the read lock and release
it before returning — they can run in parallel with each other.
* *Writes* (`InsertBeforeHead`, `Push`, `AppendAtTail`, `Enqueue`,
`Pop`, `PopTail`, `Delete`, `DeleteSearch`, `DeleteFound`,
`DeleteAtHead`, `DeleteAtTail`, `Reverse`, `Truncate`, `Trim`,
`TrimTail`) take the write lock.  *`Delete` holds the write lock
across its search*, so search-and-delete is atomic.
* *`Walk`/`ReverseWalk` hold the read lock while the callback runs.*
The callback must *not* call methods on the same list — a write from
a callback deadlocks on the lock, and even a read can deadlock if a
writer is waiting.  To visit elements while mutating, iterate a
snapshot with `All()` instead.
* *`All`/`Backward`/`IterateOver` operate on a snapshot* taken when
they are called (one O(n) copy, under the read lock).  It is safe to
mutate the list while iterating — including from inside the loop — and
an iterator never observes modifications made after it was created.
* *The legacy `DllIter` (Front/Rear/Current) walks the live list*: each
iterator method takes the list's read lock for the duration of that
call only (plus the iterator's own mutex, so one iterator may be shared
between goroutines).  This is race-free, but the iterator observes
concurrent modifications as they happen and terminates early if its
current element is deleted.  Prefer `All`/`Backward` for a stable view.
* *`Concat` snapshots the source under the source's own read lock*
before taking the destination's write lock — no two locks are ever held
at once, so the source may safely alias the destination.
* *`MarshalJSON` snapshots under the read lock and encodes without it*
(the `All`/`Backward` snapshot convention), so it is safe concurrently
with any list operation — and an element type with its own
`MarshalJSON` may safely call back into the list.
* *`UnmarshalJSON` decodes before taking the write lock* — element-level
unmarshalers must not run under the list lock — and then replaces the
contents under one hold of the write lock.
* *`Lock`/`Unlock` expose the write lock* for compound operations that
must be atomic (unlike the no-op pair in the plain `dll` package).  No
other list operation may run while the lock is held; inside the locked
region use the operation results you already hold, not the public
methods.
* *`Dump` holds the read lock for the whole dump*, so the writer must
not call methods on the same list.
* *`GetData()`/`SetData()` on a `DllElement` handle take no lock*: the
handle is a live node, so calling `SetData` on an element inside a
concurrently used list is a race (it is intended for standalone
elements).  `DllElement.Data` itself is an unexported `T`.

[source,go]
----
for _, v := range list.All() {
    list.Delete(v) // safe: All iterates a snapshot
}
----

== Errors and panics

Identical to `dll`.  Empty-list, not-found and out-of-range conditions
are errors (`ErrEmptyDll`, `ErrNotFound`, `ErrOutOfRange`,
`ErrInternalDll`; compare with `errors.Is`), and the package panics in
exactly three situations, all programmer errors:

[options="header"]
|===
| Call                               | Why

| `NewDllFunc(nil)`                  | nil equality function, caught at construction time
| Insert-family on a nil `*Dll`      | a nil list cannot store an element
| Insert-family on a zero-value list | no equality function; the message names the constructors
|===

The insert family is `InsertBeforeHead`, `Push`, `AppendAtTail`,
`Enqueue`, `Concat` (only when the source has elements), and
`UnmarshalJSON` (when the data holds elements).  Everything
else tolerates a nil list and the zero value as an empty list.

The JSON support (`MarshalJSON`/`UnmarshalJSON`) is otherwise identical
to dll's — the list encodes as a JSON array of its elements, head to
tail — see the JSON section of the
link:../dll/[dll README]; only the locking differs, as described above.

== Usage

[source,go]
----
package main

import (
    "fmt"
    "sync"

    "github.com/pschlump/pluto/dll_ts"
)

func main() {
    queue := dll_ts.NewDll[int]()

    // Writers from many goroutines share one queue.
    var wg sync.WaitGroup
    for w := 0; w < 8; w++ {
        wg.Add(1)
        go func(w int) {
            defer wg.Done()
            for i := 0; i < 100; i++ {
                queue.Enqueue(w*1000 + i)
            }
        }(w)
    }
    wg.Wait()
    fmt.Println(queue.Len()) // 800

    // Deleting from inside an All loop is safe: it iterates a snapshot.
    for _, v := range queue.All() {
        queue.Delete(v)
    }
    fmt.Println(queue.IsEmpty()) // true
}
----
