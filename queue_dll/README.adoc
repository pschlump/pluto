= queue_dll

A generic *FIFO (first-in, first-out) queue* built on a doubly linked
list that is *not safe for concurrent use*.  There is no `queue_dll_ts`
twin — for a shared FIFO on the same list structure use
link:../dqueue_ts/[`dqueue_ts`]'s `PushBack`/`PopFront`.

The element type needs *no constraints at all* — `T` is `any`, so
elements are never boxed into an interface — and the zero value of
`Queue` is an empty queue ready to use without a constructor.  Elements
are stored and returned *by value* (`Dequeue` and `Peek` return
`(T, error)`).

== Why self-contained?

Pluto's `dll` requires an equality function at
construction (its `Search` needs one), but a queue never compares
elements — so wrapping would force a dummy equality function and break
the constraint-free contract.  Like link:../dqueue/[`dqueue`] (and
`stack_sll_ts`) this package is self-contained, with its own plain
doubly linked list underneath; the `prev` pointers are what make
`Backward` O(1) per step.

The practical difference from the slice-based link:../queue/[`queue`]
is the same as link:../stack_sll_ts/[`stack_sll_ts`] vs
link:../stack/[`stack`]: *memory behavior*.  `Pop` and `Dequeue` are
strictly O(1) with no reallocation — pushes and dequeues allocate and
free one small node each, so memory use is stable across arbitrary
push/pop patterns (a slice window periodically reallocates as it
walks).  Trade-off: one allocation per push.  Need to insert and remove
at the head too?  That is a deque — link:../dqueue/[`dqueue`] is this
list with both ends exposed.

== Operations

[options="header"]
|===
| Operation                    | Description                                  | Complexity

| `Push` / `Enqueue`           | Insert at the tail (aliases)                 | O(1)
| `Pop`                        | Remove the head element, discarding it       | O(1)
| `Dequeue`                    | Remove and return the head element           | O(1)
| `Peek`                       | Look at the head without removing it         | O(1)
| `IsEmpty` / `Len` / `Length` | Size queries                                 | O(1)
| `Truncate`                   | Remove all elements                          | O(1)
| `All` / `Backward`           | Range-over-func iterators over the live list | O(n)
| `Slice`                      | Fresh `[]T`, FIFO order (head first)         | O(n)
| `String` / `StringFunc`      | Render the elements: `[a b c]`               | O(n)
| `Equal`                      | Same sequence (ORDER-SENSITIVE)              | O(n)
| `Clone`                      | Deep copy                                    | O(n)
|===

`All` iterates from the *head* (index 0, next to be dequeued) to the
tail; `Backward` from the tail to the head, with indexes counting down
from `Length()-1` so they match the index `All` assigns to the same
element.  `Len` is an alias for `Length`, matching the other pluto
packages.

== Iterators walk the live list

`All` and `Backward` do *not* copy a snapshot: `All` follows the `next`
pointers from the head, `Backward` the `prev` pointers from the tail —
both cost O(n) time with *O(1) extra space*.  The price is the usual
one for a plain package:

[source,go]
----
for _, v := range q.All() {
    // q.Dequeue() here would be a bug: the queue must not be
    // modified while an iterator is running.
    _ = v
}
----

== Set-convenience capabilities

Sequences get the minimal menu only — `Slice`, `String`/`StringFunc`,
`Equal` and `Clone`, in link:capabilities.go[`capabilities.go`].
Sequences are not sets, so there is deliberately no `Contains`, no batch
insert/delete and no predicate bulk delete: an O(n) membership scan over
a sequence would be a footgun.

[source,go]
----
q.Push(1)
q.Push(2)

fmt.Println(q.String())   // [1 2]
fmt.Println(q.Slice())    // [1 2]
dup := q.Clone()
fmt.Println(q.Equal(dup)) // true
----

`Equal` is the one *order-sensitive* `Equal` in pluto — `[1 2]` is not
equal to `[2 1]`; every set-shaped package compares membership instead.
It compares elements pairwise with Go's `==` through interface
conversion, so the element type must be comparable: a non-comparable
element type (a slice, map or function) panics with Go's runtime
comparison panic, but only when two elements are actually compared —
queues of different lengths, and nil or empty queues, are answered
without touching any element.

All four are total functions: none of them panics on a nil queue, which
behaves as an empty queue.

== Errors and panics

The empty queue is reported with an error (compare with `errors.Is`):

[options="header"]
|===
| Error | Meaning

| `ErrEmptyQueue` | `Pop`/`Dequeue`/`Peek` on empty
|===

The package has exactly *one* panic:

[options="header"]
|===
| Call | Why

| `Push`/`Enqueue` on a nil queue | a nil queue cannot store an element
|===

Everything else — including the zero value, which is fully usable
because there is no comparison or equality function to configure —
tolerates a nil queue as an empty queue.  The capability methods add no
panics of their own; the only caveat is `Equal`, which inherits Go's
runtime comparison panic when the element type is non-comparable and two
elements are actually compared (see above).

== Usage

[source,go]
----
package main

import (
    "fmt"

    "github.com/pschlump/pluto/queue_dll"
)

func main() {
    var q queue_dll.Queue[int]

    for _, job := range []int{10, 20, 30} {
        q.Push(job)
    }

    // FIFO: the head is the oldest element.
    v, _ := q.Peek()
    fmt.Println(v) // 10

    for !q.IsEmpty() {
        v, _ := q.Dequeue()
        fmt.Println(v) // 10, 20, 30
    }
}
----
