= hash_tab_dll

`hash_tab_dll` is a generic hash table for Go with a fixed number of
buckets in which *every bucket is a doubly linked list*
(link:../dll[`dll`]).  Collisions chain in the bucket's list exactly like
the singly chained link:../hash_tab[`hash_tab`] — what the dll buckets add
is *O(1) deletion of a previously located element*: `Search` returns a
live element handle and `DeleteFound` splices that element out through
its prev/next pointers without re-walking the chain.  The bucket count is
fixed at construction; when the number of elements is not known up front
use link:../hash_grow[`hash_grow`], which grows and re-hashes
automatically.

It is the fourth intra-charon composition after `priority_queue`,
`heap_sort` and `hash_tab_bt`: a bucket that is a doubly linked list with
O(1) splice-out is exactly what `dll` is, so the table stores one
`*dll.Dll[T]` per bucket instead of reimplementing the lists — the
counterpoint to `hash_tab`'s self-contained chains: here the bucket *does*
use the dll's prev pointers, they are the feature.  Element data is never
boxed into an interface and never unboxed with a type assertion.

* Elements are stored *by value* (`T`, not `*T`) inside the dll nodes.
  The handles `Search` returns — together with a found bool — are the one
  pointer-bearing find in the charon hash-table family, inherited from
  `dll`'s own `Search` because the handle is what makes `DeleteFound` O(1);
  `DllElement.GetData` returns the element by value, and a handle stays
  valid across an `Insert` replacement (the replacement is `SetData` on
  the same node).  `Insert`, `Delete` and `Search` take the probe by
  value — a probe only needs the fields the equality and hash functions
  read.
* `Insert` *replaces* an equal element and returns bool — true when a new
  element was added, false when it replaced one (the replacement is
  `SetData` on the existing node, so previously returned handles stay
  valid).
* Keys of types comparable with `==` (all scalars, strings, pointers,
arrays, and structs of comparable fields) need no functions at all:
`hash_tab_dll.NewHashTab[string](16)`.  Equality is the `==` operator and
hashing is the stdlib `hash/maphash` with a per-table random seed.
* Any other type — or identity by a single field — takes a plain equality
function *and* a hash function, with no interface to implement:
+
[source,go]
----
byID := hash_tab_dll.NewHashTabFunc(
	func(a, b User) bool { return a.ID == b.ID },
	func(u User) uint64 { /* hash of u.ID */ },
	8,
)
----
+
The two functions must agree: whenever `eq(a, b)` is true, `hash(a)` and
`hash(b)` must be equal.

The default hashing is *randomized per table* (a `hash/maphash` seed) — a
hash-flooding mitigation.  Bucket order in `All`, `Values`, `Walk` and
`Dump` therefore varies from process to process and must not appear in
fixed assertions or golden files.  *Within* a bucket the order is not
random at all: the lists run head-newest to tail-oldest (`Insert` pushes
at the head), the same newest-first order as `hash_tab`'s chains and the
opposite of `hash_tab_bt`'s ascending trees.

`Dump` prints an `empty` marker for vacant buckets and one line per
element; no hash values are shown — the dll nodes keep none (unlike
`hash_tab`'s `h=`-annotated dump).

A hash of exactly 0 needs no remapping — an empty bucket is an empty
list, not a hash marker (unlike `hash_grow`'s open addressing).

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Complexity

[cols="2,1,1,4",options="header"]
|===
| Operation                                | Average | Worst case | Notes

| `Insert`                                 | O(1)    | O(n)       | chain scan for an equal element, then a head push or an in-place replace
| `Search`                                 | O(1)    | O(n)       | walks the bucket list, returns the element handle
| `Delete`                                 | O(1)    | O(n)       | chain walk, then an O(1) splice
| `DeleteFound`                            | O(1)    | O(1)       | splices the located element out through its prev/next pointers — no chain walk
| `IsEmpty`, `Len`, `Length`               | O(1)    | O(1)       |
| `Truncate`                               | O(k)    | O(k)       | k = bucket count; bucket lists are emptied
| `Walk`, `Dump`, `All`, `Values`          | O(n)    | O(n)       |
|===

Worst case occurs when many keys collide into one chain; average behavior
is O(1) when hashes spread elements evenly over the k buckets.  The price
of the O(1) `DeleteFound` is two links per node (prev and next) instead
of `hash_tab`'s one, and — like `hash_tab` — the table never grows: pick
n for the expected element count, use `hash_tab` for the smallest
footprint, or `hash_tab_bt` for log-time collision behavior.

== Usage

[source,go]
----
package main

import (
	"fmt"

	"github.com/pschlump/charon/hash_tab_dll"
)

func main() {
	ht := hash_tab_dll.NewHashTab[string](16) // 16 buckets, fixed for the life of the table

	ht.Insert("alpha")
	ht.Insert("beta")
	fmt.Println(ht.Insert("alpha")) // false — duplicate replaces the element

	if el, found := ht.Search("alpha"); found {
		fmt.Println("found", el.GetData()) // the stored element, by value
		ht.DeleteFound(el)                 // O(1) removal of the located element
	}

	ht.Delete("beta") // or delete by value, like hash_tab

	// Range-over-func iteration (Go 1.23+), in bucket order:
	for pos, item := range ht.All() { // (bucket position, element)
		fmt.Println(pos, item)
	}
	for item := range ht.Values() {
		fmt.Println(item)
	}

	ht.Truncate() // remove everything
}
----

The element passed to `DeleteFound` must be a live element of this table
(the same contract as `dll.DeleteFound`): deleting an element twice, or
passing an element of another table, is undefined.

== Iteration

Two styles are supported, both in bucket order (hash-dependent, see the
randomization note above) and — within a bucket — from the most recently
inserted element to the oldest:

- Go 1.23+ range-over-func: `All() iter.Seq2[int, T]` (bucket position and
  element — as with dll/sll/hash_tab, a single-variable range yields the
  *bucket position*, not the element) and `Values() iter.Seq[T]`.
- The `Walk(ApplyFunction[T])` callback: `fx(pos int, data T) bool`, where
  `pos` is the *bucket index* (no `interface{}` userData — state is
  captured in a closure) and returning *false stops the walk* across all
  buckets (the tree-packages convention — dll's own Walk is the opposite);
  Walk returns true when the walk ran to completion.

== Panics

The package panics in exactly four situations — all programmer errors with
no sane fallback, each message naming the fix:

[options="header"]
|===
| Call | Why

| `NewHashTabFunc(nil eq, ...)` / `NewHashTabFunc(eq, nil hash, ...)` | nil function, caught at construction time
| `NewHashTab`/`NewHashTabFunc` with n < 5 | a smaller table has no headroom
| `Insert` on a nil `*HashTab` | a nil table cannot store an element
| `Insert` on a zero-value table | no equality/hash functions; the message names the constructors
|===

Everything else tolerates a nil table and the zero value as an empty table:
searches report not-found, `Delete` and `DeleteFound` return false, and the
iterators visit nothing.

== Thread safety

`hash_tab_dll` is *not* safe for concurrent use. Use the thread-safe twin
link:../hash_tab_dll_ts[`hash_tab_dll_ts`] (the same dll-bucket table with
the O(1) `DeleteFound` behind one `sync.RWMutex`), or
link:../hash_grow_ts[`hash_grow_ts`] (the auto-growing thread-safe hash
table) when the size is not known up front, when the table is shared
between goroutines.
