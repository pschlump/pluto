= hash_tab

`hash_tab` is a generic hash table for Go using separate chaining: each of a
fixed number of buckets owns a singly linked chain of elements stored by
value. The bucket count is fixed at construction; when the number of
elements is not known up front use link:../hash_grow[`hash_grow`], which
grows and re-hashes automatically.

Element data is never boxed into an interface and never unboxed with a type
assertion.

* Elements are stored and returned *by value* (`T`, not `*T`); `Search`
returns `(T, bool)` and `Insert`/`Delete` take the probe by value — a
probe only needs the fields the equality/hash functions read.
* Keys of types comparable with `==` (all scalars, strings, pointers,
arrays, and structs of comparable fields) need no functions at all:
`hash_tab.NewHashTab[string](16)`.  Equality is the `==` operator and
hashing is the stdlib `hash/maphash` with a per-table random seed.
* Any other type — or identity by a single field — takes a plain equality
function *and* a hash function, with no interface to implement:
+
[source,go]
----
byID := hash_tab.NewHashTabFunc(
	func(a, b User) bool { return a.ID == b.ID },
	func(u User) uint64 { /* hash of u.ID */ },
	8,
)
----
+
The two functions must agree: whenever `eq(a, b)` is true, `hash(a)` and
`hash(b)` must be equal.

The default hashing is *randomized per table* (a `hash/maphash` seed) — a
hash-flooding mitigation.  Bucket order in `All`, `Values`, `Walk` and
`Dump`, and the raw hash values `Dump` prints, therefore vary from process
to process and must not appear in fixed assertions or golden files.

A hash of exactly 0 needs no remapping here: an empty bucket is a nil
chain, not a hash marker (unlike `hash_grow`'s open addressing).  `Dump`
prints an `empty` marker for vacant buckets and one line per element.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Complexity

[cols="2,1,1,4",options="header"]
|===
| Operation                                | Average | Worst case | Notes

| `Insert`                                 | O(1)    | O(n)       | head push after a chain scan for an equal element
| `Search`                                 | O(1)    | O(n)       | walks the bucket chain
| `Delete`                                 | O(1)    | O(n)       | chain walk, then an O(1) unlink
| `IsEmpty`, `Len`, `Length`               | O(1)    | O(1)       |
| `Truncate`                               | O(k)    | O(k)       | k = bucket count; chains are released for GC
| `Walk`, `Dump`, `All`, `Values`          | O(n)    | O(n)       |
|===

Worst case occurs when many keys collide into one chain; average behavior is
O(1) when hashes spread elements evenly over the k buckets.  The table never
grows — pick n for the expected element count, or use `hash_grow`.

== Usage

[source,go]
----
package main

import (
	"fmt"

	"github.com/pschlump/pluto/hash_tab"
)

func main() {
	ht := hash_tab.NewHashTab[string](16) // 16 buckets, fixed for the life of the table

	ht.Insert("alpha")
	ht.Insert("beta")
	fmt.Println(ht.Insert("alpha")) // false — duplicate replaces the element

	if v, found := ht.Search("alpha"); found {
		fmt.Println("found", v)
	}

	ht.Delete("alpha")

	// Range-over-func iteration (Go 1.23+), in bucket order:
	for pos, item := range ht.All() { // (bucket position, element)
		fmt.Println(pos, item)
	}
	for item := range ht.Values() {
		fmt.Println(item)
	}

	ht.Truncate() // remove everything
}
----

== Iteration

Two styles are supported, both in bucket order (hash-dependent, see the
randomization note above) and — within a bucket — from the most recently
inserted element to the oldest:

- Go 1.23+ range-over-func: `All() iter.Seq2[int, T]` (bucket position and
  element — as with dll/sll, a single-variable range yields the *bucket
  position*, not the element) and `Values() iter.Seq[T]`.
- The `Walk(ApplyFunction[T])` callback: `fx(pos int, data T) bool`, where
  returning *false stops the walk* (the tree-packages convention — dll and
  sll are the opposite) and the closure captures caller state; Walk returns
  true when the walk ran to completion.

== Panics

The package panics in exactly four situations — all programmer errors with
no sane fallback, each message naming the fix:

[options="header"]
|===
| Call | Why

| `NewHashTabFunc(nil eq, ...)` / `NewHashTabFunc(eq, nil hash, ...)` | nil function, caught at construction time
| `NewHashTab`/`NewHashTabFunc` with n < 5 | a smaller table has no headroom
| `Insert` on a nil `*HashTab` | a nil table cannot store an element
| `Insert` on a zero-value table | no equality/hash functions; the message names the constructors
|===

Everything else tolerates a nil table and the zero value as an empty table:
searches report not-found, `Delete` returns false, and the iterators visit
nothing.

== Thread safety

`hash_tab` is *not* safe for concurrent use. Its thread-safe twin is
link:../hash_tab_ts[`hash_tab_ts`] — the same API behind a `sync.RWMutex`,
plus the `Lock`/`Unlock` pair and `Nl*` methods for compound operations.
The auto-growing alternative is link:../hash_grow_ts[`hash_grow_ts`].
