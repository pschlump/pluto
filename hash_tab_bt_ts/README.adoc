= hash_tab_bt_ts

`hash_tab_bt_ts` is a thread-safe generic hash table for Go with a fixed
number of buckets in which *every bucket is a binary search tree*
(link:../binary_tree[`binary_tree`]).  Because collisions are resolved by a
tree rather than a chain, lookups stay logarithmic in the elements per
bucket even under heavy collisions.  Every operation is guarded by a
single table-level `sync.RWMutex`; the buckets stay plain (non-thread-safe)
`binary_tree` trees — unexported and touched only while the table lock is
held — so there are no per-bucket locks.

It is the thread-safe twin of link:../hash_tab_bt[pluto/hash_tab_bt] — the
same API — with the addition of the `Lock`/`Unlock` pair and the
`Nl*`-prefixed (no-lock) methods for compound operations.  Element data is
never boxed into an interface and never unboxed with a type assertion.

* Elements are stored and returned *by value* (`T`, not `*T`).
* `Insert` replaces an equal element and returns bool — true when a new
  element was added, false when it replaced one.
* A bucket tree needs an *ordering*, not just an equality.  Tables of
naturally ordered types (all integers, floats and strings) need no
functions at all: `hash_tab_bt_ts.NewHashTab[string](16)` orders with the
builtin `<` and `>` operators and hashes with the stdlib `hash/maphash`
using a per-table random seed.
* Any other type — or identity by a single field — takes a plain
comparison function *and* a hash function, with no interface to implement.
The two functions must agree: whenever `cmp(a, b) == 0`, `hash(a)` and
`hash(b)` must be equal.

The default hashing is *randomized per table* (a `hash/maphash` seed) — a
hash-flooding mitigation.  Bucket order in `All`, `Values`, `Walk` and
`Dump` therefore varies from process to process and must not appear in
fixed assertions or golden files.  *Within* a bucket the order is not
random at all: the tree's in-order walk visits the elements ascending per
the comparison function.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Complexity

[cols="2,1,1,4",options="header"]
|===
| Operation                                | Average      | Worst case | Notes

| `Insert`                                 | O(log(n/k))  | O(n)       | tree insert/replace in the hashed bucket
| `Search`                                 | O(log(n/k))  | O(n)       | tree descent in the hashed bucket
| `Delete`                                 | O(log(n/k))  | O(n)       | tree delete in the hashed bucket
| `Contains`                               | O(log(n/k))  | O(n)       | the found flag of Search
| `IsEmpty`, `Len`, `Length`               | O(1)         | O(1)       |
| `Truncate`                               | O(k)         | O(k)       | k = bucket count; bucket trees are emptied
| `InsertSlice`, `InsertIter`              | O(k log(n/k)) | O(n·k)    | batch insert, atomic under one write-lock hold
| `DeleteSlice`                            | O(k log(n/k)) | O(n·k)    | batch delete, atomic under one write-lock hold
| `DeleteFunc`                             | O(n log(n/k)) | O(n²)     | predicate runs unlocked on a snapshot; deletes atomic
| `ContainsSlice`, `ContainsAny`           | O(k log(n/k)) | O(n·k)    | batch membership: all / at least one present
| `Slice`                                  | O(n log(n/k)) | O(n²)     | snapshot under the read lock; bucket order unspecified
| `String`, `StringFunc`                   | O(n log n)   | O(n log n) | formatted strings sorted — deterministic; format runs unlocked
| `Equal`                                  | O(n log(n/k)) | O(n²)     | membership only; never holds both tables' locks
| `Clone`                                  | O(n log(n/k)) | O(n²)     | deep copy under the read lock; keeps bucket count and cmp/hash
| `Walk`, `Dump`                           | O(n)         | O(n)       | read lock held for the whole call
| `All`, `Values`                          | O(n)         | O(n)       | snapshot copied under the read lock
| `Lock` / `Unlock` + `Nl*`                | O(1)         | O(1)       | compound operations
|===

k = number of buckets.  Worst case is every element in one bucket *and*
inserted in sorted order (the unbalanced `binary_tree` degenerates to a
path).  The table never grows — pick n for the expected element count, or
use link:../hash_grow_ts[`hash_grow_ts`].

== Usage

[source,go]
----
ht := hash_tab_bt_ts.NewHashTab[string](16) // 16 buckets, fixed for the life of the table

ht.Insert("alpha")
if v, found := ht.Search("alpha"); found {
	fmt.Println("found", v)
}
ht.Delete("alpha")
----

== Compound operations: Lock + Nl*

`Search` followed by `Delete` is two lock acquisitions — another goroutine
can mutate the table between them.  `Lock` plus the `Nl*` methods
(`NlIsEmpty`, `NlLen`, `NlSearch`, `NlInsert`, `NlDelete`) run the same
steps atomically under one lock hold — the same escape hatch as
link:../hash_grow_ts[`hash_grow_ts`]:

[source,go]
----
ht.Lock()
if v, found := ht.NlSearch(probe); found {
	use(v)
	ht.NlDelete(probe)
}
ht.Unlock()
----

Calling a locking public method while holding `Lock` deadlocks, so inside
the critical section use only the `Nl` methods.  `Lock`/`Unlock` on a nil
table are no-ops.

== Iteration

`All() iter.Seq2[int, T]` (bucket position and element — a single-variable
range yields the *bucket position*, not the element) and `Values() iter.Seq[T]`
iterate a **snapshot** copied under the read lock when the iterator method
is called, so it is safe to call other table methods — including writes —
from the loop body.  `Walk(fx)` is the callback alternative
(`func(pos int, data T) bool`, where `pos` is the *bucket index* and
returning *false stops the walk*); it holds the read lock for the whole
traversal, so `fx` must not call methods on the same table.

== Set conveniences

`capabilities.go` adds the go-set-style surface, all of it additive and
method-for-method identical to link:../hash_tab_bt[hash_tab_bt]'s:

* Materialize: `Slice() []T` — a fresh slice snapshotted under the read
  lock, each bucket's elements ascending per the comparison function,
  buckets in hash order (unspecified — sort when a global order
  matters).  `String()`/`StringFunc(f)` render *deterministically*: each
  element formatted (fmt.Sprint by default), the strings sorted, joined
  `[a b c]`-style — the per-table random seed never shows.  The format
  function runs on the snapshot without the lock, so it may safely call
  back into the table.
* Compare: `Equal(other)` — same element set by membership, never
  iteration order; a nil table equals an empty table.  Each table is
  touched under its own lock only — never two locks at once — so Equal
  cannot deadlock, even when two goroutines compare the same pair in
  opposite directions.  Precondition: both tables use consistent
  comparison/hash functions.
* Copy: `Clone()` — deep copy (fresh bucket trees rebuilt by insertion,
  same bucket count, same cmp/hash) under one hold of the read lock.
* Membership batches: `Contains(x)`, `ContainsSlice(items)` (all
  present), `ContainsAny(items)` (at least one present) — the read lock
  is held once for the whole batch.
* Mutation batches: `InsertSlice(items)` / `InsertIter(seq)` /
  `DeleteSlice(items)` return true when the receiver changed and are
  atomic — the write lock is held once for the whole batch, so an
  interleaved reader sees all or nothing.  `InsertIter` takes any
  container's `Values()` iterator directly, including the table's own
  (safe: the iterator is drained before the lock is taken).
  `DeleteFunc(pred)` snapshots under the read lock, runs the predicate
  with no lock held (it may call back into the table), then deletes the
  matches atomically — collect-then-delete, never modify while walking.

All of them tolerate a nil table and the zero value as an empty table on
the read side, exactly like the core operations.  No new `Nl*` methods:
the capabilities are self-locking, not compounds.

== Panics

The same four situations as link:../hash_tab_bt[pluto/hash_tab_bt], each
message naming the fix:

[options="header"]
|===
| Call | Why

| `NewHashTabFunc(nil cmp, ...)` / `NewHashTabFunc(cmp, nil hash, ...)` | nil function, caught at construction time
| `NewHashTab`/`NewHashTabFunc` with n < 5 | a smaller table has no headroom
| `Insert` on a nil `*HashTab` | a nil table cannot store an element
| `Insert` on a zero-value table | no comparison/hash functions; the message names the constructors
|===

The batch inserters `InsertSlice`/`InsertIter` raise the same insert
contract — a nil or zero-value table panics when, and only when, the
batch would actually store an element; an empty batch is tolerated
everywhere.

Everything else tolerates a nil table and the zero value as an empty table:
searches report not-found, `Delete` returns false, and the iterators visit
nothing.  (`NlInsert` on a zero-value table panics because it *is* the
Insert body.)

== Performance comparison

Benchmarked head-to-head against the other thread-safe pluto hash tables
(500k inserts, 750k searches, 250k deletes, Apple M4 Max): ~122
ns/insert, ~79 ns/search, ~115 ns/delete at ~25 B/elem.  The per-bucket
binary tree keeps lookups O(log n) per bucket, so it stays within ~4× of
the auto-growing open-addressing tables even at 122 elements/bucket —
the best of the three fixed-size chaining tables, with the same minimal
memory.  Full methodology, numbers, and heap profiles:
link:../note/compare-hasing/README.adoc[note/compare-hasing].
