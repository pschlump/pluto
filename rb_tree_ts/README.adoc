= rb_tree_ts

A generic, self-balancing *red-black* binary search tree that is *safe
for concurrent use* — the thread-safe twin of
link:../rb_tree/[pluto/rb_tree].  Every operation is guarded by a
`sync.RWMutex`: readers run in parallel with each other, writers are
exclusive.

Like `rb_tree`, it keeps every root-to-leaf path within a factor of two of
the shortest one, so the ordered operations are *O(log₂ n) in the worst
case* regardless of insertion order.  Ordering never goes through an
interface method, so element data is never boxed into an interface and
never unboxed with a type assertion.

* Elements are stored and returned *by value* (`T`, not `*T`); find-style
operations return `(T, bool)`.
* Trees of ordered key types (integers, floats, strings) are ordered by the
built-in `<` / `>` operators: `rb_tree_ts.NewRbTree[int]()`.
* Trees of any other type — including structs ordered by a single field —
take a plain comparison function, with no interface to implement.

The public API is identical to `rb_tree` (plus the locking behavior
below), so switching between the two is a package-name change.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.  The link:../rb_tree/[rb_tree README] documents the full API
usage; it applies unchanged.

== Operations

[options="header"]
|===
| Operation                         | Complexity

| Insert / Delete / Search          | O(log₂ n) worst case
| FindMin / FindMax                 | O(log₂ n) worst case
| DeleteAtHead / DeleteAtTail       | O(log₂ n) worst case
| Depth                             | O(n) work, under the read lock
| IsEmpty / Len / Length / Truncate | O(1)
| Dump                              | O(n)
| All / Backward (full iteration)   | O(n) — plus an O(n) snapshot
| Contains                          | O(log₂ n) worst case
| ContainsSlice / ContainsAny       | O(k·log₂ n) — atomic
| InsertSlice / InsertIter          | O(k·log₂ n) — atomic
| DeleteSlice / DeleteFunc          | O(n log₂ n) — DeleteFunc's predicate runs unlocked
| Slice / String / StringFunc       | O(n) — snapshot under the read lock, format unlocked
| Equal / Clone                     | O(n log₂ n) / O(n) — never two locks
|===

`Insert` returns `true` when a new node was added and `false` when a
duplicate replaced the stored value.  `Len` is an alias for `Length`,
matching the other pluto tree packages.  `DeleteAtHead` / `DeleteAtTail`
splice the extreme node out directly (a single descent) instead of
re-searching for the min/max item through `Delete`.

== Locking behavior

* *Reads* (`Search`, `FindMin`, `FindMax`, `Depth`, `Len`, `Length`,
`IsEmpty`) take the read lock and release it before returning — they can
run in parallel with each other.
* *Writes* (`Insert`, `Delete`, `DeleteAtHead`, `DeleteAtTail`,
`Truncate`) take the write lock.  The *batch mutators* (`InsertSlice`,
`InsertIter`, `DeleteSlice`) hold the write lock once for the whole
batch, so a batch is atomic: an interleaved reader sees none or all of
it, never part.
* *`All` and `Backward` operate on a snapshot* of the tree taken when
they are called (under the read lock, released immediately after).  It
is safe to mutate the tree while iterating — including from inside the
loop — and an iterator never observes modifications made after it was
created.  The snapshot costs one O(n) copy.
* *Compute-after-snapshot methods* (`Slice`, `String`, `StringFunc`,
`Equal`, `DeleteFunc`'s match pass) snapshot under the read lock and run
the caller format or predicate function *without* any lock held — a
callback may safely call back into the tree.  `Equal` snapshots one side
and probes the other one element at a time, so it never holds two locks —
not even when two goroutines compare the same pair in opposite
directions.  The membership batches `ContainsSlice`/`ContainsAny` hold
the read lock for the whole batch, so the answer describes one consistent
snapshot.
* *`Dump` holds the read lock for the whole dump*, so the writer must
not call methods on the same tree.

The go-set-style surface (`Contains`, the batches, `Slice`, `String`,
`Equal`, `Clone`) behaves exactly as documented in the
link:../rb_tree/[rb_tree README]; `capabilities.go` adds it behind the
locks described above.

[source,go]
----
for v := range tree.All() {
    tree.Delete(v) // safe: All iterates a snapshot
}
----

== Panics

Identical to `rb_tree` — the package panics in exactly three situations,
all programmer errors with no sane fallback:

[options="header"]
|===
| Call                          | Why

| `NewRbTreeFunc(nil)`          | nil comparison function, caught at construction time
| `Insert` on a nil `*RbTree`   | a nil tree cannot store an element
| `Insert` on a zero-value tree | no comparison function; the message names the constructors
|===

Everything else tolerates a nil tree and the zero value as an empty tree
(the zero value of `sync.RWMutex` is a working lock).

The batch inserters `InsertSlice`/`InsertIter` raise the same insert
contract as `Insert` — a nil tree or a zero-value tree panics when, and
only when, the batch would actually store an element; an empty batch is
tolerated everywhere.  Every other capability is a total function on the
read side (`Slice` of nil is nil, `String` of nil is `[]`, `Equal` of nil
is equality with an empty tree, `DeleteFunc` on nil returns false).

== Usage

[source,go]
----
package main

import (
    "fmt"
    "sync"

    "github.com/pschlump/pluto/rb_tree_ts"
)

func main() {
    tree := rb_tree_ts.NewRbTree[int]()

    // Writers from many goroutines share one tree.
    var wg sync.WaitGroup
    for w := 0; w < 8; w++ {
        wg.Add(1)
        go func(w int) {
            defer wg.Done()
            for i := 0; i < 100; i++ {
                tree.Insert(w*1000 + i)
            }
        }(w)
    }
    wg.Wait()
    fmt.Println(tree.Len()) // 800

    // Deleting from inside an All loop is safe: it iterates a snapshot.
    for v := range tree.All() {
        tree.Delete(v)
    }
    fmt.Println(tree.IsEmpty()) // true
}
----
