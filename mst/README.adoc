= mst

Minimum spanning trees of an edge-weighted *undirected graph* — Sedgwick's
§4.3 — as constructor-style query objects over
link:../dijkstra/[`dijkstra`]'s `EdgeWeightedGraph`.  All three classic
algorithms are here, each a natural intra-pluto composition:

* `LazyPrimMST` — lazy Prim's algorithm, crossing edges on a
  link:../priority_queue/[`priority_queue`].
* `PrimMST` — eager Prim's algorithm, one queue entry per vertex on a
  link:../index_pq/[`index_pq`] (`Change` is the decrease-key).
* `KruskalMST` — Kruskal's algorithm, cycle detection with a
  link:../union_find/[`union_find`].

Each result is computed eagerly in the constructor and is an *immutable
snapshot*: later `AddEdge` calls on the graph are not reflected.  On a
disconnected graph every constructor produces the minimum spanning
*forest* — one minimum tree per connected component, so fewer than `V-1`
edges.  Edge weights may be *negative* (an MST is well-defined for
arbitrary weights — unlike the Dijkstra constructors, nothing here
rejects them), and self-loops / parallel edges are handled: a self-loop
never joins a tree and the cheapest of parallel edges wins.

Not safe for concurrent use (a mutex-guarded twin,
link:../mst_ts/[`mst_ts`], has the same interface over
link:../dijkstra_ts/[`dijkstra_ts`] graphs).

== Operations

[options="header"]
|===
| Operation            | Description                                   | Complexity

| `NewLazyPrimMST(g)`  | MST/MSF via lazy Prim's algorithm             | O(E log E) time, O(E) space
| `NewPrimMST(g)`      | MST/MSF via eager Prim's algorithm            | O(E log V) time, O(V) space
| `NewKruskalMST(g)`   | MST/MSF via Kruskal's algorithm               | O(E log E) time, O(E) space
| `Edges()`            | The tree edges, a fresh slice                 | O(Len)
| `Weight()`           | Total weight of the tree (forest)             | O(1)
| `Len()`              | Number of tree edges (`V-1` when connected)   | O(1)
|===

All three algorithms produce the same total weight; when the MST is
unique (distinct edge weights) they produce the same edge set, too.

== Usage

[source,go]
----
g := dijkstra.NewEdgeWeightedGraph(4)
g.AddEdge(dijkstra.Edge{V: 0, W: 1, Weight: 1})
g.AddEdge(dijkstra.Edge{V: 1, W: 2, Weight: 2})
g.AddEdge(dijkstra.Edge{V: 2, W: 3, Weight: 3})
g.AddEdge(dijkstra.Edge{V: 0, W: 3, Weight: 10})

mst := mst.NewKruskalMST(g)
for _, e := range mst.Edges() {   // 0--1(1), 1--2(2), 2--3(3), ascending by weight
    ...
}
mst.Weight()                      // 6
mst.Len()                         // 3 — V-1 on a connected graph
----

== Panics

[options="header"]
|===
| Call                                    | Why

| `NewLazyPrimMST`/`NewPrimMST`/`NewKruskalMST` on a nil or empty graph | no spanning tree exists to compute
|===

That is the whole panic surface.  A nil result object tolerates every
read: `Edges` reports nil, `Weight` 0, `Len` 0.

== Concurrency

Not safe for concurrent use.  Use link:../mst_ts/[`mst_ts`], whose
constructors read the graph's adjacency through `dijkstra_ts.Adj`
snapshot copies taken under the read lock and then compute lock-free;
its result objects are immutable and safe for concurrent reads.
