= rb_tree

A generic, self-balancing *red-black* binary search tree.  A red-black
tree keeps every root-to-leaf path within a factor of two of the shortest
one, so the ordered operations are *O(log₂ n) in the worst case* —
regardless of insertion order, unlike the unbalanced
link:../binary_tree/[`binary_tree`].  See
link:https://en.wikipedia.org/wiki/Red–black_tree[]
for the theory; link:../avl_tree/[`avl_tree`] is the height-balanced
alternative.

Ordering never goes through an interface method, so element data is
never boxed into an interface and never unboxed with a type assertion.

* Elements are stored and returned *by value* (`T`, not `*T`); find-style
operations return `(T, bool)`.
* Trees of ordered key types (integers, floats, strings) are ordered by the
built-in `<` / `>` operators: `rb_tree.NewRbTree[int]()`.
* Trees of any other type — including structs ordered by a single field —
take a plain comparison function, with no interface to implement:
`rb_tree.NewRbTreeFunc(func(a, b Item) int { ... })`.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Operations

[options="header"]
|===
| Operation                       | Description                                      | Complexity

| `Insert`                        | Add an item; duplicates replace the stored value | O(log₂ n)
| `Delete`                        | Remove an item; reports whether it was found     | O(log₂ n)
| `Search`                        | Return the stored item equal to the probe        | O(log₂ n)
| `FindMin` / `FindMax`           | Return the smallest / largest item               | O(log₂ n)
| `DeleteAtHead` / `DeleteAtTail` | Remove the smallest / largest item               | O(log₂ n)
| `Depth`                         | Longest root-to-leaf path                        | O(log₂ n)
| `IsEmpty` / `Len` / `Length`    | Size queries                                     | O(1)
| `Truncate`                      | Remove all items                                 | O(1)
| `Dump`                          | Indented picture with node colors, for debugging | O(n)
| `All` / `Backward`              | Range-over-func iterators                        | O(n), O(1) space
|===

`Insert` returns `true` when a new node was added and `false` when a
duplicate replaced the stored value.  `Len` is an alias for `Length`,
matching the other charon tree packages.  `DeleteAtHead` / `DeleteAtTail`
splice the extreme node out directly (a single descent) instead of
re-searching for the min/max item through `Delete`.

The tree is *not* safe for concurrent use.

== Usage

[source,go]
----
tree := rb_tree.NewRbTree[int]()

// Sorted input still leaves a shallow tree: the red-black recoloring and
// rotations keep every root-to-leaf path within 2x of the shortest one.
for i := range 1000 {
    tree.Insert(i)
}

min, _ := tree.FindMin()
max, _ := tree.FindMax()
fmt.Println(min, max, tree.Depth()) // 0 999 17
----

Structs ordered by a field — the element type implements no interface, and
the exported `Compare` helper builds the field comparison:

[source,go]
----
type Employee struct {
    ID   int
    Name string
}

byID := rb_tree.NewRbTreeFunc(func(a, b Employee) int {
    return rb_tree.Compare(a.ID, b.ID)
})
byID.Insert(Employee{ID: 3, Name: "Ada"})

// A search probe only needs the fields the comparison reads: the ID.
if e, found := byID.Search(Employee{ID: 3}); found {
    fmt.Println(e.Name) // Ada
}
----

== Iteration

`All()` and `Backward()` are range-over-func iterators (Go 1.23+) in
ascending and descending order.  Because every node stores a parent
pointer, both are plain successor/predecessor walks with *O(1) extra
space* — no recursion and no explicit stack:

[source,go]
----
for v := range tree.All() {
    ...
}
for v := range tree.Backward() {
    ...
}
----

The tree must not be modified while an iterator is being consumed — the
iterators walk the live nodes.

== Panics

The package panics in exactly three situations — all programmer errors
with no sane fallback:

[options="header"]
|===
| Call                          | Why

| `NewRbTreeFunc(nil)`          | nil comparison function, caught at construction time
| `Insert` on a nil `*RbTree`   | a nil tree cannot store an element
| `Insert` on a zero-value tree | no comparison function; the message names the constructors
|===

Everything else tolerates a nil tree and the zero value as an empty tree:
searches find nothing, deletes return `false`, and the iterators visit
nothing.
