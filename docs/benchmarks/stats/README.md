### Causes

- **Quantiles.** The CPU profile of the old pass was 45% `slices.insertionSortOrdered`
  (the `slices.Sort` call on every group of five) plus 28% `partition` with
  10% in `cmp.Compare`. Every recursion level computed a full repeated
  median-of-five pivot — an O(n) pass that sorts n/5 groups through a generic
  call — before partitioning, so a "linear" selection cost several full-array
  passes per level, more than pdqsort on the whole array. Measured split: with
  the cheap pivots disabled (median-of-five at every level, but plain `<` and
  inline insertion sort) the pass took ~255 µs, so the pivot rule was ~80% of
  the excess and the generic compare/sort overhead the rest. The replacement
  is an introselect in the spirit of Guava's `Quantiles.selectAllInPlace`:
  median-of-three / ninther pivot values, a Hoare partition (3-way only as the
  no-progress fallback), descent only into partitions holding requested ranks,
  insertion sort at ≤16 elements, and the old median-of-five pivot only after
  a `2·bits.Len(n)` level budget. Dutch-flag 3-way partition with the new
  pivots measured ~50 µs; switching to Hoare took it to ~37 µs.
- **Accumulators.** `math.Min`/`math.Max` compile to out-of-line calls
  (`math.archMin` 31% + `archMax` 14% of the profile). They are replaced by
  inlinable `minFloat`/`maxFloat` with identical bits — the builtin `min`/`max`
  alone differ from `math.Min`/`Max` on a (-Inf, NaN) / (+Inf, NaN) pair, which
  a new test caught. `finite` became `value-value == 0` (exact; ~2–3% on the
  accumulator, within noise on paired). The rest is the serial
  `mean += delta / count` dependency chain, which is Guava's arithmetic; a
  reciprocal multiply would be faster but changes results, so it was not done.

### Harness check

`StatsBenchmark.java` and `bench_test.go` match: 10,000 values
`((i*7919)%1000)/7`, indexes 0,10,…,100 at scale 100, `Quantiles.compute`
clones the input inside the timed region exactly as Go's copying `Quantiles`
does, and both consume the result. Guava's quantile benchmark also builds a
`Map<Integer, Double>` result, which only adds to its cost. No mismatch found.

### Rejected experiments

- Insertion cutoff 8 (~41 µs), 32 (~37.6 µs, no better than 16), 48 (~40 µs):
  kept 16.
- `Accumulator.AddAll` with the state hoisted into locals (same arithmetic):
  ~40 µs vs ~38 µs — slower, reverted.
- Fused `PairedAccumulator.AddAll` loop with locals: ~72 µs vs ~71 µs — no
  gain, reverted. Paired is bound by two division chains per pair.
- Folding the three small index-bookkeeping allocations into one: not
  attempted beyond estimation (≈100 ns of a ~40 µs op); the 80 KB input copy
  is inherent to the copying API (Guava clones too).
