# Phase 8 math benchmark record

Recorded 2026-11-22 on Apple M4 Max, darwin/arm64, Go 1.27.0, OpenJDK 11.0.28,
Guava commit `36e3995499d6c3b74b1207d362fa9e19915d2589`. Go ran three 1-second
measurements; JMH 1.37 ran two 1-second warmups and three 1-second measurements,
one fork/thread. Inputs are fixed non-trivial signed 64-bit boundaries; the
prime is `2^63-25`.

G=billion). Go ranges are reciprocal conversions of measured latency,
slowest to fastest; JMH rates are reported directly.

**Causes (CPU and alloc profiles).** Log10 and Binomial spent their time in
`math/big` (`nat.make` was 98% of allocated bytes; `nat.expNN`, `nat.div`,
`Int.Mul`/`Quo` dominated CPU) on inputs that always fit a machine word.
IsPrime's `mulMod` was a bit-serial double-and-add loop (64 iterations per
modular multiplication). Divide spent more time in its two non-inlined helper
layers (`shouldRound`, `compareTwiceMagnitude`) than in the division.

**Changes.**
- Log10/Log2 half modes: the midpoint is irrational, so the exact comparison
  value² vs 2^(2f+1) / 10^(2f+1) is a single compare against a precomputed
  floor-square-root threshold (`halfPowersOf10`, `0xB504F333F9DE6484 >> (63-f)`).
  Log10's floor uses a bit-length estimate plus one `powersOf10` lookup
  instead of a 19-step multiply loop. 49× faster, allocation-free.
- Binomial: Pascal-triangle table for n ≤ 67 (every C(n,k) that fits uint64),
  128-bit `bits.Mul64`/`bits.Div64` recurrence with a provably-correct early
  overflow exit above that. ~240×. An intermediate step — the 128-bit loop
  alone, no table — measured 12.2–13.0 ns (≈80M ops/s); the table was kept
  because it measured another 12×.
- IsPrime: first `bits.Mul64` + `bits.Rem64` (5.2 µs, 8×), then Montgomery
  multiplication (1.47 µs, another 3.6×; `bits.Rem64` is a software divide on
  arm64). Witness set unchanged.
- Divide: rounding decision inlined into one function. 3.7 → 2.3 ns.
- Sqrt: multiply-based correction of the float estimate instead of three
  divisions. 2.4 → 2.0–2.2 ns — a modest ~10% gain, kept because it was
  consistent across runs.

**The Guava figures for divide, sqrt and binomial are almost certainly
constant-folded.** `MathBenchmark.java` passes literal constants
(`LongMath.divide(9223372036854775806L, 37, …)`, `LongMath.binomial(30, 15)`)
to pure static methods, and all three land at ~782M ops/s (≈1.28 ns) — the
same ceiling regardless of work. `LongMath.binomial(30, 15)` takes Guava's
multiply/divide loop (n = 30 exceeds its factorial table), which cannot run in
1.3 ns. The JIT evaluated those calls at compile time; the numbers measure the
JMH harness, not the arithmetic. The Go benchmarks call non-inlined functions
and measure the real work. Log10 (426M) and isPrime are plausibly genuine.

**Rejected / not pursued.** None of the measured steps regressed; the
rejected alternative was keeping `bits.Rem64` for IsPrime (superseded by
Montgomery). The Divide figure still trails the (folded) Guava number; the
remaining cost is the hardware divide plus the generic-shape dictionary call.
