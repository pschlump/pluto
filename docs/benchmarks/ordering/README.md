# ordering benchmarks: Pluto (Go) vs Guava (Java)

## Current results

Rates are operations per second; higher is better. The Go column was
measured 2026-11-27 on an Apple M4 Max, darwin/arm64, Go 1.27.0: three
1-second runs, shown slowest–fastest, plus bytes and allocations per
operation. Raw output is `go-2026-11-27-current.txt`.
The Java column is Guava under JMH on OpenJDK 11.0.28, copied from the
2026-11-22 record below and not re-run (mean ± error).

## Original record (2026-11-22)

Recorded 2026-11-22 on Apple M4 Max, darwin/arm64, Go 1.27.0, OpenJDK 11.0.28,
Guava commit `36e3995499d6c3b74b1207d362fa9e19915d2589`. Each workload uses
10,000 deterministic integers modulo 100,000; top-k uses k=32. Go ran three
1-second measurements. JMH 1.37 ran two 1-second warmups and three 1-second
measurements, one fork/thread.

All comparison rates use operations/second (K=thousand, M=million,
G=billion). Go ranges are reciprocal conversions of measured latency,
slowest to fastest; JMH rates are reported directly.

| Workload           | Pluto/Go                              | Guava/Java                   |
|--------------------|--------------------------------------:|-----------------------------:|
| Stable sorted copy | 1.186–1.198K ops/s; 81,920 B, 1 alloc | 1,971.834 ops/s ± 208.328    |
| Least 32           | 31.746–32.154K ops/s; 336 B, 4 allocs | 45,074.272 ops/s ± 2,211.602 |
| Greatest 32        | 26.476–26.631K ops/s; 360 B, 5 allocs | 46,628.871 ops/s ± 1,368.965 |
| Full-sort baseline | 5.889–6.139K ops/s; 81,920 B, 1 alloc | 7,860.844 ops/s ± 4,965.949  |

The baseline is Go `slices.Sort` on an `[]int` copy versus Java `Arrays.sort` on
an `int[]` copy, so its primitive representation differs from the boxed generic
ordering workloads. No cross-language speed ratio is inferred.

Raw files are `go-matched.txt`, `jmh-matched.json`, and `normalized.json`.
The checked golden is `ordering/testdata/guava_ordering.json`, generated by
`OrderingOracle` from the pinned source.
