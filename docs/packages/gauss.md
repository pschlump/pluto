# gauss notes

`gauss` is Sedgwick §9.5's two elimination classes as constructor-built query objects over the minimal matrix story (`[][]float64` A, `[]float64` b): `GaussianElimination` (forward elimination + back substitution, RECTANGULAR m×n allowed) and `GaussJordanElimination` (full reduction, square n×n only, carrying an identity block). Both use partial pivoting with the algs4 epsilon 1e-8 (both classes — Gaussian's is 1e-8 too, not the 1e-10 you might half-remember), and both PANIC on non-finite input with the position (NaN compares false against every bound, and pivoting compares ABSOLUTE VALUES so a NaN pivot would slip through `|a[p][p]| <= eps` as "not tiny" and poison the elimination — the floyd_warshall/global_mincut precedent, checked BEFORE the augmented matrix is built). Pivot ≤ eps ⇒ `continue` (the column is skipped; its variable is a free variable reported as zero); a zeroed row with rhs > eps ⇒ infeasible. Row swaps swap SLICE REFERENCES (one assignment pair), and ties in the max scan keep the FIRST row (strict `>`) — so outputs and certificates are deterministic.

GaussJordan keeps the algs4 augmented shape n×(2n+1): A | identity | b. The identity block is NOT decoration — `Dual()` reads it: for the first inconsistent reduced row i (tiny diagonal, non-tiny rhs), y = a[i][n:2n] is a Farkas certificate (yA = 0, yb ≠ 0). `pivot(p, q)` is the algs4 form verbatim: eliminate every row i≠p over every column j≠q, then zero column q explicitly, then scale row p — the explicit zeroing exists because the j==q entries were skipped in the elimination loop ("consistency with the simplex pivot"). Primal reads x[i] = a[i][2n]/a[i][i] (the division matters only for skipped-pivot rows, where the diagonal is tiny and the rhs must be tiny too or the system is inconsistent — free variables report 0). `IsNonsingular` is a pluto ADDITION over the algs4 surface (the backlog's "singular detection" ask): all |a[i][i]| > eps; nil/empty is vacuously nonsingular.

THE CORNER (cost a wrong doc comment and a wrong test to find): Gaussian's back substitution assigns variable j at row j, from i = min(n−1, m−1) down, and includes Σ_{j>i} a[i][j]·x[j] in the consistency check — so the SQUARE case is sound even with a zero leading column ([[0,5],[0,3]]·x=[10,6] correctly yields x=(0,2): row 1 solves x[1]=2 first, then row 0 balances 5·2=10 with x[0]=0). The gap is UNDERDETERMINED ONLY: for m < n, columns m..n−1 never pivot (the forward loop bounds at min(m,n)) so those variables stay 0, and a row needing one of them nonzero reports inconsistent — [[0,5]]·x=10 (solvable, x=(0,2)) reports infeasible. Faithful to algs4, documented in Primal's comment and the README. GaussJordan is square-only, so Dual-certificate users never see it.

Oracles, all assumption-free (the algs4 certifySolution turned into tests): (1) feasible answers must satisfy A·x = b — generated systems carry an EXACT integer solution (diagonally dominant integer A, x★ random integers, b = A·x★ exact in float64), so the unique-solution case checks x == x★ componentwise; (2) infeasible answers must carry a Dual with yA = 0 and |yb| > eps; (3) singular-consistent (duplicate a row, b from A·x★) and singular-inconsistent (then bump one rhs entry by 1 — integer, unmissable); (4) cross-family: Gauss and Jordan agree on square systems, and both report built-inconsistencies infeasible (that direction is corner-immune: the zeroed row is caught regardless). Benchmarks measured BEFORE documented (the item-17/fft lesson — the first comment draft had guessed 4.4×; measured is ~6×): Gaussian 213µs @n=100 / 6.0ms @n=300, Jordan 1.36ms / 34.7ms, both 28× for 3× n.
