# sharded_hash_ts notes

`sharded_hash_ts` is the striped (sharded) concurrent hash table (request `note/03-sharded-hash-table.md`, the Ultima keyspace — it replaces N independent `cuckoo_ts` tables plus caller-side routing/iteration glue): one logical table, N power-of-two stripes each with its own `sync.RWMutex` and chained table, `Len` a lock-free `atomic.Int64` — no global lock anywhere; **no plain twin** (the `queue_dll`/`suffix_array` documented-exception precedent; striping exists only for concurrent use). Constructors are **positional, not the note's functional options** (house convention): `NewShardedHash[T comparable](stripes, initialCapacity, loadFactor)` / `NewShardedHashFunc[T any](eq, hash, stripes, initialCapacity, loadFactor)`; normalization: stripes round **up** to a power of two (1 and 2 legal — 1 is the degenerate single-lock benchmark case; > 2^24 panics, the cursor's stripe field), initialCapacity rounds up to a power of two with floor 16, loadFactor ≤ 0/NaN → 0.75. **Set-shaped like every pluto hash table** (the note's `Pair[T, V]` sketch dropped per its own "consistency with the existing HashTab[T] API matters more" instruction) — the map pattern is a two-field struct with eq/hash reading only the key field (tested in `TestMapPattern`); `Insert` returns true=added/false=replaced (hash_grow polarity). Stripe routing is **Fibonacci hashing** (`(hash * 0x9E3779B97F4A7C15) >> stripeShift`, top bits route, low bits bucket) — decorrelates routing from bucket bits for any caller hash; elements never migrate stripes.

**The stripe internals are deliberately NOT hash_grow/cuckoo open addressing, even though hash_grow benchmarks fastest** — the SCAN contract forces chains. Scan promises the Redis guarantee (a full iteration returns everything present throughout at least once), which is only provable when an element never changes buckets except by the deterministic split of a doubling (bucket v → v or v+oldSize by one hash bit). `hash_grow`'s backward-shift deletion moves elements between buckets on every delete and its growth re-probes from home depending on occupancy — either can strand an element in an already-scanned bucket. Chains move nothing: insert push-front, delete unlink, growth re-link at `h & newMask` (nodes keep their raw hash, never re-hashed; this is Redis's own `dict` split; hash 0 legal — no empty-slot marker needed, unlike hash_grow).

`Scan(cursor, count)`: cursor = stripe index in the high 24 bits | Redis **reverse-binary bucket cursor** in the low 40 (`revBinNext`: `v |= ^m; reverse; ++; reverse; &m` — the `dictScan` increment; unit-tested sequence 0,2,1,3 / 0,4,2,6,1,5,3,7). At most ONE stripe read lock per call, never across calls; whole buckets emitted (count is a hint, ≤ 0 → 10); Truncate-during-scan **proceeds cleanly** (pick-and-documented — the guarantee covers only what remains); an invalid cursor restarts at 0 rather than panicking. `LockKey(key)` returns just the unlock closure (the note's `NlShardedHash[T]` view dropped — the pluto `Nl*`-on-the-main-type convention); `Nl*` are race-free only for keys of the **held** stripe, `NlLen`/`NlIsEmpty` are global atomics; multi-key clients MUST lock in stripe-index order (documented deadlock rule). Count deltas are conserved under the stripe write lock (Insert/Delete/Truncate update the atomic while holding the stripe's lock, so a concurrent Truncate can never double-subtract). Panic contract exactly 4 in the hash_grow shape (nil eq/hash, stripes < 1, Insert on nil, Insert on zero-value) plus a pathological grow-past-2^40 guard.

Tests: `checkInvariants` (node sits in the bucket its hash masks to, per-stripe live counts, Σ == atomic Len); **`TestScanGrowthMidScan` is the contract test** (mid-scan churn forces doublings; churn is capped at the first 50 calls — uncapped churn adds buckets faster than a count=1 scan visits them and livelocks the scan); `TestConcurrentOracle` holds the oracle mutex **across** predict/table-op/apply/compare (updating oracle and table in separate critical sections is the racy-wrong first draft — exact per-op cross-checks are only sound when the two update atomically together); `TestLockKeyRMWAtomicity` (8 writers × 250 lock-held increments must land exactly 2000 — a lost update would read low); randomized model seed 42. Benchmarks in `bench_test.go`: 1/4/16/256 stripes × read-heavy and 50/50 via `b.RunParallel` vs `hash_grow_ts`/`cuckoo_ts` single-lock and a `manualCuckoo16` glue baseline; contenders flow through one generic-constraint helper (`stringTable` as a **type-parameter constraint, not interface values** — monomorphized, no dispatch in the measured loop). M4 Max, 14 cores: 58.5→12.5 ns/op read-heavy from 1→256 stripes vs 67 (`hash_grow_ts`) and 75 (`cuckoo_ts`) single-lock; ~1.15 ms per full 100k scan.

`capabilities.go` (set-capabilities phase 1) adds the go-set surface (`Slice`/`String`/`StringFunc`/`Equal`/`Clone`/`Contains`/`ContainsSlice`/`ContainsAny`/`InsertSlice`/`InsertIter`/`DeleteSlice`/`DeleteFunc`) translated to the sharding discipline — the batch methods are **grouped by stripe, not one-lock-atomic like the other twins**. `groupByStripe` routes each item via `stripeIndexOf` and the batch walks stripes in **stripe-index order** (the multi-key LockKey rule — concurrent batches can never deadlock), taking each stripe's lock for that stripe's whole share and only ever one stripe lock at a time: per-stripe atomic, deliberately NOT table-wide atomic (the Scan/Truncate caveat, documented on every batch method). `InsertSlice` and `InsertIter` share the `insertGrouped` helper; each inserts/deletes apply its count delta under the stripe write lock like the core ops. `InsertIter` drains the iterator first (self-feed safe) and runs its own `insertContractCheck("InsertIter")` — the panic must name the actual method, not the helper (first draft delegated to `InsertSlice` and named the wrong method; the test catches this). Panics add no new situations: the batch inserters raise exactly Insert's nil/zero-value contract, prefix `sharded_hash_ts:`, firing only when a batch would store an element. `Slice` snapshots per stripe (each stripe consistent, stripes not mutually consistent); `String`/`StringFunc` sort the formatted strings (`g_lib.FormatSorted`) so the seed never leaks; the `DeleteFunc` predicate and `StringFunc` format run unlocked on the snapshot; `Equal` holds at most one stripe lock of one table at any moment (no deadlock both directions). `Clone` rebuilds each stripe under its RLock (`heads` same length, `live`/`threshold` copied, chains node-by-node preserving order, count via `Store`) — no background machinery to skip, unlike cuckoo_ts. **The BatchAtomicity test must probe through a stripe lock, not `Len`**: `Len` is the lock-free atomic the batch increments per element under the stripe lock, so it legitimately observes fine-grained partial states; `StripeLen(0)` on a 1-stripe table blocks on the write lock and wakes to 0-or-batch (the first draft polled `Len` and failed on exactly this). `TestCapabilitiesBatchCrossStripe` covers the table-wide half: every element lands and the stripes' live counts sum to Len. Test/example files derive from the hash_tab_ts pair — keep in sync.
