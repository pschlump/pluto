# binary_tree notes

`BinaryTree[T any]` holds `root`, `length`, and the stored `cmp` func. `deleteBy` implements delete (two-children case promotes the in-order successor). `DeleteAtHead`/`DeleteAtTail` splice the extreme node out in a single descent — they do not call `FindMin`/`FindMax` + `Delete`. Split across files: core in `binary_tree.go`, `Front`/`All`/`Backward` iterators in `iter.go` (slice stack, no external stack package), `WalkFunc` in `apply.go`.

`binary_tree_ts` adds a `lock sync.RWMutex` to the same struct, lock-free `nl*` helpers (`nlIsEmpty`, `nlFindMin`, `nlFindMax`, `nlDepth`) for use while the lock is held, and `snapshotInOrder() []T`, which backs `Front`/`All`/`Backward`.

`capabilities.go` (set-capabilities phase 2) adds the go-set surface: `Slice`/`String`/`StringFunc`/`Equal`/`Clone`/`Contains`/`ContainsSlice`/`ContainsAny`/`InsertSlice`/`InsertIter`/`DeleteSlice`/`DeleteFunc`.  Ordering is free: every walk is the in-order traversal, so `Slice` is ascending and `String` (`fmt.Sprint`, space-joined in brackets) is deterministic with **no sorting** — that is the ordered-family contrast with the hash families' sorted-format rule.  `Equal` is membership-based (never tree shape) with the documented cmp-consistency precondition; nil == empty.  `Clone` is a recursive structural copy preserving shape and `cmp`.  `DeleteFunc` is collect-then-delete (in-order snapshot first, then `Delete` each match).  `InsertSlice`/`InsertIter` share `insertContractCheck(caller)`/`insertAll`: the insert panic contract fires **only when the batch would store an element** (empty batch tolerated everywhere), messages naming the actual method; `InsertIter` drains the iterator before inserting, so `InsertIter(tt.All())` is safe.  nil `fx`/`format`: `DeleteFunc`/`StringFunc` return false/"[]" — no new panics.  The twin mirrors method for method: batches atomic under one write-lock hold, `Slice`/`String` snapshot via `snapshotInOrder` then compute unlocked (caller format functions may call back), `DeleteFunc`'s predicate runs unlocked, `Equal` never holds two locks (each operand touched under its own lock), `Clone` copies under the read lock, and `ContainsSlice`/`ContainsAny` use the lock-free `nlContains` walk added in `capabilities.go` under one read-lock hold.  Tests: `capabilities_test.go` runs verbatim against the twin (only the package line differs) plus the twin-only concurrency block; `capabilities_example_test.go` mirrors the same way.
