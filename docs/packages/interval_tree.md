# interval_tree notes

`IntervalTree[K, V any]` is the interval search tree (backlog 3.3 — CLRS §14.3 / algs4 exercise 3.3.43 IntervalST): a red-black BST over **closed intervals** `Interval[K]{Lo, Hi K}` with a satellite value `V` (two type params, the lru map pattern — the backlog sketch's `IntervalTree[T]`/`val T` was a sketch typo), keyed by (lo, hi) lexicographic (`ivCmp` — equal means the same interval, replace the value).  **Self-contained, not composed on `rb_tree`** (the stack_sll_ts/dqueue rationale): every node carries the augmentation `maxHi` = max Hi over its subtree, and it must be maintained inside the rotations.  Constructors are the house pair on the ENDPOINT type: `NewIntervalTree[K cmp.Ordered, V any]()` / `NewIntervalTreeFunc[K, V any](fx func(a, b K) int)` (custom-key test uses `Interval[bound]{Lo: bound{...}, Hi: bound{...}}` — elided nested literals do NOT compile through a type parameter).

maxHi protocol (the part to preserve): `fixMax(n)` = max(n.iv.Hi, child maxHi's, nil child contributes nothing); both rotations `fixMax(x)` then `fixMax(y)` (x becomes the lower node).  Insert: z.maxHi = z.iv.Hi, walk up from z.parent GROWING maxima with an early break at the first ancestor already covering the new Hi, THEN `insertFixup` (rotations self-maintain).  Delete: the rb_tree `deleteNode` splice verbatim, then a full `fixMax` walk from `xParent` up to root (deletes can only SHRINK maxima, no early break) — the walk covers y's new position in every case because the chain from xParent passes through every changed node — and this MUST run BEFORE `deleteFixup`, whose rotations read their children's maxima.  `deleteFixup`/`insertFixup` are rb_tree's verbatim.

Queries: overlap = closed-interval predicate `a.Lo <= b.Hi && b.Lo <= a.Hi` (touching endpoints overlap; point intervals legal).  `AnyOverlap` = CLRS INTERVAL-SEARCH single descent (go left iff left != nil && left.maxHi >= probe.Lo).  `Overlaps(iv)`/`Stab(p)` = pruned in-order DFS yielding ascending (lo,hi) — expected O(log n + k) but a low-Lo probe against many high-Hi nodes degrades toward O(n) (documented, don't "fix"); `Stab` is just `Overlaps([p,p])`.  `Min`/`Max` are (lo,hi)-extremes.  Plain iterators walk LIVE nodes (successor/predecessor, rb_tree pattern).  Naming deviates from the backlog sketch: `AnyOverlap` (not AnyOverlaps), `Overlaps` (not OverlapsAll).

Panic contract is exactly 4 (b_tree shape): `NewIntervalTreeFunc(nil)`, `Insert` on nil, `Insert` on zero-value, `Insert` with `Hi < Lo` (inverted interval — no closed-set meaning).  Queries never validate the probe (inverted probe = unspecified non-panicking answer); deleting an inverted probe naturally misses.

The phase-2 set-convenience capabilities live in `capabilities.go` in the **map-shaped reduced form the tries use**: `Slice`/`String`/`StringFunc` (ascending (Lo, Hi); default render `Lo..Hi`), `Equal` (**interval keys only** — values are `V any` and comparing them needs boxing; loudly documented, trees with identical intervals and different values are Equal), `Clone` (structural copy carrying iv/val/**maxHi**/red with parent rebuild — clone passes `checkInvariants`, which re-verifies maxHi), `Contains` (**exact-match** Search found-flag, NOT an overlap test — that family is `AnyOverlap`/`Overlaps`/`Stab`), `ContainsSlice`/`ContainsAny`, `DeleteSlice`, `DeleteFunc` over `(iv, val)` pairs (collect-then-delete via `All`).  **No `InsertSlice`/`InsertIter`** — a map-shaped batch insert would need key/value pairs; callers loop (the tries precedent).  None of the new methods panics — no `insertContractCheck` exists in this package.

`interval_tree_ts` is the self-contained twin (tree twins are copies, not wrappers — its `Interval[K]` is structurally identical; twin-switching = assigning the two fields): nil guards BEFORE lock, `interval_tree_ts:`-prefixed panics, eager-snapshot `All`/`Backward` (toPairs) / `Overlaps`/`Stab` (nlOverlaps snapshot), `Delete` write-locked across the splice, `Dump` holds the read lock and computes depth lock-free (never call `Depth` from `Dump` — queued-writer RLock deadlock).  It mirrors the capability menu with the twin lock discipline: `Slice` = RLock + `toPairs` + project (nil when empty), `ContainsSlice`/`ContainsAny` under one RLock via `NlSearch`, `DeleteSlice`/`DeleteFunc`'s delete pass atomic under one write-lock hold via `NlDelete`, compute-after-snapshot for `String`/`Equal`/`DeleteFunc`'s match pass, `Equal` never two locks, `Clone` = structural copy under RLock (BatchAtomicity test uses `DeleteSlice` — there is no batch insert to race).  Unlike rb_tree_ts it exports the REAL `Lock`/`Unlock` + `Nl*` (`NlIsEmpty`/`NlLen`/`NlSearch`/`NlInsert`/`NlDelete`/`NlAnyOverlap`/`NlTruncate`; the skip_list_ts/trie_ts surface) because the atomic compound is the point of the structure: **check-overlap-then-book** — `Lock` + `NlAnyOverlap` + `NlInsert` + `Unlock` (`ExampleIntervalTree`, `TestLockNlCompound` races it against a concurrent writer and asserts no booking ever overlaps).  Tests: `checkInvariants` in thorough_test.go (BST order by ivCmp, maxHi == subtree max, all five red-black properties + parent pointers, count == Len) — call after structural changes; `TestTreeRandomizedModel` (PCG 42,7, 4000 steps — SAME seed/steps in both twins) cross-checks Insert/Delete/Search/AnyOverlap/Overlaps/Stab against a sorted-slice O(n)-scan oracle plus full-state All/Backward/Min/Max every 37 steps; `TestDepthBalance` (100k sequential inserts, depth <= 2·log₂(n+1)); race trio + `TestIteratorSnapshotSemantics` in the ts tests.  Benches: Insert ~68 ns/element, Search ~39 ns, AnyOverlap 21 ns single descent.
