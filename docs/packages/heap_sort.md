# heap_sort notes

`HeapSort[T any]` composes `pluto/heap` (the second intra-pluto composition, after `priority_queue` — a sorter is exactly a heap being drained): it stores just the heap, no comparator copy of its own, because nothing builds a snapshot — `Sort`/`SortDown` drain via the heap's `Pop` and return a `[]T` of copies; the drained slots are zeroed by the heap.  Two constructors (`NewHeapSort[T cmp.Ordered]` / `NewHeapSortFunc`).  `InsertArray` = `AppendHeap` + the bottom-up `Heapify` rebuild (`i = Len()/2-1` down to 0) and may be interleaved with `Insert` (each batch re-heapifies the combined data); the batch is copied in, so the caller's slice can be mutated afterwards.  The sort is **not stable** — equal elements may come out in any relative order.  Panic contract: exactly 3 (`NewHeapSortFunc(nil)`, `Insert`/`InsertArray` on nil or zero-value); no-op `Lock`/`Unlock` kept.

`heap_sort_ts` is the thread-safe twin, composing `pluto/heap_ts` the same way (pluto's own design; its README documents it alongside pluto's `heap_sort`).  Like `priority_queue_ts` it has **no lock of its own**: every operation delegates to the heap's guarded methods, and `Lock`/`Unlock` are the real exposed write lock delegating to the heap's.  The three multi-step operations — `InsertArray` (append + rebuild) and `Sort`/`SortDown` (drain) — hold the heap's write lock for the whole operation (atomic), which is why `heap_ts` grew `NlAppendHeap`/`NlHeapify`: a concurrent `Insert` landing between the plain package's append and its per-node heapify would break the heap invariant.  Its `Nl*` set is `NlLen`/`NlIsEmpty`/`NlInsert`/`NlInsertArray`/`NlSort`/`NlSortDown` for atomic insert-batch-then-sort sequences.  Race coverage lives in `TestConcurrentInsertSort`/`TestConcurrentCompoundSort`/`TestLockNlCompound`, whose accounting checks that every distinct inserted key comes out exactly once across all concurrent results (a torn compound would surface as an inversion or a lost/duplicated key).
