# hash_tab_dll notes

`HashTab[T any]` is the fixed-size hash table whose buckets are each a `*dll.Dll[T]` — the fourth intra-pluto composition after `priority_queue`/`heap`, `heap_sort`/`heap`, and `hash_tab_bt`/`binary_tree` (a bucket that is a doubly linked list with O(1) splice-out is exactly what `dll` is — the counterpoint to `hash_tab`'s self-contained chains, because here the bucket *does* use dll's prev pointers: `DeleteFound` splices a located element out through them).  The differentiator in the family: `Search` returns a live `(*dll.DllElement[T], bool)` **handle** — the one pointer-handle find in the pluto hash tables, inherited from dll's own Search, because the handle is what makes `DeleteFound(el)` **O(1)** (hash `el.GetData()`, then the bucket's splice — no chain walk).  The handle must be a live element of this table (same contract as `dll.DeleteFound`); elements are stored by value inside the nodes (`GetData` returns `T`), and a handle stays valid across an `Insert` replacement (the replacement is `SetData` on the same node).  Two constructors, `NewHashTab[T comparable](n)` (== + per-table random maphash seed) and `NewHashTabFunc(eq, hash func(T) uint64, n)`; the eq+hash pair **must agree**.  n buckets (n ≥ 5) fixed for the life of the table.  `Insert` **replaces** an equal element and returns bool like `hash_tab`/`hash_tab_bt`.  `Walk`/`All`/`Values`/`Dump` visit bucket order and, within a bucket, dll head-to-tail = **newest-first** — same as `hash_tab`'s chains, opposite of `hash_tab_bt`'s in-order trees; `Walk` is false-to-stop with the bucket index as pos.  `Dump` shows no hash values (dll nodes keep none).  `ItemExists` is dropped (Search's found covers it).  Panic contract: exactly 4, identical in shape to `hash_tab`/`hash_tab_bt`/`hash_grow`; nil and zero-value tables tolerate every read (empty tables report not-found from `DeleteFound` before touching any bucket).  The twin is pluto's own design.  `checkInvariants[T comparable]` in thorough_test.go inspects the buckets through dll's public `All`/`Len` (dll's fields are not visible from this package) to verify placement (bucketOf(hashOf(x)) == stored bucket), bucket totals == `Len`, Search hits every element, and `All` agreement — call it after structural changes (single-goroutine tests only; it reads internals without the lock).

`hash_tab_dll_ts` is the twin with the `lock sync.RWMutex` — but like `hash_tab_bt_ts` the buckets stay **plain `dll` lists**, not `dll_ts`: one table lock guards everything, and n per-bucket locks would be redundant.  Nil guards come **before** the lock acquisition, `All`/`Values` copy a **value snapshot at call time** under the read lock, and `Walk`/`Dump` hold the read lock for the whole traversal.  It exposes the **real `Lock`/`Unlock`** (nil no-ops) plus `NlIsEmpty`/`NlLen`/`NlSearch`/`NlInsert`/`NlDelete`/`NlDeleteFound` for compound operations (`NlInsert` is the Insert body, so it carries the zero-value panic); calling a locked public method while holding `Lock` deadlocks.  The handle contract gains a concurrency clause: a handle returned by the standalone `Search` can go stale between the Search and its use (stale `DeleteFound` is undefined, the same contract as dll/dll_ts), so the race-free locate-then-splice is `Lock` + `NlSearch` + `NlDeleteFound` + `Unlock` — `TestConcurrentCompound` and `TestLockNlCompound` cover it.  Race coverage lives in `TestConcurrentInsertSearchIterate`/`TestConcurrentDelete`/`TestConcurrentCompound` in thorough_test.go.

`capabilities.go` (set-capabilities phase 1, both packages, method-for-method identical) adds the go-set surface: `Slice`/`String`/`StringFunc`/`Equal`/`Clone`/`Contains`/`ContainsSlice`/`ContainsAny`/`InsertSlice`/`InsertIter`/`DeleteSlice`/`DeleteFunc`.  None of them touch the Search handles — every element flows by value through the value-based Insert/Delete (`Contains` discards NlSearch's handle under the lock; `DeleteFunc` deletes via `Delete`, never `DeleteFound`), so no live handle escapes into caller code.  `String` is deterministic *because it sorts the formatted element strings* (`g_lib.FormatSorted`) — the random seed never leaks (tested).  `Slice` is bucket order = unspecified (documented; callers sort); within a bucket it is dll head-to-tail = newest-first.  `Clone` rebuilds each bucket list with `dll.NewDllFunc(tt.eq)` walking the source head-to-oldest and `AppendAtTail`ing — the clone's lists keep exactly the receiver's newest-first order (contrast hash_tab's Clone, which copies chain nodes in chain order — same result, different mechanism).  `Equal` is membership-based (eq/hash-consistency precondition; nil == empty).  `DeleteFunc` is collect-then-delete.  `InsertSlice`/`InsertIter` share `insertContractCheck(caller)`/`insertAll`; the panic fires **only when the batch would store an element**, messages prefixed `hash_tab_dll:`/`hash_tab_dll_ts:`.  `InsertIter` drains the iterator **before** inserting (self-feeding safe).  nil `fx`/`format` args: `DeleteFunc`/`StringFunc` return false/"[]" — no new panics.  The twin follows the standard capability lock discipline (mutating batches one write lock for the whole batch, `DeleteFunc` predicate and `StringFunc` format run unlocked on a snapshot, `Equal` never holds two locks, no new `Nl*`); `capabilities_test.go` is the plain package's file verbatim plus the twin-only block at the bottom — keep them in sync.
