# hash_grow notes

`HashTab[T any]` is the auto-growing hash table (open addressing, linear probing, backward-shift deletion, double on load factor > saturation).  It is the first equality+hashing package: `NewHashTab[T comparable](n, saturation)` uses `==` and hashes with a **per-table random `hash/maphash` seed** (`maphash.Comparable`) — bucket order and `Dump` hashes are nondeterministic across processes, so tests/examples never assert them (the test suite uses `NewHashTabFunc` with deterministic FNV when it needs to reason about placement, e.g. `findKeyWithHome`); `NewHashTabFunc(eq, hash func(T) uint64, n, saturation)` takes both functions, which **must agree** (equal ⇒ equal hash).  Empty buckets are marked by a zero raw hash in `originalHash []uint64` (a hash of exactly 0 is remapped to 1 on every path ); `Truncate` `clear`s both slices.  `Insert` returns bool (added vs replaced), value semantics throughout (`Search` returns `(T, bool)`), `Walk` is `func(pos int, data T) bool` with **false-to-stop** (the tree convention, not dll's) and no depth/userData.  Probes stop after one full cycle, and an insert into a completely full table (saturation ≥ 1.0) **forces growth** instead of being silently dropped; saturation ≤ 0 or NaN selects the 0.5 default.  Panic contract: exactly 5 situations (`NewHashTabFunc` nil eq or hash, `n < 5`, `Insert`/`Upsert`/`GetOrInsert`/`UpsertFunc` on nil, `Insert`/`Upsert`/`GetOrInsert`/`UpsertFunc` on zero-value, `UpsertFunc` with a nil fn; `Remove` tolerates both like `Delete`).  `checkInvariants` in thorough_test.go verifies occupancy ⟺ non-zero hash, occupied == Len, Search finds every element, and iterator/bucket agreement — call it after structural changes.

`hash_grow_ts` is the twin with the `lock sync.RWMutex`: nil guards come **before** the lock acquisition (a nil-receiver `lock.RLock()` would itself panic), `All`/`Values` copy a **value snapshot at call time** under the read lock (value copies, as in queue_ts/heap_ts), and `Walk`/`Dump` hold the read lock for the whole traversal so callbacks must not touch the table.  It exposes the **real `Lock`/`Unlock`** (nil no-ops) plus `NlIsEmpty`/`NlLen`/`NlSearch`/`NlInsert`/`NlDelete`/`NlUpsert`/`NlGetOrInsert`/`NlRemove`/`NlUpsertFunc` for compound operations (`NlInsert`/`NlUpsert`/`NlGetOrInsert`/`NlUpsertFunc` are the method bodies, so they carry the zero-value panic; the public forms check nil before taking the lock); calling a locked public method while holding `Lock` deadlocks.  Race coverage lives in `TestConcurrentInsertSearchIterate`/`TestConcurrentDelete`/`TestConcurrentCompound` in thorough_test.go.

`capabilities.go` (set-capabilities phase 1) adds the go-set surface: `Slice`/`String`/`StringFunc`/`Equal`/`Clone`/`Contains`/`ContainsSlice`/`ContainsAny`/`InsertSlice`/`InsertIter`/`DeleteSlice`/`DeleteFunc`, in both the plain package and the twin.  `String` sorts the formatted strings (`g_lib.FormatSorted`) — deterministic output despite the random seed (two separately built tables print identically; tested).  `Slice` is slot order = unspecified (depends on seed **and growth history**).  `DeleteFunc`'s collect-then-delete is **mandatory** here, not just tidy: `Delete`'s backward-shift moves elements between slots, so a delete-during-slot-walk would double-visit moved elements and skip others (the mass-delete test re-verifies every membership after deleting ~half of 1000).  `Clone` copies `buckets` + `originalHash` arrays plus size/saturation/generation/eq/hash — zero-value clones with `buckets == nil` stay nil-backed (`if tt.buckets != nil` guard, so a zero-value table clones to a genuine zero value).  `InsertSlice`/`InsertIter` share `insertContractCheck`/`insertAll` — insert contract fires only when an element would be stored, messages name the actual method.  In the twin: mutating batches atomic under one write lock (`TestCapabilitiesBatchAtomicity`), `DeleteFunc` predicate + `StringFunc` format run **unlocked on a snapshot** (call-backs legal), `Equal` never holds two locks.  `capabilities_test.go`/`capabilities_example_test.go` are the hash_grow files mirrored (constructor gains the saturation arg).

**Scan (both packages, note/11):** cursor-based incremental Scan lives in `scan.go` — a **generation-stamped cursor** (high 32 bits `generation`, low 32 the next bucket index), NOT Redis's reverse-binary: open addressing gives no twin-bucket split on a rebuild (a probe chain can move an element backward), so no bucket-order enumeration survives a resize.  `generation` bumps in `grow()` and `Truncate`; a stale-generation cursor restarts the walk at bucket 0 (duplicates allowed, coverage kept).  The at-least-once guarantee is exact for a frozen table and across growths; under arbitrary insert/delete churn it is best-effort — a delete's backward-shift repair can carry a present element backward across the cursor (documented in `scan.go`; the churn tests assert termination, the frozen/grow tests assert exact coverage).  The ts `Scan` takes the read lock per batch, none held across calls.

**Probe fast paths (both packages).** Every probe loop (`Search`/`NlSearch`, `Delete`/`NlDelete`, `insertNewItem`) checks `originalHash[i] == rh` **before** calling `eq`. This is sound because the eq/hash agreement contract means a different stored hash can never be an equal element. Without the check, every occupied slot along a chain costs an indirect equality call (string compares dominated bimap's profile). The home bucket comes from `home(rh)`: a mask when `size` is a power of two (sizes only double, so this holds whenever the constructor's `n` does, which covers every in-repo caller), and `%` otherwise. **Don't reintroduce `rh % size` on the hot paths**, because the division shows up in profiles. `TestSharedHomeDistinctHashes` (identity hash, keys sharing a home bucket) counts equality calls and fails if the stored-hash check is removed; the size-5/7 tests keep the `%` fallback covered. An inline `{hash, item}` slot layout was measured and rejected (docs/benchmarks/bimap/README.md): +3% for bimap, −4% for hash_set mixed.

**Single-probe compound operations (both packages, `upsert.go`).** `Upsert(item) (old T, replaced bool)`, `GetOrInsert(item) (existing T, found bool)` and `Remove(find) (removed T, found bool)` replace the Search+Insert / Search+Delete pairs every caller wrote: one `hashOf` (so the 0→1 remap applies), one walk of the chain. `probe(rh, item)` returns either the equal element's slot or the chain's first empty slot (correct as the insert point only because backward-shift deletion leaves no tombstones), or -1 for a completely full table; `placeNew` then grows-and-reprobes for -1 and applies Insert's load-factor growth afterwards. `Remove` and `Delete` share `deleteAt(h)` (the backward-shift tail, factored out of Delete unchanged; A/B showed no Delete regression). `replaced` is exactly `!Insert(...)`; `GetOrInsert` never overwrites and returns the inserted `item` on a miss (the `sync.Map.LoadOrStore` convention). Their panics use `writeContract(method)` (message names the method and the constructors). `upsert_test.go` (identical in both packages) runs a seed-42 model against a Go map under four hash shapes (FNV, constant, all-zero, few-homes) × three size/saturation configs (incl. size 5 sat 1.0 to hit the full-table and `%` paths), re-verifying every membership after each removal; it also counts hash calls (exactly 1 per call) and eq calls (`TestSingleProbeStoredHashPrefilter`). The twin adds Nl/parity-with-plain/race tests in `upsert_concurrency_test.go` (GetOrInsert atomicity: exactly one goroutine per key sees `found == false`). Gains (M4 Max, plain / ts): replace-and-return 23.6→15.8 / 31.8→22.7 ns; remove-and-return 37.0→29.2 / 53.7→46.0 ns; a growth-dominated build-from-16 graph-index workload only 2–5% (rehashing dominates). `lfu.Touch` is a read-modify-write (new counter depends on the old one), so Upsert could not fold it into one probe — that is what `UpsertFunc` (next paragraph) is for.

**Read-modify-write: `UpsertFunc` (both packages, `upsert.go`).** `UpsertFunc(item T, fn func(existing T, found bool) T) T` — one `hashOf(item)`, one `probe`; `fn` gets the stored equal element (`found == true`) or `item` (`found == false`), and its result is stored in that slot (hit: `buckets[slot] = v`, the stored hash stays `rh`; miss: `placeNew(slot, rh, v)`, so the full-table forced growth and the load-factor growth are exactly Insert's) and returned. By-value: `fn` receives a copy, no `*T` into storage ever escapes. Invariants to keep: (1) **`fn` runs before any write** — on a miss it is called *before* `placeNew`, so a panicking `fn` leaves no half-inserted slot, no length change and no growth (not even the full-table pre-growth; `TestUpsertFuncPanicLeavesTableUnchanged` checks size/len/generation/slots for hit, miss, miss-at-threshold and miss-into-full-table, and a "grow before fn" mutant fails it); the twin's deferred `Unlock` releases the lock on that panic (`TestUpsertFuncPanicReleasesLock`). (2) **`fn`'s result must be equal to `item` and hash identically** — documented, NOT checked: verifying would need the second hash + an eq call this method exists to remove, and the table could not repair a violation anyway (same footing as the eq/hash agreement). (3) **`fn` must not call into the same table** — plain: a mutation invalidates the probed slot; twin: `fn` runs under the write lock, so any locked call deadlocks. Nil `fn` panics with a named message (the fifth panic situation) rather than a bare nil-func runtime error. No `Update` (modify-only-if-present) companion was added: lfu — the only caller with a read-modify-write — inserts on a miss, and its reads (`Counter`/`IdleMinutes`) are pure (decay is not stored back), so nothing would use it. Tests: `upsertfunc_test.go` (identical in both packages) — seed-42 model vs a Go map under the four hash shapes × three size/saturation configs, checking every call ran `fn` exactly once with the right `existing`/`found` and that the returned value is what got stored; growth (load factor checked after every insert, generation bump), full-table forced growth, hash-once / stored-hash-prefilter counts, nil/zero-value/nil-fn panics, zero allocs on hit and non-growing miss; twin `upsertfunc_concurrency_test.go` — `NlUpsertFunc` under `Lock`, parity with plain (results + slot order), and a lost-update race test (8 goroutines × 2000 increments on shared counters must sum exactly). Measured (M4 Max, load avg 4.9–6.7 from concurrent agents, 5 interleaved rounds × 0.7 s, medians; `upsertfunc_bench_test.go`, plain / ts): read-modify-write hit Search+Insert 24.4 → UpsertFunc 17.2 / 32.1 → 23.7 ns (≈ −29% / −26%, the same as Upsert's replace 16.8 / 23.3 — the indirect `fn` call is in the noise); miss (+ an identical Delete) 31.6 → 28.2 / 44.6 → 39.9 ns. Mutation-checked (fn given `item` on a hit, `found=false` on a hit, hit result not stored, miss skipping load-factor growth, miss skipping placeNew, insert-before-fn, grow-before-fn): every mutant fails a test.

**Slot layout: re-measured 2026-11-27 and kept as two arrays.** Interleaved A/B (4 rounds × 0.7 s, load avg 3.6–5.4 from concurrent agents, ±3–8% noise), same binaries except the layout: (A) inline `[]struct{hash uint64; item T}`: bimap +4.4%, lfu Add +8.5%, hash_grow Insert +13%, hash_set ±1–3%, MissHeavy +3%, but growth-heavy graph-index workloads −12/−13% (one allocation and local rehash); (B) 8-slot groups (`hash [8]uint64; item [8]T`, keeps hashes dense per cache line): worse nearly everywhere (hash_set +3–7%, lfu Add +9%, Insert +19%; graph −3/−6%) — the `i>>3`/`i&7` indexing costs more than the locality gives. Neither is a clear net win, consistent with the earlier bimap measurement; both reverted. The win for growth-heavy callers is better had by pre-sizing (`n` hint). Benchmarks used: `upsert_bench_test.go` (`BenchmarkUserGraphFuncIndex` mimics generic_graph's Func-config index, which its own benchmarks never exercise; `BenchmarkUserMissHeavy` is a 50% miss probe on a 100k table) plus hash_set, bimap and lfu's own.
