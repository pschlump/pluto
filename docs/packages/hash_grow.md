# hash_grow notes

`HashTab[T any]` is the auto-growing hash table (open addressing, linear probing, backward-shift deletion, double on load factor > saturation).  It is the first equality+hashing package: `NewHashTab[T comparable](n, saturation)` uses `==` and hashes with a **per-table random `hash/maphash` seed** (`maphash.Comparable`) — bucket order and `Dump` hashes are nondeterministic across processes, so tests/examples never assert them (the test suite uses `NewHashTabFunc` with deterministic FNV when it needs to reason about placement, e.g. `findKeyWithHome`); `NewHashTabFunc(eq, hash func(T) uint64, n, saturation)` takes both functions, which **must agree** (equal ⇒ equal hash).  Empty buckets are marked by a zero raw hash in `originalHash []uint64` (a hash of exactly 0 is remapped to 1 on every path ); `Truncate` `clear`s both slices.  `Insert` returns bool (added vs replaced), value semantics throughout (`Search` returns `(T, bool)`), `Walk` is `func(pos int, data T) bool` with **false-to-stop** (the tree convention, not dll's) and no depth/userData.  Probes stop after one full cycle, and an insert into a completely full table (saturation ≥ 1.0) **forces growth** instead of being silently dropped; saturation ≤ 0 or NaN selects the 0.5 default.  Panic contract: exactly 4 (`NewHashTabFunc` nil eq or hash, `n < 5`, `Insert` on nil, `Insert` on zero-value).  `checkInvariants` in thorough_test.go verifies occupancy ⟺ non-zero hash, occupied == Len, Search finds every element, and iterator/bucket agreement — call it after structural changes.

`hash_grow_ts` is the twin with the `lock sync.RWMutex`: nil guards come **before** the lock acquisition (a nil-receiver `lock.RLock()` would itself panic), `All`/`Values` copy a **value snapshot at call time** under the read lock (value copies, as in queue_ts/heap_ts), and `Walk`/`Dump` hold the read lock for the whole traversal so callbacks must not touch the table.  It exposes the **real `Lock`/`Unlock`** (nil no-ops) plus `NlIsEmpty`/`NlLen`/`NlSearch`/`NlInsert`/`NlDelete` for compound operations (`NlInsert` is the Insert body, so it carries the zero-value panic); calling a locked public method while holding `Lock` deadlocks.  Race coverage lives in `TestConcurrentInsertSearchIterate`/`TestConcurrentDelete`/`TestConcurrentCompound` in thorough_test.go.

`capabilities.go` (set-capabilities phase 1) adds the go-set surface: `Slice`/`String`/`StringFunc`/`Equal`/`Clone`/`Contains`/`ContainsSlice`/`ContainsAny`/`InsertSlice`/`InsertIter`/`DeleteSlice`/`DeleteFunc`, in both the plain package and the twin.  `String` sorts the formatted strings (`g_lib.FormatSorted`) — deterministic output despite the random seed (two separately built tables print identically; tested).  `Slice` is slot order = unspecified (depends on seed **and growth history**).  `DeleteFunc`'s collect-then-delete is **mandatory** here, not just tidy: `Delete`'s backward-shift moves elements between slots, so a delete-during-slot-walk would double-visit moved elements and skip others (the mass-delete test re-verifies every membership after deleting ~half of 1000).  `Clone` copies `buckets` + `originalHash` arrays plus size/saturation/generation/eq/hash — zero-value clones with `buckets == nil` stay nil-backed (`if tt.buckets != nil` guard, so a zero-value table clones to a genuine zero value).  `InsertSlice`/`InsertIter` share `insertContractCheck`/`insertAll` — insert contract fires only when an element would be stored, messages name the actual method.  In the twin: mutating batches atomic under one write lock (`TestCapabilitiesBatchAtomicity`), `DeleteFunc` predicate + `StringFunc` format run **unlocked on a snapshot** (call-backs legal), `Equal` never holds two locks.  `capabilities_test.go`/`capabilities_example_test.go` are the hash_grow files mirrored (constructor gains the saturation arg).

**Scan (both packages, note/11):** cursor-based incremental Scan lives in `scan.go` — a **generation-stamped cursor** (high 32 bits `generation`, low 32 the next bucket index), NOT Redis's reverse-binary: open addressing gives no twin-bucket split on a rebuild (a probe chain can move an element backward), so no bucket-order enumeration survives a resize.  `generation` bumps in `grow()` and `Truncate`; a stale-generation cursor restarts the walk at bucket 0 (duplicates allowed, coverage kept).  The at-least-once guarantee is exact for a frozen table and across growths; under arbitrary insert/delete churn it is best-effort — a delete's backward-shift repair can carry a present element backward across the cursor (documented in `scan.go`; the churn tests assert termination, the frozen/grow tests assert exact coverage).  The ts `Scan` takes the read lock per batch, none held across calls.
