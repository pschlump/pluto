# multiway_merge notes

`multiway_merge` is algs4 §2.4 `Multiway.java` as two stateless functions: `MergeK[T cmp.Ordered](streams ...[]T) []T` / `MergeKFunc[T any](fx, streams ...[]T) []T` merge any number of sorted slices into one freshly allocated sorted slice, O(n log₂ k) compares for n elements over k non-empty streams, O(n + k) workspace (result preallocated at the summed length). It composes `pluto/index_pq` (backlog item 23's sketch named it): index = stream id, value = a private `head[T]{v T; id int}` wrapper. **The wrapper is load-bearing for stability**: `index_pq.less` is a strict `< 0` compare with NO tie-break by index, so bare values would pop equal heads in incidental heap order; the wrapper comparator is `(fx(a.v, b.v), then a.id - b.id)` lexicographic — ids are unique, so the order is total and equals from earlier streams come first. The merge is therefore STABLE in the merge_sort sense (stream-major order = concat order), `MergeK(a, b)` IS merge_sort's two-run merge generalized, and the exact test oracle is `slices.SortStableFunc(concat)` (sorted + stable permutation is unique). Loop discipline: `Peek` the min stream, emit, then `Change(id, next head)` — the decrease-key, one sift where Multiway.java pays delMin+insert (the dijkstra pattern on the same queue) — and `Delete(id)` when the stream runs out. Since streams are sorted, `Change` only ever demotes or ties (fix sinks or no-ops), but correctness does not rely on the direction. Panic contract: exactly 1 (`MergeKFunc` with nil fx, message names its function); zero streams / all-empty / nil streams → empty NON-nil `[]T{}` (the n==0 early return also dodges `NewIndexPQFunc`'s n<1 panic — do not remove it); inputs never modified; unsorted input is GIGO (unspecified but deterministic). Stateless → no `_ts` twin (merge_sort/suffix_array precedent).

**Benchmark reality** (M4 Max, 100k ints, PCG-fixed streams, `multiway_merge_test.go`): k=2 1.09 ms, k=16 3.05 ms, k=256 6.38 ms — a clean linear-in-log₂k fit (~0.44 ms fixed + ~0.65 ms per doubling, 6–7 allocs) — against 2.30 ms for a full `slices.Sort` of the same data (the clone-inside-loop baseline keeps pdqsort from seeing sorted data). So the merge beats the full sort ~2.1× at k=2 but the specialized int sort wins past k≈8: every element pays Peek+Change with `fix`'s sink-then-swim attempts and the compare rides an indirect `fx` call through the wrapper. The pattern is still the only tool when the runs exist for free (external sorting, log-structured storage — the result is correct at any k, and the alternative there is a full sort of data that may not fit memory). Oracles: the stability oracle (`thorough_test.go`, PCG 42/7, 1000 rounds, duplicate-heavy keys 4-wide range, unique `id*1000+j` tags, empty streams sprinkled in) against `slices.SortStableFunc` EXACT-equal; the run-merge oracle (shuffle → chunk → sort chunks → merge == full stable sort of the deck, 200 rounds); and `TestAgreesWithMergeSort` (500 rounds of two runs vs `merge_sort.SortFunc` of the concat). `multiway_pq.Example_mergeKSortedSlices` remains the raw-heap teaching example; this package is the first-class API.
