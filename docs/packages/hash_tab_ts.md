# hash_tab_ts notes

`hash_tab_ts` is the twin with the `lock sync.RWMutex` — `hash_tab`'s chained buckets behind one table lock, following the `hash_grow_ts`/`hash_tab_bt_ts` pattern.  Nil guards come **before** the lock acquisition (a nil-receiver `lock.RLock()` would itself panic), `All`/`Values` copy a **value snapshot at call time** under the read lock (the plain package's iterators walk the live chains), and `Walk`/`Dump` hold the read lock for the whole traversal so callbacks must not touch the table.  `Delete` holds the write lock across the chain walk and the unlink (atomic search-and-delete, like `dll_ts`).  It exposes the **real `Lock`/`Unlock`** (nil no-ops) plus `NlIsEmpty`/`NlLen`/`NlSearch`/`NlInsert`/`NlDelete` for compound operations (`NlInsert` is the Insert body, so it carries the zero-value panic); calling a locked public method while holding `Lock` deadlocks.  Race coverage lives in `TestConcurrentInsertSearchIterate`/`TestConcurrentDelete`/`TestConcurrentCompound` in thorough_test.go; `checkInvariants` there reads internals without the lock — single-goroutine tests only.
