= priority_queue

A generic *priority queue* backed by the link:../heap/[`heap`] binary
min-heap: the lowest-priority (minimum) element is always the next to
come out.  A reversed comparison function (`NewPriorityQueueFunc`) makes
the highest priority come out first.

The element type implements no interface: ordering is either the
element type's built-in `<` / `>` operators (`NewPriorityQueue`) or a
caller supplied function (`NewPriorityQueueFunc`) — no boxing, no
dynamic dispatch, no type assertions.  Elements are stored and
returned *by value* (`T`, not `*T`).

== Operations

[options="header"]
|===
| Operation                    | Description                                   | Complexity

| `Insert`                     | Add an element                                | O(log n)
| `Pop`                        | Remove and return the minimum                 | O(log n)
| `Peek`                       | The minimum, without removing                 | O(1)
| `Search(v)`                  | Element + internal position by key-only probe | O(n)
| `UpdatePriority(pos, v)`     | Replace at `pos`, re-heapify in place         | O(log n)
| `Delete(pos)`                | Remove and return the element at `pos`        | O(log n)
| `All`                        | Iterate in *priority order* (non-destructive) | O(n log n) snapshot
| `Len` / `Length` / `IsEmpty` | Size queries                                  | O(1)
| `Truncate`                   | Remove all elements                           | O(1)
| `Slice` / `String` / `StringFunc` | Materialize/render in *priority order* (sorted) | O(n log n)
| `Equal`                      | Multiset equality via the stored comparison function | O(n log n)
| `Clone`                      | Deep copy; the exact layout and pop sequence survive | O(n)
|===

Positions come from `Search` and compose with `UpdatePriority` and
`Delete`; both report `false` for an out-of-range position.  The
element-returning operations (`Pop`, `Peek`, `Search`, `Delete`)
return `(T, …)` with a `bool`/`-1` signal — `Search` returns
`(T, int, bool)` — never a pointer into the queue.  A search probe
only needs the fields the comparison function reads.

`All` yields elements in *priority order* (minimum first) — unlike the
heap's `All`, this one _is_ sorted — by draining a private copy of the
heap taken when `All` is called: the iteration is non-destructive, the
queue is unchanged afterwards, and mutating the queue from inside the
loop is safe.

== Set-convenience capabilities

Priority queues get the minimal menu only — `Slice`,
`String`/`StringFunc`, `Equal` and `Clone`, in
link:capabilities.go[`capabilities.go`].  A priority queue is a
multiset with a pop order, not a set and not a sequence, so there is
deliberately no membership batch and no predicate bulk delete.

This is the one §4.5 package whose materialization order is *sorted*:
`Slice` and `String` yield the elements in priority order, minimum
first — the same order `All` iterates in and the JSON marshal emits
(this queue's `All` is sorted, unlike the heap's).

[source,go]
----
pq.Insert(3)
pq.Insert(1)
pq.Insert(2)

fmt.Println(pq.Slice())  // [1 2 3] — priority order
fmt.Println(pq.String()) // [1 2 3]
----

`Equal` is *multiset* equality: same length and the same
priority-ordered sequence, so two queues built from the same elements
in any insertion order are equal.  Because both sides materialize
already sorted by the comparator, no re-sorting happens — and ties are
safe by construction.  It is non-destructive and compares through the
stored comparison function, *never Go's `==`*, so a non-comparable
element type is fine.

`Clone` copies the underlying backing array, which preserves the heap
property exactly: the clone has the same priority order and the same
pop sequence as the receiver.

All of them are total functions: none panics on a nil queue or a
zero-value queue, which behave as empty.

== Usage

[source,go]
----
type Task struct {
    Priority int
    Name     string
}

pq := priority_queue.NewPriorityQueueFunc(func(a, b Task) int {
    return a.Priority - b.Priority
})
pq.Insert(Task{3, "write"})
pq.Insert(Task{1, "review"})

next, _ := pq.Peek() // {1 review} — still queued

// Demote/boost: find by probe, update by position.
if _, pos, found := pq.Search(Task{Priority: 3}); found {
    pq.UpdatePriority(pos, Task{Priority: 0, Name: "write"})
}
// Pop now yields {0 write} first.
----

== Panics

The package panics in exactly three situations — all programmer errors
with no sane fallback:

[options="header"]
|===
| Call | Why 

| `NewPriorityQueueFunc(nil)` | nil comparison function, caught at construction time 
| `Insert` on a nil `*PriorityQueue` | a nil queue cannot store an element 
| `Insert` on a zero-value queue | no underlying heap; the message names the constructors 
|===

Everything else — including `Pop`/`Peek` on an empty queue and every
indexed operation with a bad position — tolerates a nil queue and the
zero value as an empty queue and reports `false`.

Not safe for concurrent use; the mutex-guarded twin is
link:../priority_queue_ts/[`priority_queue_ts`].  The `Lock`/`Unlock`
pair is a no-op kept for API compatibility with that twin.
