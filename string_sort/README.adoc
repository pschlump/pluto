= string_sort

The §5.1 character-key radix sorts from Sedgwick & Wayne, Algorithms,
4th ed. — `LSD.java`, `MSD.java`, `Quick3string.java` — as stateless
in-place functions over `[]string`.  There is no sorter object, no
constructor and no stored state, and no comparison function anywhere:
ordering is by *bytes*, inherently (one 256-bucket alphabet, one
bucket per byte value — the algs4 extended-ASCII assumption, which in
Go covers every string, binary-safe and UTF-8 alike).  The produced
order is byte-wise lexicographic — exactly Go's native string `<`,
the same as `slices.Sort` — with a key that is a prefix of another
sorting first.

* `LSDSort(a, w)` — *least-significant-byte first*: w passes of
  key-indexed counting, one per byte position from `w-1` down to `0`.
  Each pass is a stable counting sort, and least-significant-first
  composition is what makes that correct.  Requires fixed-width keys
  (every key at least w bytes; the textbook contract is exactly w).
  *Stable.*
* `MSDSort(a)` — *most-significant-byte first*: key-indexed counting
  on the leading byte, then recursion inside each bucket on the next
  byte; a key that ends sorts first (the `-1` end-of-key sentinel).
  *Stable.*
* `Quick3String(a)` — *3-way radix quicksort*: partition a band into
  bytes <, =, > a pivot byte, recurse the side bands in place and the
  equal band one byte deeper.  No auxiliary buffer, no 256-bucket
  pass.  *Not stable.*

== Operations

[options="header"]
|===
| Operation            | Description                                              | Complexity

| `LSDSort(a, w)`      | Sort fixed-width `[]string` in place, w counting passes   | O(w·(n+R)) time, O(n+R) space
| `MSDSort(a)`         | Sort `[]string` in place, MSD radix recursion             | between O(n+R) and O(w·(n+R))
| `Quick3String(a)`    | Sort `[]string` in place, 3-way radix quicksort           | O(n log n) expected, O(n·w) worst
|===

R is 256.  For MSDSort the complexity depends on how much the keys
share prefixes — random keys cost about `n·log_R n` bucket work,
degrading toward `w·(n+R)` on long shared prefixes; recursion depth is
at most the longest key's length.  Quick3String's recursion stack is
O(log n) deep in the number of keys plus the length of the longest
shared prefix.  Nil, empty and single-element slices are no-ops for
all three.

== Which sort when

Measured on this repository's reference machine (Apple M4 Max,
`go test -bench=. -benchmem`), sorting 100,000 keys; every figure
includes the O(n) input clone the benchmark performs per iteration:

[options="header"]
|===
| Sorter             | random16 (16 random bytes) | prefixed16 (12 shared + 4) | long64 (48 shared + 16)

| `slices.Sort`      | 9.4 ms                     | 9.3 ms                     | 11.6 ms
| `quick_sort.Sort`  | 11.9 ms                    | 11.9 ms                    | 14.5 ms
| `LSDSort`          | 4.6 ms                     | 6.2 ms                     | 25.3 ms
| `MSDSort`          | **2.5 ms**                 | 6.3 ms                     | 18.2 ms
| `Quick3String`     | 6.7 ms                     | **7.9 ms**                 | **11.1 ms**
|===

The textbook guidance, confirmed here: **MSD** is the fastest sort in
the library on random-ish keys (3.7× `slices.Sort`) but pays a
256-count pass per shared-prefix level, so long common prefixes drive
it toward its worst case; **Quick3String** is the robust general
default — never far from the best, and the strongest radix choice on
long shared prefixes; **LSD** wins its niche — short fixed-width keys
(IP addresses, license plates, dates) — and loses on long keys because
every one of the w passes is a full counting sort.

== Usage

[source,go]
----
plates := []string{"4PGC938", "2IYE230", "3ATR721", "1ICK750"}
string_sort.LSDSort(plates, 7) // [1ICK750 2IYE230 3ATR721 4PGC938]

words := []string{"she", "sells", "sea", "shells", "by", "the", "sea", "shore"}
string_sort.MSDSort(words)     // [by sea sea sells she shells shore the]
string_sort.Quick3String(words) // same order, in place
----

== Panics

The package panics in exactly two situations — both programmer errors
in `LSDSort`, the only function with a precondition (it reads byte
positions `0..w-1` of every key):

[options="header"]
|===
| Call | Why

| `LSDSort(a, w)` with w < 0 | negative key width
| `LSDSort(a, w)` with a key shorter than w | fixed-width precondition violation
|===

Everything else — including nil, empty and single-element slices, and
every input to `MSDSort`/`Quick3String` — is tolerated; those two
functions never panic at all.

== Thread safety

All three functions are *stateless*: they keep no package state and
touch only the slice they are given.  They are safe for concurrent
use on disjoint slices.  Because there is no shared state to guard,
*no `_ts` twin exists or is needed* — there is nothing for a lock to
protect (the `quick_sort`/`geo`/`bitmap` precedent).

== Deviations from the algs4 reference

The three algorithms are `LSD.sort`, `MSD.sort` and
`Quick3string.sort` respectively; the deviations, all documented in
the source, are:

* **Quick3String pivots on the median of three bytes** (band ends and
  middle) instead of the first key's byte, and recurses into the
  smaller side band while looping on the larger.  A library cannot
  pre-shuffle the input the way the textbook client does — the same
  deviation `quick_sort` makes, for the same reason — so sorted and
  reverse-sorted inputs stay O(n log n) with an O(log n) stack
  (asserted by `TestSortedAdversarial` at 100k keys).
* `less(v, w, d)` is `v[d:] < w[d:]` — Go's native byte-wise string
  comparison with shorter-prefix-first — instead of algs4's character
  loop.  Same semantics, fewer instructions.
* MSDSort skips recursion into buckets known empty (algs4 recurses
  and returns immediately).  A no-op elimination; no behavioral
  difference.
* The algs4 `Alphabet` machinery, `InplaceMSD` and American-flag
  sorts are out of scope: keys are always raw bytes (which covers
  every Go string), and the three shipped sorts are the §5.1 classics
  the book teaches.
