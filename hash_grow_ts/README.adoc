= hash_grow_ts

`hash_grow_ts` is a thread-safe generic hash table for Go using open
addressing with linear probing. When the load factor exceeds a configurable
saturation threshold (default 0.5) the table automatically doubles in size
and re-hashes all entries. Every operation is guarded by a `sync.RWMutex`.

It is the thread-safe twin of link:../hash_grow[pluto/hash_grow] — the
same API — with the addition of the `Lock`/`Unlock` pair and the
`Nl*`-prefixed (no-lock) methods for compound operations.

Element data is never boxed into an interface and never unboxed with a type
assertion.

* Elements are stored and returned *by value* (`T`, not `*T`); `Search`
returns `(T, bool)` and `Insert` returns bool — true when a new element
was added, false when it replaced an equal element.
* Keys of types comparable with `==` need no functions at all:
`hash_grow_ts.NewHashTab[string](16, 0)`.  Equality is the `==` operator and
hashing is the stdlib `hash/maphash` with a per-table random seed.
* Any other type — or identity by a single field — takes a plain equality
function *and* a hash function, with no interface to implement.  The two
functions must agree: equal elements must have equal hashes.

The default hashing is *randomized per table* (a `hash/maphash` seed) — a
hash-flooding mitigation.  Bucket order in `All`, `Values`, `Walk` and
`Dump`, and the raw hash values `Dump` prints, therefore vary from process
to process and must not appear in fixed assertions or golden files.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Complexity

[cols="2,1,1,4",options="header"]
|===
| Operation                      | Average    | Worst case | Notes

| `Insert`                       | O(1)       | O(n)       | amortized; growth doubles the table
| `Search`                       | O(1)       | O(n)       | linear probe from the home bucket
| `Delete`                       | O(1)       | O(n)       | backward-shift keeps probe chains intact
| `Upsert`                       | O(1)       | O(n)       | one hash + one probe: insert or replace, returns the replaced element; write lock held across probe and store
| `GetOrInsert`                  | O(1)       | O(n)       | one hash + one probe: returns the stored element, inserts only on a miss; write lock held across probe and store
| `Remove`                       | O(1)       | O(n)       | one hash + one probe: delete and return the stored element; write lock held across probe and store
| `UpsertFunc`                   | O(1)       | O(n)       | one hash + one probe read-modify-write (plus fn); write lock held across probe, fn and store
| `Contains`                     | O(1)       | O(n)       | the found flag of Search
| `IsEmpty`, `Len`, `Length`     | O(1)       | O(1)       |
| `Truncate`                     | O(n)       | O(n)       | clears all buckets for GC
| `InsertSlice`, `InsertIter`    | O(k)       | O(n·k)     | batch insert, atomic under one write-lock hold
| `DeleteSlice`                  | O(k)       | O(n·k)     | batch delete, atomic under one write-lock hold
| `DeleteFunc`                   | O(n)       | O(n²)      | predicate runs unlocked on a snapshot; deletes atomic
| `ContainsSlice`, `ContainsAny` | O(k)       | O(n·k)     | batch membership: all / at least one present
| `Slice`                        | O(n)       | O(n)       | snapshot under the read lock, slot order (unspecified)
| `String`, `StringFunc`         | O(n log n) | O(n log n) | formatted strings sorted — deterministic; format runs unlocked
| `Equal`                        | O(n)       | O(n²)      | membership only; never holds both tables' locks
| `Clone`                        | O(n)       | O(n)       | deep copy under the read lock; keeps size, saturation, eq/hash
| `Walk`, `Dump`                 | O(n)       | O(n)       | read lock held for the whole call
| `All`, `Values`                | O(n)       | O(n)       | snapshot copied under the read lock
| `Scan` (per call)              | O(count)   | O(count)   | read lock per batch, none held across calls
| `Lock` / `Unlock` + `Nl*`      | O(1)       | O(1)       | compound operations
|===

Worst case occurs when many keys collide; the load factor is kept below the
saturation threshold (default 0.5) so average behavior is O(1).  Probes
(`Insert`/`Search`/`Delete`) never run past one full cycle of the table.

A saturation of 1.0 or more defers growth until the table is actually full;
growth is then forced, so a completely full table can neither silently drop
an insert nor wedge a probe.  A saturation ≤ 0 or NaN selects the 0.5
default.

== Usage

[source,go]
----
ht := hash_grow_ts.NewHashTab[string](16, 0) // initial size 16, default saturation 0.5

ht.Insert("alpha")
if v, found := ht.Search("alpha"); found {
	fmt.Println("found", v)
}
ht.Delete("alpha")
----

== Compound operations: Lock + Nl*

`Search` followed by `Delete` is two lock acquisitions — another goroutine
can mutate the table between them.  `Lock` plus the `Nl*` methods
(`NlIsEmpty`, `NlLen`, `NlSearch`, `NlInsert`, `NlDelete`, `NlUpsert`,
`NlGetOrInsert`, `NlRemove`, `NlUpsertFunc`) run the same
steps atomically under one lock hold:

[source,go]
----
ht.Lock()
if v, found := ht.NlSearch(probe); found {
	use(v)
	ht.NlDelete(probe)
}
ht.Unlock()
----

Calling a locking public method while holding `Lock` deadlocks, so inside
the critical section use only the `Nl` methods.  `Lock`/`Unlock` on a nil
table are no-ops.

== Single-probe compound operations

`Search` followed by `Insert` (or by `Delete`) hashes the element twice and
walks its probe chain twice.  Four methods do the combined step with one
hash and one probe walk (plus any growth, exactly as `Insert` grows):

* `Upsert(item T) (old T, replaced bool)` — insert, or replace the stored
  equal element and return it.  `replaced` is the negation of `Insert`'s
  result; `old` is the zero value when nothing was replaced.
* `GetOrInsert(item T) (existing T, found bool)` — return the stored equal
  element (never replacing it); on a miss insert `item` and return it with
  `found == false`.
* `Remove(find T) (removed T, found bool)` — delete and return the stored
  equal element (same backward-shift repair as `Delete`).
* `UpsertFunc(item T, fn func(existing T, found bool) T) T` — the
  read-modify-write (a counter bump, an append, a merge — anything whose
  new value depends on the old one, which `Upsert` cannot express because
  it needs the new value up front).  One hash and one probe on `item`; `fn`
  is called once with the stored equal element (`found == true`) or with
  `item` (`found == false`); its result is stored in that slot (replacing,
  or inserting with `Insert`'s growth rule) and returned.  Values only:
  `fn` gets a copy and returns a value — no pointer into the table.
  Contract, documented and not checked: `fn`'s result must be equal to
  `item` and hash identically (it is filed under `item`'s hash; checking
  would cost the second hash this method exists to avoid) — change only
  satellite fields; `fn` must not call back into the same table (it runs under the write lock, so a locked call deadlocks).  A
  panicking `fn` leaves the table unchanged (it runs before anything is
  written: no half-inserted slot, no length change, no growth) and the write lock is released.

`Upsert`/`GetOrInsert`/`UpsertFunc` carry `Insert`'s panic contract (nil or
zero-value table), and `UpsertFunc` also panics on a nil `fn`; `Remove` tolerates both like `Delete`.
Each takes the write lock once; `NlUpsert`/`NlGetOrInsert`/`NlRemove`/`NlUpsertFunc` are
the no-lock forms for use inside `Lock`/`Unlock`.

== Iteration

`All() iter.Seq2[int, T]` (bucket position and element — a single-variable
range yields the *bucket position*, not the element) and `Values() iter.Seq[T]`
iterate a **snapshot** copied under the read lock when the iterator method
is called, so it is safe to call other table methods — including writes —
from the loop body.  `Walk(fx)` is the callback alternative
(`func(pos int, data T) bool`, returning *false stops the walk*); it holds
the read lock for the whole traversal, so `fx` must not call methods on the
same table.

== Incremental Scan

`Scan(cursor, count)` iterates the table a batch at a time against an
opaque cursor — the Redis SCAN contract, for walking a huge table
without one O(n) stall.  Each call takes the read lock for its
batch only — no lock is held across calls:

[source,go]
----
cursor := uint64(0)
for {
    items, next := ht.Scan(cursor, 100)
    for _, v := range items { use(v) }
    if next == 0 { break }
    cursor = next
}
----

- A full iteration (0 → … → 0) returns every element present for the
  *entire* iteration at least once; elements added or deleted
  mid-iteration may or may not appear, and duplicates are allowed.
  Qualification: a delete's backward-shift repair can move a present
  element backward across the cursor, so under arbitrary insert/delete
  churn the at-least-once property is best-effort — it is exact for a
  frozen table and across growths.
- `count` is a hint, not a limit; `count <= 0` selects a default of 10.
- Resize-safety: the cursor stamps the table generation (bumped by every
  growth and by `Truncate`); a stale generation restarts the walk at
  bucket 0 — re-reporting is allowed, losing elements is not.  (Redis's
  reverse-binary cursor does not apply here: a rebuild of an
  open-addressing table has no clean twin-bucket split.)
- Only 0 is meaningful in a cursor (start/done); a foreign cursor may
  return arbitrary results but never corrupts the table.

== Set conveniences

`capabilities.go` adds the go-set-style surface, all of it additive and
method-for-method identical to link:../hash_grow[hash_grow]'s:

* Materialize: `Slice() []T` — a fresh slice snapshotted under the read
  lock, in slot order (unspecified; sort when order matters).
  `String()`/`StringFunc(f)` render *deterministically*: each element is
  formatted (fmt.Sprint by default), the formatted strings are sorted,
  then joined `[a b c]`-style — the per-table random seed never shows.
  The format function runs on the snapshot without the lock, so it may
  safely call back into the table.
* Compare: `Equal(other)` — same element set by membership, never
  iteration order; a nil table equals an empty table.  Each table is
  touched under its own lock only — never two locks at once — so Equal
  cannot deadlock, even when two goroutines compare the same pair in
  opposite directions.  Precondition: both tables use consistent
  equality/hash functions.
* Copy: `Clone()` — deep copy (fresh bucket and raw-hash arrays, same
  size, saturation and eq/hash) under one hold of the read lock.
* Membership batches: `Contains(x)`, `ContainsSlice(items)` (all present),
  `ContainsAny(items)` (at least one present) — the read lock is held once
  for the whole batch.
* Mutation batches: `InsertSlice(items)` / `InsertIter(seq)` /
  `DeleteSlice(items)` return true when the receiver changed and are
  atomic — the write lock is held once for the whole batch, so an
  interleaved reader sees all or nothing.  `InsertIter` takes any
  container's `Values()` iterator directly, including the table's own
  (safe: the iterator is drained before the lock is taken).
  `DeleteFunc(pred)` snapshots under the read lock, runs the predicate
  with no lock held (it may call back into the table), then deletes the
  matches atomically — collect-then-delete, mandatory with backward-shift
  deletion, which moves elements between slots.

All of them tolerate a nil table and the zero value as an empty table on
the read side, exactly like the core operations.  No new `Nl*` methods:
the capabilities are self-locking, not compounds.

== Panics

The same five situations as link:../hash_grow[pluto/hash_grow], each
message naming the fix:

[options="header"]
|===
| Call | Why

| `NewHashTabFunc(nil eq, ...)` / `NewHashTabFunc(eq, nil hash, ...)` | nil function, caught at construction time
| `NewHashTab`/`NewHashTabFunc` with n < 5 | a smaller table has no headroom
| `Insert`/`Upsert`/`GetOrInsert`/`UpsertFunc` on a nil table | a nil table cannot store an element
| `Insert`/`Upsert`/`GetOrInsert`/`UpsertFunc` (and their `Nl*` forms) on a zero-value table | no equality/hash functions; the message names the constructors
| `UpsertFunc`/`NlUpsertFunc` with a nil `fn` | nothing to compute the stored value with
|===

The batch inserters `InsertSlice`/`InsertIter` raise the same insert
contract — a nil or zero-value table panics when, and only when, the batch
would actually store an element; an empty batch is tolerated everywhere.

Everything else tolerates a nil table and the zero value as an empty table:
searches report not-found, `Delete` returns false, and the iterators visit
nothing.  (`NlInsert`/`NlUpsert`/`NlGetOrInsert`/`NlUpsertFunc` on a zero-value table
panic because they *are* the method bodies.)

== Performance comparison

Benchmarked head-to-head against the other thread-safe pluto hash tables
(500k inserts, 750k searches, 250k deletes, Apple M4 Max):
~36 ns/insert, ~21 ns/search, ~35 ns/delete at ~34 B/elem — the fastest
of the five on all three operation classes, at roughly the 2× memory
floor its 0.5 saturation threshold implies.  The auto-growing open
addressing also makes it insensitive to the initial size hint, unlike the
fixed-size chaining tables.  Full methodology, numbers, and heap
profiles: link:../note/compare-hasing/README.adoc[note/compare-hasing].
