= hash_grow_ts

`hash_grow_ts` is a thread-safe generic hash table for Go using open
addressing with linear probing. When the load factor exceeds a configurable
saturation threshold (default 0.5) the table automatically doubles in size
and re-hashes all entries. Every operation is guarded by a `sync.RWMutex`.

It is the thread-safe twin of link:../hash_grow[pluto/hash_grow] — the
same API — with the addition of the `Lock`/`Unlock` pair and the
`Nl*`-prefixed (no-lock) methods for compound operations.

Element data is never boxed into an interface and never unboxed with a type
assertion.

* Elements are stored and returned *by value* (`T`, not `*T`); `Search`
returns `(T, bool)` and `Insert` returns bool — true when a new element
was added, false when it replaced an equal element.
* Keys of types comparable with `==` need no functions at all:
`hash_grow_ts.NewHashTab[string](16, 0)`.  Equality is the `==` operator and
hashing is the stdlib `hash/maphash` with a per-table random seed.
* Any other type — or identity by a single field — takes a plain equality
function *and* a hash function, with no interface to implement.  The two
functions must agree: equal elements must have equal hashes.

The default hashing is *randomized per table* (a `hash/maphash` seed) — a
hash-flooding mitigation.  Bucket order in `All`, `Values`, `Walk` and
`Dump`, and the raw hash values `Dump` prints, therefore vary from process
to process and must not appear in fixed assertions or golden files.

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Complexity

[cols="2,1,1,4",options="header"]
|===
| Operation                                | Average | Worst case | Notes

| `Insert`                                 | O(1)    | O(n)       | amortized; growth doubles the table
| `Search`                                 | O(1)    | O(n)       | linear probe from the home bucket
| `Delete`                                 | O(1)    | O(n)       | backward-shift keeps probe chains intact
| `IsEmpty`, `Len`, `Length`               | O(1)    | O(1)       |
| `Truncate`                               | O(n)    | O(n)       | clears all buckets for GC
| `Walk`, `Dump`                           | O(n)    | O(n)       | read lock held for the whole call
| `All`, `Values`                          | O(n)    | O(n)       | snapshot copied under the read lock
| `Scan` (per call)                        | O(count) | O(count)  | read lock per batch, none held across calls
| `Lock` / `Unlock` + `Nl*`                | O(1)    | O(1)       | compound operations
|===

Worst case occurs when many keys collide; the load factor is kept below the
saturation threshold (default 0.5) so average behavior is O(1).  Probes
(`Insert`/`Search`/`Delete`) never run past one full cycle of the table.

A saturation of 1.0 or more defers growth until the table is actually full;
growth is then forced, so a completely full table can neither silently drop
an insert nor wedge a probe.  A saturation ≤ 0 or NaN selects the 0.5
default.

== Usage

[source,go]
----
ht := hash_grow_ts.NewHashTab[string](16, 0) // initial size 16, default saturation 0.5

ht.Insert("alpha")
if v, found := ht.Search("alpha"); found {
	fmt.Println("found", v)
}
ht.Delete("alpha")
----

== Compound operations: Lock + Nl*

`Search` followed by `Delete` is two lock acquisitions — another goroutine
can mutate the table between them.  `Lock` plus the `Nl*` methods
(`NlIsEmpty`, `NlLen`, `NlSearch`, `NlInsert`, `NlDelete`) run the same
steps atomically under one lock hold:

[source,go]
----
ht.Lock()
if v, found := ht.NlSearch(probe); found {
	use(v)
	ht.NlDelete(probe)
}
ht.Unlock()
----

Calling a locking public method while holding `Lock` deadlocks, so inside
the critical section use only the `Nl` methods.  `Lock`/`Unlock` on a nil
table are no-ops.

== Iteration

`All() iter.Seq2[int, T]` (bucket position and element — a single-variable
range yields the *bucket position*, not the element) and `Values() iter.Seq[T]`
iterate a **snapshot** copied under the read lock when the iterator method
is called, so it is safe to call other table methods — including writes —
from the loop body.  `Walk(fx)` is the callback alternative
(`func(pos int, data T) bool`, returning *false stops the walk*); it holds
the read lock for the whole traversal, so `fx` must not call methods on the
same table.

== Incremental Scan

`Scan(cursor, count)` iterates the table a batch at a time against an
opaque cursor — the Redis SCAN contract, for walking a huge table
without one O(n) stall.  Each call takes the read lock for its
batch only — no lock is held across calls:

[source,go]
----
cursor := uint64(0)
for {
    items, next := ht.Scan(cursor, 100)
    for _, v := range items { use(v) }
    if next == 0 { break }
    cursor = next
}
----

- A full iteration (0 → … → 0) returns every element present for the
  *entire* iteration at least once; elements added or deleted
  mid-iteration may or may not appear, and duplicates are allowed.
  Qualification: a delete's backward-shift repair can move a present
  element backward across the cursor, so under arbitrary insert/delete
  churn the at-least-once property is best-effort — it is exact for a
  frozen table and across growths.
- `count` is a hint, not a limit; `count <= 0` selects a default of 10.
- Resize-safety: the cursor stamps the table generation (bumped by every
  growth and by `Truncate`); a stale generation restarts the walk at
  bucket 0 — re-reporting is allowed, losing elements is not.  (Redis's
  reverse-binary cursor does not apply here: a rebuild of an
  open-addressing table has no clean twin-bucket split.)
- Only 0 is meaningful in a cursor (start/done); a foreign cursor may
  return arbitrary results but never corrupts the table.

== Panics

The same four situations as link:../hash_grow[pluto/hash_grow], each
message naming the fix:

[options="header"]
|===
| Call | Why

| `NewHashTabFunc(nil eq, ...)` / `NewHashTabFunc(eq, nil hash, ...)` | nil function, caught at construction time
| `NewHashTab`/`NewHashTabFunc` with n < 5 | a smaller table has no headroom
| `Insert`/`NlInsert` on a nil table | a nil table cannot store an element (`NlInsert` on a zero-value table)
| `Insert` on a zero-value table | no equality/hash functions; the message names the constructors
|===

Everything else tolerates a nil table and the zero value as an empty table:
searches report not-found, `Delete` returns false, and the iterators visit
nothing.  (`NlInsert` on a zero-value table panics because it *is* the
Insert body.)

== Performance comparison

Benchmarked head-to-head against the other thread-safe pluto hash tables
(500k inserts, 750k searches, 250k deletes, Apple M4 Max):
~36 ns/insert, ~21 ns/search, ~35 ns/delete at ~34 B/elem — the fastest
of the five on all three operation classes, at roughly the 2× memory
floor its 0.5 saturation threshold implies.  The auto-growing open
addressing also makes it insensitive to the initial size hint, unlike the
fixed-size chaining tables.  Full methodology, numbers, and heap
profiles: link:../note/compare-hasing/README.adoc[note/compare-hasing].
