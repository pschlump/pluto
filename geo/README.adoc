= geo — Redis GEO Geohash Math
:toc:

== Overview

`geo` is the pure geohash math behind the Redis GEO command family
(`note/redis/src/geohash.c`, `geohash_helper.c`, `geo.c`; request
`note/08-geo.md`, built for Ultima's GEOADD / GEODIST / GEOHASH /
GEOPOS / GEOSEARCH / GEOSEARCHSTORE and the legacy GEORADIUS).  Redis
stores every member of a GEO key in a sorted set whose **score is a
52-bit interleaved geohash** of its position; this package produces,
decodes, neighbors and range-queries exactly those scores:

[source,go]
----
import "github.com/pschlump/pluto/geo"

score, err := geo.Encode(51.5074, -0.1278)   // what GEOADD stores
lat, lon := geo.Decode(score)                // what GEOPOS reports
d := geo.Distance(51.5074, -0.1278, 40.7128, -74.0060)

ranges, err := geo.RangesForRadius(51.5074, -0.1278, 5000)
for _, r := range ranges {
	// look up scores in [r[0], r[1]) in the sorted set ...
}
// ... then keep each candidate when
// geo.Distance(51.5074, -0.1278, candLat, candLon) <= 5000
----

There is no state, nothing to construct, and no `_ts` twin (the
`substring` / `quick_sort` / `lzw` / `maxflow` precedent): pure
functions over floats and integers, safe for concurrent use as-is.

== The score layout

26 bits of latitude interleaved with 26 bits of longitude — latitude in
the **even** bit positions 0,2,…,50, longitude in the **odd** positions
1,3,…,51, so read MSB-first the score alternates lon,lat,lon,… starting
with longitude's top bit (the standard geohash bit order).  The
latitude range is the Web-Mercator bound ±85.05112878 (EPSG:900913 —
the poles are not encodable), longitude is ±180, and the boundary
values themselves are legal, as in Redis.  Encoding the exact
north-east corner sets two spill bits above the nominal space — Redis
stores 13510798882111488 there — so cell intervals may reach
`scoreSpaceTop` = 13·2⁵⁰.

== Functions

[cols="2,3,1",options="header"]
|===
| Function | Description | Complexity

| `Encode(lat, lon)`    | The 52-bit score GEOADD stores for the position. | O(1)
| `Decode(hash)`        | Center of the cell the score names — GEOPOS.     | O(1)
| `Neighbors(hash)`     | The 8 adjacent cells, N, NE, E, SE, S, SW, W, NW. | O(1)
| `RangesForRadius(lat, lon, radiusMeters)` | Score ranges covering the circle. | O(1) (≤26 coverage checks)
| `RangesForBox(lat, lon, widthMeters, heightMeters)` | Score ranges covering the rectangle. | O(1)
| `Distance(lat1, lon1, lat2, lon2)` | Haversine great-circle distance in meters — GEODIST. | O(1)
| `ToMeters`, `FromMeters` | Unit conversion for m, km, ft, mi (case-insensitive). | O(1)
|===

Constants: `StepBits` (26 per axis), `ScoreBits` (52),
`LatMin`/`LatMax`/`LonMin`/`LonMax`, `EarthRadiusInMeters`
(6372797.560856, the quadratic-mean WGS-84 radius `geohash_helper.c`
uses — not the 6371 km textbook sphere).

== Redis compatibility

*Encode, Decode, Neighbors and the radius→step estimator are
bit-compatible with the Redis C code*, pinned by vectors baked into the
tests from two independent oracles that agree with each other:

* a harness compiling the actual `note/redis` sources (v8.9.241),
  printing `%.17g` / exact-integer vectors — encode at every step 1–26,
  decode, neighbors, step estimation, 710 range queries, distance;
* a live Redis server (v7.2.7): GEOADD + ZSCORE for the stored scores,
  GEOPOS for decoded positions, and a 20-query GEOSEARCH BYRADIUS
  membership differential.

Two caveats, both inherent rather than porting sloppiness:

* *Distance is not bit-stable.* The Go spec lets the compiler contract a
  multiply feeding an add/sub into one fused op; the package pins its
  products through `math.FMA(x, y, 0)` (a single-rounded multiply, the
  C's two-rounding arithmetic, deterministic on every platform — and
  what keeps `Distance(p, p)` exactly 0), but the *trigonometry* still
  differs by an ulp between libms, which the formula's cancellations
  amplify to ~1e-11 relative for near-coincident points.  The vector
  test tolerates 1e-9 (the note's accuracy gate is ±0.5%).
* *Decode pins the fused edge arithmetic* (`math.FMA(frac, scale, min)`)
  because the reference C compiles that way (clang's default
  contraction) and the `min + frac·scale` addition cancels ~7 digits
  near the band's bottom, where a rounding difference would show far
  beyond an ulp.

Benchmarks (M4 Max): Encode 3.2 ns, Decode 3.5 ns, Neighbors 2.3 ns,
Distance 16 ns, RangesForRadius 88 ns (3 allocs), RangesForBox 113 ns.

== The search contract

`RangesForRadius` / `RangesForBox` return a sorted list of disjoint
half-open ranges `[lo, hi)` whose union is a **conservative-complete
superset** of the query shape: every member inside the shape has its
score inside the ranges (no false negatives — pinned by a 137k-sample
completeness fuzz plus the live-Redis GEOSEARCH differential), and
members outside the shape regularly fall inside them (false positives).
The caller post-filters every candidate exactly — with `Distance` for a
circle, or for a box Redis's two-call rule:

[source,go]
----
inBox := Distance(candLat, lon, lat, lon) <= heightMeters/2 &&
	Distance(candLat, candLon, candLat, lon) <= widthMeters/2
----

(the longitude test runs at the *candidate's* latitude — a box's left
and right edges bend towards the poles).

Antimeridian: neighbors wrap in longitude (the western neighbor of a
+180-hugging cell is past −180), so the ranges stay complete for
circles crossing ±180.  Poles: a shape whose bounding box leaves the
encodable band cannot be covered by any 3×3 window — those queries
return the single full range `[0, scoreSpaceTop)`; scan everything and
post-filter.

== Divergences from the Redis C, all widening or clarifying

The C's area chooser checks window coverage once and decreases the step
**at most one time**; near the poles that is not enough (a circle at
latitude 84 with a 446 km radius spans ±115° of longitude while a
step-4 window spans ~±34°) and Redis silently misses members.  Pluto's
coverage test is arc-correct — it sees that a wrapped east neighbor
covers the box's eastern side across the antimeridian, and that a
top-row center cell has nothing above the band left to cover — and it
**loops** the step decrease until the window provably covers the box,
degrading to the full space only when no window can.  Consequences,
measured over the 710 C vectors:

* 297 queries: identical windows to Redis;
* where Redis's plain comparison forced an unnecessary decrement
  (antimeridian, band-edge centers), pluto keeps the estimated step —
  a *finer* window, still complete;
* where Redis's single decrement under-covers (pole-adjacent shapes),
  pluto walks down or returns the full space — a *wider* window.

Never fewer results than Redis would find; the exact post-filter keeps
the answer right.

== Errors

Data errors are sentinel errors, compared with `errors.Is`:

* `ErrOutOfRange` — latitude outside ±85.05112878 or longitude outside
  ±180 (or NaN); the boundaries themselves are legal, as in Redis.
* `ErrNegativeRadius` — negative or NaN radius / box width / height;
  zero is legal (the tightest precision), as in Redis.
* `ErrInvalidUnit` — a unit other than m, km, ft, mi.

The mile factor is Redis's 1609.34, not the 1609.344 survey mile —
ported exactly so distances match Redis.

== Panics

None.  The package is pure functions; bad input is an error.

== Thread Safety

Safe for concurrent use: no state, no mutable package variables —
every function reads only its arguments.
