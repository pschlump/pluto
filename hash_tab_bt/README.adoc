= hash_tab_bt

`hash_tab_bt` is a generic hash table for Go with a fixed number of
buckets in which *every bucket is a binary search tree*
(link:../binary_tree[`binary_tree`]).  Because collisions are resolved by
a tree rather than a chain, lookups stay logarithmic in the elements per
bucket even under heavy collisions — where the chained
link:../hash_tab[`hash_tab`] degrades to O(n/k) on the same load, this
table holds O(log(n/k)).  The bucket count is fixed at construction.

It is the third intra-pluto composition after `priority_queue` and
`heap_sort`: a bucket that is a search tree is exactly what `binary_tree`
is, so the table stores one `*binary_tree.BinaryTree[T]` per bucket
instead of reimplementing a tree.  Element data is never boxed into an
interface and never unboxed with a type assertion.

* Elements are stored and returned *by value* (`T`, not `*T`); `Insert`,
  `Delete` and `Search` take the probe by value — a probe only needs the
  fields the comparison and hash functions read.
* `Insert` replaces an equal element and returns bool — true when a new
  element was added, false when it replaced one.
* A bucket tree needs an *ordering*, not just an equality.  Tables of
naturally ordered types (all integers, floats and strings) need no
functions at all: `hash_tab_bt.NewHashTab[string](16)` orders with the
builtin `<` and `>` operators and hashes with the stdlib `hash/maphash`
using a per-table random seed.
* Any other type — or identity by a single field — takes a plain
comparison function *and* a hash function, with no interface to implement:
+
[source,go]
----
byID := hash_tab_bt.NewHashTabFunc(
	func(a, b User) int { return a.ID - b.ID },
	func(u User) uint64 { /* hash of u.ID */ },
	8,
)
----
+
The two functions must agree: whenever `cmp(a, b) == 0`, `hash(a)` and
`hash(b)` must be equal, otherwise `Search` and `Delete` look in a
different bucket than the element is stored in.

The default hashing is *randomized per table* (a `hash/maphash` seed) — a
hash-flooding mitigation.  Bucket order in `All`, `Values`, `Walk` and
`Dump` therefore varies from process to process and must not appear in
fixed assertions or golden files.  *Within* a bucket the order is not
random at all: the tree's in-order walk visits the elements ascending per
the comparison function (unlike `hash_tab`'s newest-first chains).

`Dump` prints an `empty` marker for vacant buckets and one line per
element in ascending bucket order; no hash values are shown — the tree
nodes keep none (unlike `hash_tab`'s `h=`-annotated dump).

A hash of exactly 0 needs no remapping — an empty bucket is an empty
tree, not a hash marker (unlike `hash_grow`'s open addressing).

Runnable, tested copies of the examples live in
link:example_test.go[`example_test.go`] — they run under `go test` and appear
on pkg.go.dev.

== Complexity

[cols="2,1,1,4",options="header"]
|===
| Operation                                | Average      | Worst case | Notes

| `Insert`                                 | O(log(n/k))  | O(n)       | tree insert/replace in the hashed bucket
| `Search`                                 | O(log(n/k))  | O(n)       | tree descent in the hashed bucket
| `Delete`                                 | O(log(n/k))  | O(n)       | tree delete in the hashed bucket
| `Contains`                               | O(log(n/k))  | O(n)       | the found flag of Search
| `IsEmpty`, `Len`, `Length`               | O(1)         | O(1)       |
| `Truncate`                               | O(k)         | O(k)       | k = bucket count; bucket trees are emptied
| `InsertSlice`, `InsertIter`              | O(k log(n/k)) | O(n·k)    | batch insert; true if any element was new
| `DeleteSlice`                            | O(k log(n/k)) | O(n·k)    | batch delete; true if any was present
| `DeleteFunc`                             | O(n log(n/k)) | O(n²)     | bulk delete by predicate, collect-then-delete
| `ContainsSlice`, `ContainsAny`           | O(k log(n/k)) | O(n·k)    | batch membership: all / at least one present
| `Slice`                                  | O(n log(n/k)) | O(n²)     | fresh slice; buckets ascending, bucket order unspecified
| `String`, `StringFunc`                   | O(n log n)   | O(n log n) | formatted strings sorted — deterministic
| `Equal`                                  | O(n log(n/k)) | O(n²)     | same element set, membership only (never order)
| `Clone`                                  | O(n log(n/k)) | O(n²)     | deep copy; keeps bucket count and cmp/hash
| `Walk`, `Dump`, `All`, `Values`          | O(n)         | O(n)       |
|===

k = number of buckets.  Average behavior assumes the hashes spread
elements evenly over the buckets; the worst case is every element in one
bucket *and* inserted in sorted order (the unbalanced `binary_tree`
degenerates to a path — the same worst case as that package).  Use
`avl_tree`/`rb_tree`-style buckets or `hash_grow` if that matters.  The
table never grows — pick n for the expected element count, or use
`hash_grow`.

== Usage

[source,go]
----
package main

import (
	"fmt"

	"github.com/pschlump/pluto/hash_tab_bt"
)

func main() {
	ht := hash_tab_bt.NewHashTab[string](16) // 16 buckets, fixed for the life of the table

	ht.Insert("alpha")
	ht.Insert("beta")
	fmt.Println(ht.Insert("alpha")) // false — duplicate replaces the element

	if v, found := ht.Search("alpha"); found {
		fmt.Println("found", v)
	}

	ht.Delete("alpha")

	// Range-over-func iteration (Go 1.23+), in bucket order:
	for pos, item := range ht.All() { // (bucket position, element)
		fmt.Println(pos, item)
	}
	for item := range ht.Values() {
		fmt.Println(item)
	}

	ht.Truncate() // remove everything
}
----

== Iteration

Two styles are supported, both in bucket order (hash-dependent, see the
randomization note above) and — within a bucket — ascending per the
comparison function:

- Go 1.23+ range-over-func: `All() iter.Seq2[int, T]` (bucket position and
  element — as with dll/sll/hash_tab, a single-variable range yields the
  *bucket position*, not the element) and `Values() iter.Seq[T]`.
- The `Walk(ApplyFunction[T])` callback: `fx(pos int, data T) bool`, where
  `pos` is the *bucket index* (no `interface{}` userData — state is
  captured in a closure), returning *false stops the walk* across all
  buckets (the tree-packages convention — dll and sll are the opposite);
  Walk returns true when the walk ran to completion.

== Set conveniences

`capabilities.go` adds the go-set-style surface, all of it additive:

* Materialize: `Slice() []T` — a fresh slice, each bucket's elements
  ascending per the comparison function, buckets in hash order
  (unspecified — sort the slice when a global order matters).
  `String()`/`StringFunc(f)` render *deterministically*: each element is
  formatted (fmt.Sprint by default), the formatted strings are sorted,
  then joined `[a b c]`-style — the per-table random seed never shows in
  the output.
* Compare: `Equal(other)` — same element set by membership, never
  iteration order; a nil table equals an empty table.  Precondition: both
  tables use consistent comparison/hash functions (same constructor over
  the same type always satisfies it).
* Copy: `Clone()` — deep copy: fresh bucket trees rebuilt by insertion,
  same bucket count, same cmp/hash; mutating either table never affects
  the other.
* Membership batches: `Contains(x)`, `ContainsSlice(items)` (all
  present), `ContainsAny(items)` (at least one present).
* Mutation batches: `InsertSlice(items)` / `InsertIter(seq)` /
  `DeleteSlice(items)` return true when the receiver changed;
  `DeleteFunc(pred)` bulk-deletes the predicate's matches with a
  collect-then-delete pass (the table is never modified while walked).
  `InsertIter` takes any container's `Values()` iterator directly —
  including the table's own, which is safe because the iterator is
  drained before the first insert.

All of them tolerate a nil table and the zero value as an empty table on
the read side, exactly like the core operations.

== Panics

The package panics in exactly four situations — all programmer errors with
no sane fallback, each message naming the fix:

[options="header"]
|===
| Call | Why

| `NewHashTabFunc(nil cmp, ...)` / `NewHashTabFunc(cmp, nil hash, ...)` | nil function, caught at construction time
| `NewHashTab`/`NewHashTabFunc` with n < 5 | a smaller table has no headroom
| `Insert` on a nil `*HashTab` | a nil table cannot store an element
| `Insert` on a zero-value table | no comparison/hash functions; the message names the constructors
|===

The batch inserters `InsertSlice`/`InsertIter` raise the same insert
contract as `Insert` — a nil or zero-value table panics when, and only
when, the batch would actually store an element; an empty batch is
tolerated everywhere.

Everything else tolerates a nil table and the zero value as an empty table:
searches report not-found, `Delete` returns false, and the iterators visit
nothing.

== Thread safety

`hash_tab_bt` is *not* safe for concurrent use. Use the
link:../hash_tab_bt_ts[`hash_tab_bt_ts`] package, which guards every
operation with a `sync.RWMutex` and adds `Lock`/`Unlock` plus the `Nl*`
methods for compound operations, when the table is shared between
goroutines.
